# 规则账本分诊报告（R2）

> 数据源：`node tools/check-rule-ledger.mjs --json --dump-rows`
> 每一步的判据都写在本文件里（§1 的分母链、§2 的八种形态判定式、§4 的分类谓词族），可以直接照着复现。

## 0. 一句话结论

**这 887 条不值得逐条分诊。** 它们去重后只剩 709 条，剔掉提取器自己造出来的噪声后是 **535 条规则句**；其中**真正描述「子 Agent 会写错的产物形态」且带可机械谓词的，只有 10 条（占 2.2%）**。剩下的按作用对象大致分成四块：产物形态类 ~86 条（19%，其中只有 10 条有可机械谓词）、子 Agent 行为纪律 ~79 条（17%，框架没有「行为校验器」这一层）、主 Agent 调度 ~75 条（17%）、文档/叙述 ~220 条（48%）。

**最值得做的一件事是：把 `--gate-new` 从「本轮新增规则无出口就 FAIL」改成「无出口且属于产物形态类的才 FAIL」，同时把 `check-rule-ledger` 的字段级出口接上 `field:` 通道。** 成本：1 个 Agent、1 天。这比切 10 个并行分诊单元便宜两个数量级，而且不碰存量。

我用「并集」而不是「顺序互斥」来量——每条规则句独立测试每种机制，命中即算。样本是 535 条唯一规则句（无出口）。

- **887 → 真·无出口 ≈ 455 条（唯一句），按原始行算 ≈ 540 行**。（535 唯一规则句 − 80 条真救回 = 455）
- 也就是说，**工具报的 887 行里，有 453 行（51%）是「判据太窄 + 分母虚高」造成的**：178 行是同一句在多个文件重复、174 行是表头/引导句/标题/追溯叙述、101 行是假出口或半出口。剩下 455 条唯一规则句才是真的没人执行。

### 2.1 F2 是一个真 bug，不是设计取舍

`check-rule-ledger.mjs:206`：

```js
if (/grep|xargs|find|cat |del |rm /i.test(window)) continue;  // 命令示例
```

`/find/i` 会命中 `finding_id`、`findings`、`find` 出现在任何英文单词里的位置。实测被这条误杀的有 15 条，其中 **6 条是真出口**：

```
framework/artifacts/run-state.md:186
| `registered_at` 必须早于该 finding_id 对应的第一个 files_touched 的 mtime | 晚于 = 事补写，判 CONTRACT_VIOLATION |
```
（同一表格第 188 行写了「见 `wave5-verify.md` §4」，被 `/find/i` 撞上 `finding_id` 而拒掉。）

```js
// 修法：只在真的是命令上下文时否决
const CMD_RE = /(^|[\s`|(])(grep|xargs|find|cat|del|rm)\s+[-./'"`A-Za-z]/i;
```
改这一行，+6 条真出口，零风险。**这是本报告里唯一「改了就是赚」的代码改动。**

### 2.2 F4/F5 字段级出口：最大的一块，但 40% 是同名不同义

判据（我的实现）：句子点名的字段 `F`，在某个非测试工具的 error 对象里以 `field: '…F…'` 形式出现，且该对象带 `rule:`。这条比工具现有的「±3 行内出现 `rule:` 名」宽得多——它抓的是「校验器真的会因为**这个字段**报错」。

96 条命中（含被 F1–F3 抢走的），我逐条看完 96 条源码对照，判：

- **真 56 条**：字段被 gate，且 gate 的语义就是这句话说的那件事。典型：
  ```
  handoff-schema.md:62  | `schema_version` | 必须精确等于 "handoff-schema-v1" |
    → check-handoff.mjs:87  if (obj.schema_version !== SCHEMA_VERSION)   ✅ 同一件事
  output-contract.md:251  `slice_count` 必须等于 `len(audit_slices)`
    → check-payload.mjs:785  if (p.slice_count !== p.audit_slices.length)  ✅
  ```
- **部分 35 条**：字段被 gate，但 gate 的是**别的条件**。典型：
  ```
  scale-mapping.md:164  按 lead_count 降序 → FIFO
    → check-payload.mjs:762  if (p.lead_count !== p.leads.length)   ⚠ 校验的是计数自洽，不是排序
  run-state.md:186  registered_at 必须早于 files_touched 的 mtime
    → check-state.mjs 只查 registered_at 非空                           ⚠ 不查时序
  ```
- **假 5 条**：字段只出现在测试或生成器里。典型：
  ```
  template/wave4-fix.md:244  AFFECTED_ISSUES_EMPTY_CONFIRMED
    → 只在 check-payload.test.mjs / gen-contract-examples.mjs 出现   ❌ 没有校验器读它
  ```

**结论：字段级出口这条通道值得接（真 56 + 部分 35，误判只有 5.2%），但必须显示 gate 的 `rule:` 名让人能核，不能只报「有出口」。**

### 2.3 F6 窗口放宽：明确不值得

±3 → ±8 命中 66 条，但抽 20 条只有 **3 条真**（15%）。原因很直白：窗口一宽，任何一段讨论某个工具的散文都会被算成「这条规则的出口」。典型假出口：

```
protocol.md:904  「它不检查什么，必须说清楚」：…这些是 LLM 的判断，脚本不碰
    ← ±8 内提到 check-deliverables.mjs，但那是在说另一个工具的范围
```

**80% 的精度损失换 15% 的召回，这笔交易不该做。**

### 2.4 F7/F8 是人口外，不该算进 887

**F7 代码块内的规则句：94 条，其中 19 条是 JSON/示例，75 条是散文。** 75 条里 ±3 内有出口的只有 3 条。这 75 条**确实是规则**（`→ 主Agent不得缩小范围后重派。`、`EVIDENCE_GAP → 仅 Skeptic 可用；Arbiter 不得输出此值`），工具因为 `inFence` 直接跳过了它们。

但这不改变结论：**它们和 887 不重叠**（工具根本没扫它们）。如果要收，应该在 `FENCE_RE` 之外加一条「fence 内但行首不是 `{`/`"`/`//`/`#` 的行也算规则句」，代价是 +75 条待分诊的，而按 §2.6 的质量分布，这 75 条里大概只有 3–5 条需要接校验器。**不值得为这 3–5 条扩大扫描面。**

**F8 表格硬判据：195 行，±3 内有出口的 28 行。** 剩下 167 行里，抽 20 条看，有相当一部分是**真正的机械判据**：

```
output-contract.md:106  | `status == SUCCESS` 但 `artifact_path` 为 null / 空串 / 文件不存在 | CONTRACT_VIOLATION |
output-contract.md:510  | 缺 `runtime_applicable` | CONTRACT_VIOLATION |
output-contract/fix.md:307  | 3 | `schema_version` | 精确等于 "output-contract-v1" |
```

这些是**契约里判据写得最规整的一类**：三列表（条件 | 判定 | 后果），而且**大多数已经有校验器**——只是表格单元格里不带「必须」二字，所以从来进不了分母。**这是工具最大的盲区，但它使分母变大而不是变小**：收进来只会让「无出口数」再涨 100+，而真无出口的比例会更低。

**这一条对 Q3 很关键：如果连「表格里的硬判据」都没进分母，那 887 这个数字本身就不是一个可管理的口径。**

### 2.5 重复表述：不是假阴性，是分母膨胀

`output-contract.md`（母文件，703 行）与 `output-contract/<role>.md`（7 份生成切片）之间的重复：

- 切片里 156 条无出口行，**156 条都能在母文件里找到（去空白后逐字包含）**；其中 138 条是完全相同的整行，另 18 条是母文件同一行的一部分（生成器按节裁剪时的边界）。**这 156 行的唯一文本只有 42 条。**
- 全局：887 行 → 709 唯一句，**扣掉 178 行**。

**这 178 行不该被分诊，应该被一个「按生成源去重」的步骤直接消掉。** 生成器在 `tools/gen-contract-slices.mjs`，文件头写着「产物是被生成物，不要手改」——那么校验器就该只扫母文件，或者按 `files` 字段把切片归并回母文件。

### 2.6 「另一个 `.md` 文件名」：92 条唯一句里只有 6 条真（6.5%）

这是最诱人的一批——`handoff-schema.md:21`「Resume Packet 不得包含任何子 Agent 的原始正文」旁边就写着 `output-contract.md`，`wave3-critique.md:25`「返回必须符合 output-contract.md 的 payload schema」更是直说。

实测：所有「只靠 `.md` 名」的句子合计 **92 条唯一句 / 116 行**（其中 `WEAK-c` 无指引词 69 条 / 77 行，`WEAK-b` 指引词扩展 4 条 / 20 行，`WEAK-a` 命令正则误杀 19 条 / 19 行）。我逐条看完 92 条：**真 6 / 部分 17 / 假 69**——**真率 6.5%**。

**「指向另一份 `.md`」根本不是机器出口。** 我按 §3 的强度分级查了一遍：226 条「有出口」里，**102 条（45%）的出口只是一个 `.md` 文件名，没有任何进程会因它失败**。

```
final-report.md:216  | 1 | 报告的每一行结论都有 artifact_ref | … |   ← 出口是 handoff-schema.md
```
`check-deliverables.mjs` 检查的是「报告缺不缺节」，不检查「每一行有没有 artifact_ref」。**这句话在机器上是没人读的。**

## 3. 出口强度：226 个「有出口」里，一半是纸的

这是本报告最重要的发现，也是我建议改指标的理由。

| 强度 | 定义 | 条数（1113 行口径） | 占 226 |
|---|---|---|---|
| **STRONG** | 点名 `tools/*.mjs` 脚本，或点名一个真实实现的 `rule:` 名 | 124 | 55% |
| **WEAK** | 只点名 framework 内另一份 `.md` | 102 | 45% |

弱出口的真实定义是：**「这条规则由另一份文档约束」**——而那份文档也是提示词，也没有执行者。**把它算成「有出口」是把递归当成了终止。**

按唯一句算更刺眼：867 唯一文本里，**只有 83 条（9.6%）能指出一个会失败的工具**。工具报的 20.3% 出口率，真实值在 **9.6%**。而这个工具自己的文件头就记录过同样的教训：

> 宽松判据给出 512 个"出口"，严格判据（只认 rule: 名）是 104 个。宽松版把出口率从约 2% 抬到 8.9%，**那个差值是假的**。

**`artifact:` 这个通道（2026-11-19 加的）正在重演同一个错误**，只是幅度小一点。

## 4. Q2：剩下的真·无出口能不能自动分三类

### 4.1 我试了四版分类器，最高准确率 43%

| 版本 | 判据 | C1 准确率 | C2 准确率 | 总体 |
|---|---|---|---|---|
| v1 | 关键词计数（必填/枚举/至少…） | ~30% | ~25% | 差 |
| v2 | 加置信度分层 | 52% | 28% | 41% |
| v3 | 加「作用对象」轴（产物/调度/子Agent/泛化） | 52% | 28% | 41% |
| v4 | 谓词族（eq/setop/exists/bound/closed/fmt/mustwrite） | 52% | 28% | 41% |
| v5 | 补 `必须为/非空/一一对应/不得包含…以外` | — | — | 未超过 v4 |

**每一版的抽样都是 25 条/类、按文件分散、人工逐条判。** v4 的详细结果：

- **C1（该接校验器）样本 25 条：真 13 / 部分 2 / 假 10 → 52%**
  假的主要形态：`**唯一硬规则**：只要这一轮启动过，就必须留下报告。`（"必须"是强调，不是谓词）、`NeurIPS 的结论让修复与验收必须分开`（引用别人论文的结论，不是本框架规则）。
- **C2（该标 DISCRETIONARY）样本 25 条：真 7 / 部分 4 / 假 14 → 28%**
  假的主要形态：`| 8 | 附上「被审仓库零改动」的自检输出 | 有改动即严重违规，必须报告 |`——这是**可机械判定**的（比 `git status` 前后差），被分进了 C2。
- **C3（该删）只有 1–2 条**：真正的「已过时叙述」极少，因为作者在写的时候就把修订记录做成了 `> 2026-11-03 修正：…` 的引用块，本身是**有价值的变更说明**，不该删。

### 4.2 为什么低：一句话

**「该不该有出口」这个判断需要知道「这句话描述的东西长什么样」。** 正则看到的是「必须+字段名」，但：

- `registered_at 必须早于 files_touched 的 mtime` ——有字段、有比较，但**没有校验器能做时序比对**（需要 mtime，而 mtime 不是 payload 的一部分）；
- `主 Agent 不得自行提高并发上限` ——有字段 `concurrency`，但这是**角色禁令**，没有产物可以检查；
- `审计 Agent 必须执行至少一次真实运行验证` ——完全可机械判定，但判定对象是**审计 Agent 的行为**，不是产物，框架里没有「行为校验器」这一层。

**低于 70% 就是不可用。** 按我的实测，43% 的自动分类会把 455 条里的 260 条分错——**比不分还糟**，因为分错会让人相信一个错的清单。

### 4.3 但有一个子集可以自动分，而且这正是 Q3 的答案

把 455 条按「作用对象」切开：

| 作用对象 | 条数 | 其中带可机械谓词 | 值得接校验器 |
|---|---|---|---|
| 子 Agent 产物形态 | 30 | 10 | **10（这是全部）** |
| 产物形态（未限定角色） | 56 | 14 | ~10 |
| 子 Agent 行为纪律 | 79 | 15 | 0（无「行为校验器」层） |
| 主 Agent 调度 | 75 | 13 | ~5（多数需读 harness 状态） |
| 文档/叙述 | 220 | 38 | 0 |

**交集「子 Agent 产物形态 + 可机械谓词」= 10 条，占 455 的 2.2%。** 逐条列出（全部可执行）：

```
protocol.md:861          主 Agent 必须在仓库外建本轮目录，否则 artifact_path 无法落地
PORTABILITY.md:98        改写 tools 字段，否则子 Agent 拿不到写权限
output-contract.md:123   contract_valid 必须与 payload 真实合规性一致
wave3-critique.md:419    Arbiter 的 payload 必须含 arbiter_artifact_ref
wave3-critique.md:430    conflicts[].resolution 只能由 Arbiter 填
wave5-verify.md:90       验收 Agent 无写权限，临时文件必须写临时目录并在 payload 说明
evidence-policy.md:49    findings 条目的 evidence 与 inference 必须分字段
handoff-schema.md:205    resolution=UPHELD/DOWNGRADED/REVOKED 时 arbiter_artifact_ref 必填
handoff-schema.md:257    scale_decision 是只读快照，下一波不得修改
wave5-verify.md:279      修复成功率只能依据 closed_waves[wave-5].summary 统计
```

**这 10 条里，只有 3 条能追到已有的校验器**（`artifact_path` 在 `check-payload`、`arbiter_artifact_ref` 在 `check-fix-instances` 的 `REF_COLS`、`evidence/inference` 在 `check-payload` 的形状检查），而且三条都只覆盖了半句。我用 `grep -l` 直接查过：`scale_decision`、`closed_waves`、`resolution` **在 `tools/*.mjs` 里零出现**——所以这 7 条是**规则写了、没有任何代码读过**。

这是整份报告里唯一一处「值得接校验器」的确定名单。

## 5. Q3：建议

### 5.1 明确的选择

**不碰存量。三步，按这个顺序做，总成本 1 个 Agent × 1 天。**

**第 1 步（30 分钟，唯一改代码的一步）：修 `check-rule-ledger.mjs` 的三处。**

1. **命令正则**（`第 206 行`）：`/grep|xargs|find|cat |del |rm /i` → `/(^|[\s`|(])(grep|xargs|find|cat|del|rm)\s+[-./'"`A-Za-z]/i`。**+6 条真出口，零风险。**

**第 2 步（1 小时，只改输出）：把分母去重 + 剔噪声。**

做完之后分母是 **~670 行 / ~535 唯一句**，出口率 **9.6%**，这个数字**可管理**。

**第 3 步（半天，改 `--gate-new` 的判据，这是核心建议）：**

`--gate-new` 现在的逻辑是「本轮新增的规则句无出口 → FAIL」。改成：

```
新增规则句 → 分类：
  A. 描述子 Agent 产物形态（含 payload/字段/信封/verdict/findings/artifact_path，
     且有可机械谓词：必须等于/必填/非空/闭集/只能取/至少/一一对应/格式必须）
     → 无出口则 FAIL，错误信息要求作者二选一：接校验器 or 标 DISCRETIONARY + ≥10 字理由
  B. 其余（角色禁令、调度纪律、设计判断、叙述）
     → 只 WARN，不阻塞
```

为什么这样切是对的：**存量里 98% 的规则本质上不需要机器出口，而新规则里真正会伤人的那一类（子 Agent 写错产物）是可以从措辞识别的**——这也正是这个工具文件头记录的历史事故（`mutation_scope` 范例自己违反规则、`residual_risks` 只出现在生成器字面量里）。

**为什么不是其它三个选项：**

| 选项 | 否决理由（基于实测） |
|---|---|
| 按文件切 N 个并行分诊单元 | 455 条真·无出口里，只有 10 条（2.2%）值得接校验器。**要让 10 个 Agent 读 455 条，命中率 2.2%——每个 Agent 平均找到 1 条有用的。** 按 CLAUDE.md 的 token 单价算，这是本仓库最贵的一种做法。 |
| 只处理 top-N 文件 | Top 5 文件（protocol / wave2-audit / wave3-critique / wave5-verify / wave4-fix）占 209 条真·无出口（46%）。但这 5 个里，`protocol.md` 的 65 条有 40 条是「主 Agent 不得读源码」的重复表述，`wave2-audit.md` 的 48 条里 30 条是维度定义。**按文件切等于按「这个文件话多」切，不按「这里有缺陷」切。** |
| 放弃这个指标 | 不建议。它的**趋势**是有效的——2026-11-17 那次红队复盘（7 条修复全绿但 2 条严重）确实需要这个仪表。要放弃的是它的**绝对值**。 |

## 7. 附录：如果真要接校验器，接哪几条

按「规则描述的东西 → 谁能检查」分组，只列 §4.3 那 10 条 + 表 3 中明确可执行的：

| 规则 | 现校验器 | 缺口 | 谁来做 |
