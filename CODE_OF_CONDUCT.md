# Code of Conduct

## The short version

Be straightforward and be kind. Discuss the work, not the person who did it.

## Scope

This applies to issues, pull requests, commit messages, code comments, and any other
channel where you are representing this project.

## What is expected

- **Criticise artifacts, not authors.** "This rule never fires because the regex cannot
  match X" is good. "Whoever wrote this didn't think" is not — and in this repo it is
  also usually wrong: the history is full of rules that were carefully written and
  still did not fire, because writing a rule and enforcing a rule are different jobs.
- **Bring evidence.** This project's culture is numbers over assertions. If you say a
  gate is broken, show the input and the output.
- **Assume good faith on first contact.** Especially with translated content: the
  primary language of the framework documents is Chinese, and nuance does not survive
  machine translation well.
- **Respect the scope boundary.** Reports about the security of a *target repository*
  that someone audited with this framework belong to that project, not here.

## What is not acceptable

Harassment, personal attacks, discriminatory language, deliberate intimidation,
publishing someone's private information, and sustained disruption of discussion.

Also: **do not paste other people's credentials or private data** into issues, PRs, or
advisories — even to demonstrate a leak. A prefix and a commit hash are enough.

## Enforcement

Report concerns to the maintainer via the address on the GitHub profile, or open a
private advisory if the report itself is sensitive. Reports will be read, and the
response will state what was done — no silent handling.

Consequences scale with severity and repetition: a request to rephrase, then removal of
the comment, then a temporary block, then a permanent ban. Anyone handling a report
about themselves will be recused.

## Attribution

This is a short project-specific policy rather than an adopted template
(Contributor Covenant and similar). If the project grows beyond a single maintainer,
adopting a standard template with formal governance would be the right next step —
this document does not pretend to be that.
