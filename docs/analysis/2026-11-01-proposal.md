## 0. 一句话主张

**这个框架要补的不是"更严的门控"，而是"任务完成机制"。**

现状是一台**审计质量机器**：它能把 124 条发现收敛成 60 条经得起攻击的发现。但它不是一台**任务完成机器**：round31 跑完 40 个审计 agent、4 个锐评 agent 之后，停在 83 条待修复只做了 1 条、**没有最终报告**的状态。

你的目标是"不计 token 的长任务，一次跑到底，用户不用擦屁股"。按这个目标，**当前框架的优化方向是错的**——它把力气花在了"如何让每一条发现更可信"，而真正的瓶颈是"如何让整轮跑完并交付"。

## 1. 三条要修的主线（按性价比排序）

### 主线一：把预算花在活代码上（对应 D0，性价比最高）

**问题**：launcher 的 478 个首方文件里 273 个是 `fakefx`（JavaFX 移植），实际派发的 40 片里 29 片是它。而 Skeptic 事后算出其中 162 个文件"从任何生产入口都到不了"。

**改法**：给侦察波加一个**入口可达性闭包**步骤。

```
1. 侦察 Agent 先识别入口点（main / Activity / 注册表 / 路由表 / 导出符号）
2. 从入口点按 import / 引用关系做传递闭包
3. 每个切片标注 reachability: PROD | TEST_ONLY | UNREACHABLE
4. 派发顺序：PROD 优先 → TEST_ONLY → UNREACHABLE 最后（不是排除，是不优先）
```

**为什么这是机械规则而不是裁量**：`import` 闭包是确定性计算，不依赖"这个目录看起来重不重要"的判断。它既解决了 D0（钱花在死代码上），也**不违反** `scale-mapping.md:156` 的"禁止按内容特征排序"——因为可达性是**结构特征**，不是内容特征。

**预期收益**：在 launcher 这个案例上，能把约 72% 的预算从死代码里抢回来，等于**覆盖率翻倍而不增加一个 agent**。

> **证据强度**：这条完全基于 launcher 的实测数据（文件分布、切片分布、Skeptic 自己的可达性统计）。不依赖任何外部文献。

---

### 主线二：让「切片 × 维度」的算术成立（对应 D1，最严重的结构缺陷）

**问题**：文档要求每个 `(切片, 维度)` 派一个实例，共 6 个维度；但预算公式是 `planned = effective_slices`，**没有乘 6**。round31 实际按"1 片 1 维"跑，等于悄悄放弃了 5/6 的维度覆盖。

**三个可选改法，我推荐 B**：

| | 改法 | 优点 | 缺点 |
|---|---|---|---|
| A | 明写「每片只审 1 个主维度」，按切片特征分配维度 | 算术简单 | 每片仍有 5 维没审，覆盖率换个名字的谎 |
| **B** | **两遍制：第一遍"宽扫"，第二遍"深挖"**（推荐） | 算术自洽，且覆盖是真的 | 需要定义"宽扫"的产出格式 |
| C | 保持 6 维×全切片，把预算提到 510 | 覆盖最全 | 预算爆炸，且大部分维度在该切片上无意义 |

**推荐 B 的具体形状**：

```
第一遍 · 宽扫（每个切片 1 个 agent，产出「线索」而非「发现」）
  - 该 agent 看全部 6 个维度，但只输出线索（file:line + 一句话 + 疑似维度）
  - 线索不进锐评波，成本低，允许高噪声
  - 1 片 = 1 agent，算术成立

第二遍 · 深挖（只对线索密集的切片派，每片按维度拆）
  - 触发条件：某切片线索数 ≥ 阈值，或含 HIGH 疑似
  - 深挖 agent 才执行完整的门 0 证据链 + 单维度隔离
  - 预算按线索数分配，不按切片数分配

锐评波只处理第二遍的产出，第一遍的线索不消耗锐评预算
```

**为什么这样对**：现在的设计把"单维度隔离"（防认知过载，有依据）和"全片全维度覆盖"（成本主张）捆在一起，导致**要么贵 6 倍，要么假覆盖**。两遍制把这两件事分开：宽扫负责**不漏**，深挖负责**可信**。

**需要你拍板的点**：宽扫的"线索"是否算发现？我的建议是**不算**——它只用于决定第二遍派给谁，不出现在最终报告里。这样最终报告的信噪比不会下降。

### 主线三：跑到底 + 断了能续（对应 D5，直接对应你说的"擦屁股"）

**问题**：round31 停在 `IN_PROGRESS`，没有最终报告。而中断是常态：DEV-PLAN 记录了网关 502 连续掐断 agent、Round 22 因误判"静默中断"导致双实例并发写覆盖。

**改法：把账本从"对话里的状态"改成"磁盘上的状态机"**。

核心是一个 `state.json`，每一波结束、每一个 agent 终态，都立即落盘：

```json
{
  "round": 31,
  "phase": "wave2",
  "done": ["slice-01", "slice-02", ...],
  "running": [{"slice_id": "slice-23", "agent_id": "...", "started_at": "..."}],
  "pending": ["slice-40", ...],
  "artifacts": {"slice-01": "docs/reports/round31/round31-02-audit-slice-01-logic.md"},
  "budget_spent": 47,
  "last_heartbeat": "2026-11-01T21:40:00Z"
}
```

配套三条硬规则：

1. **每次派发前先写 `running`，拿到结果先写 `done`，再派下一个。** 中断最多丢一个 agent 的结果。
2. **续跑入口是独立提示词**：`继续 round31`，新对话读 `state.json`，只补 `pending` 和超时的 `running`，不重跑 `done`。
3. **中断判据用 agent 运行状态，不用文件 mtime**（Round 22 的直接教训：红队 agent 100 分钟没写文件但其实在正常读码，被误判中断后双实例覆盖同一文件）。

另外加一条**收尾保险**：不论因为什么原因停止，主 Agent 必须先生成一份**不完整但可用的最终报告**（覆盖了多少、有哪些未闭合、下一步跑什么），再退出。**"没有最终报告"这个状态不允许存在。**

## 2. 两处原则性取舍（需要你拍板）

### 取舍一：是否废除「主 Agent 零裁量」

**现状**：`protocol.md:26` 禁止主 Agent 读任何文件；`scale-mapping.md:156` 禁止按任何内容特征排序。

**round31 的证据**：两处违规，性质不同——
- 并发超限（峰值 7 / 上限 4）：用户指出后才核验，**纯失守**；
- 维度偏离 9/40：主 Agent **为了让 `ExpressionHelper` 等关键文件进入审计**才按内容调整，被 Devil's Advocate 机械比对抓出，**是为质量而违规**。

**我的建议**：**不废除，改成"裁量必须留痕 + 可被机械复核"**。

```
原：「主Agent不得……」
改：「主Agent可以做以下 N 类裁量，但每次必须在 discipline_log 中记录：
     做了什么、为什么、依据是什么（file:line）。
     未登记的裁量一经发现，该轮结论作废。」
```

理由：round31 已经证明**禁令没有消除裁量，只是把它逼成了不申报**。而「留痕 + 可复核」既保留了可审计性，又不再逼 Agent 在"守规矩"和"审出真问题"之间二选一。

> 这条对应你选的"允许推翻个别原则，须附证据"。

### 取舍二：是否把「修复波」移出默认路径

**现状**：五波次默认连跑，修复波在验收波之后才算完。

**证据**：
- round31：83 条待修复 vs 1 条实际修复，**修复波是整个流程卡住的唯一原因**；
- 修复是唯一有写权限、有副作用的角色，规则最严（rollback、affected_issues、变异验证），每一步都容易停；
- 你的目标是"找出 bug"，不是"修完 bug"。

**我的建议**：**默认只跑到「审计报告」，修复作为独立的、显式的第二步**。

```
默认路径（一次跑完）：侦察 → 宽扫 → 深挖 → 锐评 → 出报告     ← 只读，无副作用，必然能跑完
可选路径（另行启动）：修复 → 验收                            ← 有副作用，可分批、可中断
```

这样"一次对话跑不完"的问题从根上消失：**只读路径没有理由跑不完**。而修复可以按你的节奏分批做。

> 这条是我的建议，但影响较大，需要你确认。如果你希望修复仍在默认路径，我就改成"修复波有独立预算上限，超出的进下一轮"。

## 3. 三种交付形态对比（你说要看的）

| | **A · 纯提示词 Markdown** | **B · A + 可选调度器** | **C · A + Claude Code 原生分发** |
|---|---|---|---|
| **形态** | 21 份 md，手动拼 | md 为主 + 一个薄脚本（100-200 行） | md + `.claude/agents/` + skill |
| **加载** | 靠模型自律（round31 证明会失效） | 脚本强制拼接 | harness 原生加载 |
| **门控** | 靠模型自查（round31 证明会失效） | 脚本机械校验 `state.json` / 契约 | harness 工具白名单 + 脚本 |
| **断点续跑** | 需要人工读 md 接上 | 脚本读 `state.json` 自动续 | 同 B |
| **只读约束** | 提示词声明 | 提示词 + 脚本不给写工具 | **工具层强制拒绝**（最可靠） |
| **可移植性** | 任何 harness | 需 Python/Node | **仅限 Claude Code** |
| **代码量** | 0 | ~200 行 | ~200 行 + agents 定义 |
| **最大风险** | 自律失效（已实测） | 脚本本身要维护 | 锁定单一 harness |

**我的推荐：A + B**。

理由：
1. 你要的 **A 必做**，且 A 是 B 和 C 的内容基础——三者共享同一批提示词，不冲突；
2. B 只加一个脚本，解决的是 A 完全解决不了的两件事：**机械门控**（D2/D3）和**断点续跑**（D5）。这两个恰好是你最痛的点；
3. C 的工具层只读约束最可靠，但会锁死 Claude Code。如果只跑 Claude Code，C 比 B 值；如果要"任何 harness"，就别绑。

**建议的推进顺序**：先把 A 改对（主线一/二/三的提示词部分），再决定要不要 B。**A 改完就已经能显著改善**，B 是"想彻底根治"时的增量。

## 4. 外部调研与引用核实的吸收（含两条警示）

### 4.1 引用核实：结论与我的初始怀疑相反，必须纠正

我派了 agent 逐条核实框架的 25 个外部引用。**结果推翻了我自己的一个判断**：

- **我错了**：我曾说 `neurips.cc/.../loc/atlanta/171452` 是"会议地点页而非论文"。实际上它是 **Atlanta 分会场命名空间下的 poster 详情页**（规范地址 `/virtual/2026/poster/171452`），返回 200，且**逐字支持**框架的论断。这条是全框架证据链**最硬的一环**，已改用规范 URL 并补全了它真正的价值（见 §4.3）。
- **真正的问题**：25 个 URL **无一 404**。问题不是编造，是**「链接真实、用错地方」**——用一个「某包存在」的页面撑起一个「某结论已被证明」的论断。

三类误用已修：

| 类型 | 实例 | 已执行的处置 |
|---|---|---|
| **把 API 掉线率当审计失败率**（最严重） | `scale-mapping.md` 用 HiveMind 的 72–100% 论证"并发窗口=8"。实际：mock 服务器上的 **HTTP 502/连接重置**率，非审计质量；论文从未建议窗口 8；且**仅加准入控制仍有 81.8% 失败**，"准入+背压即降到 0–18%"是反向误读 | 窗口 8 降级为「设计假设」；补三个限定；纠正为「**背压必须与重试配对**」 |
| **引用了全文不含该内容的 PDF** | `wave1-recon.md` 称「LobeHub 用 5–10 files per chunk」，挂的 Zenodo PDF 全文 grep `LobeHub` **0 次** | 已删除该引用并留注 |
| **一个锚点撑 5 个论断** | `protocol.md` 的 `ref0/ref2/ref3/ref10/ref11` 全指向同一 Oracle 博客锚点，且该 URL **403 无法访问** | 5 处全部降级为 D 级，改为「从原理推导，不假装有出处」 |

**由此给框架立了一条新规矩**（已写进 `evidence-policy.md` 第 8 节）：引用分 A/B/C/D 四级，三条硬规则——① 引 A 级必须写出限定条件与口径；② 一个脚注只能撑一个论断；③ 数字必须带单位与口径。

**一个附带发现**：所有文件的 `source:` 都指向 `chat.deepseek.com/share/...`，该链接返回 **429**。这意味着**多数论断的真实上游是一段 LLM 对话记录，而非论文**。框架的自我定位应当据此调整为「一套设计约定的集合」，而不是「实证研究的汇总」。

### 4.2 外部调研：能站住的结论

- **Anthropic 官方**：多 agent 系统消耗的 token 是单 agent 的**数倍**（有说法 agent ~4×、多 agent ~15×），且明确提醒**多数编程任务的可并行子任务比研究少**，建议"先找最简方案，只在可证明改善结果时增加复杂度"。**支持主线二的两遍制**——不要一上来就 6 维扇出。
- **多 agent debate 相对 self-consistency 没有可靠优势**（Smit et al., ICML 2024, **arXiv 2311.17371**，已核实存在），且对超参高度敏感。**支持给锐评波瘦身**，也支持"只在真实冲突时才扇出"。
- **无外部反馈的自我批判基本无效**（Huang et al., **arXiv 2310.01798**）——**支持"锐评必须绑证据，不能只让模型自查"**，与框架现有设计一致。
- **工程界通用做法**：子 agent 把产物写到文件系统、只回传轻量引用，避免"传话游戏"。**支持主线三的 `state.json` 方案**。

### 4.3 最有价值的单条证据（原来被浪费了）

NeurIPS 2026《Silent Regressions: The Verification Gap in Coding Agents》(Aman Mehta) 的对照数字：

| 验证方式 | silent regression 率 |
|---|---|
| FAIL TO PASS **外部**测试（瞄准故障） | **4.8%** |
| 让修复 Agent 自己随机写测试 | 10.0% |
| 不验证 / 自证 | 18.8% |

原文还逐字说：「Prompting GPT-5 to write and run a failing test **moves neither resolve nor regression rate**」。

这条同时支撑三件事，我已全部写进框架：① 波次四/五必须分离；② 验收必须**独立构造**触发条件；③ **变异检验不能省**（"有测试"与"测试瞄准缺陷"差一倍以上）。配合 launcher 的实战结论「**测试打不红的修复等于没修**」，变异检验已从**可选升级为强制**，并要求覆盖**调用点**一层（R28 的 493 条假绿就是只测纯函数的结果）。

### 4.4 我剔除的调研材料

我派出的调研 agent 引了十几个 **2026 年的 arXiv 编号**（2602.17875、2605.01885 等），在当前网络策略下我**无法逐个打开核对**，其中"约 50% 的 code review 评论含幻觉"这句我用检索**没能找到对应论文**。**这些数字一个都没有写进框架。** 这恰好是 §4.1 那条新规矩的反面示范。
