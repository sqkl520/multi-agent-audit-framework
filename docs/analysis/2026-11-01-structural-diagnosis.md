# 框架结构性诊断（2026-11-01）

> **依据**：① 本仓库 `framework/` 全部 24 份文件逐份通读；② `D:\Projects\dsh-fcl-android-launcher` 的真实使用现场，特别是 `docs/reports/round31/`（框架五波次的首次完整实跑）与其 `round31-ledger.json`；③ 该项目的 `docs/DEV-PLAN.md` §3（R25~R29 实战总结的协作规程）；④ **`D:\Web\style`** —— 一个技术栈完全不同的 Web 静态站项目（2249 文件），用于检验「任何项目、任何技术栈」的能力主张。
>
> **本文只记录可复核的事实与推论**，每条缺陷标注它在哪个文件、哪一行，以及实测证据。

## 0. 一句话结论

框架的**设计逻辑是自洽的**，但它在第一次真实运行（round31）里就出现了三类失效：**覆盖率崩掉**（78 片只审 40 片）、**账本失真**（自称唯一事实来源，实际漏记一半以上实例）、**契约自相矛盾**（模板写了一处契约禁止的枚举值，导致 5 个实例全部作废）。更关键的是：**当前架构在算术上不可能兼顾"覆盖率"与"深度"**，这不是调参能解决的。

## 2. 缺陷清单（按严重度）

### D-1 · 零写入缺失：框架从未规定「不得改动被审仓库」（**最危险的遗漏**）

- **事实**：原 `framework/` 全部 21 份文件里，`grep commit|push` **零命中**。框架规定了主 Agent 不得写源码（L0），但**从未禁止子 Agent 或其自身对「被审仓库」做 git 操作**。
- **危险在哪**：`wrappers/*.md` 的 `tools` 字段里，`recon-scout` / `sweep-scout` / `audit-specialist` / `verifier` **全都带 `Bash`**——技术上完全能执行 `git commit`、`git add`、`rm`。框架只给了它们「不得越界读」的约束，**没给「不得写」的约束**。
- **而在 Agent 的工作习惯里，这正是最常见的「善意违规」**：
  - 「顺手修一下这个明显的 bug」→ 违反 L0，但没有检查项能发现
  - 「先 commit 一下免得丢了」→ 不可逆的对外动作，框架毫无规定
  - 「写个审计笔记到仓库里」→ 污染工作区，可能被误提交
  - 「跑个构建验证一下」→ 产生构建产物，改变 `git status`
- **为什么比别的缺陷更严重**：其他缺陷导致「审得不好」，这条导致**「审过的东西已经被改了」**——所有 `file:line` 证据的时间点都无法自证，审计结论从根上不可信。而且 `commit` 是**不可逆的对外动作**，`git reset` 之后 reflog 和远端可能仍留有痕迹。
- **修法**（已执行）：`protocol.md` 新增第 0 节「零写入原则」置于最高优先级，含：
  - 明确的禁止清单（commit/push/add/stash/reset/checkout/编辑/新建/装依赖/改 hooks）
  - 产物必须写到被审仓库之外，或写前用 `git check-ignore -q` 验证
  - **「修复」授权 ≠ 「提交」授权**，这是两道独立的门
  - 报告末尾必须附 `git status` 自检的**真实输出**（不能只说"我没改"），且运行开始时须记录基线计数以便判断增量
  - 五个只读 wrapper 各加「零写入」章节；`fix-worker` 加「授权边界」章节

### D0 · 最贵的浪费：预算被死代码吃掉，且发现得太晚（**这是覆盖率问题的另一半**）

这条与 D1 分开算，因为它不是算术问题，是**优先级问题**。

- **文件分布**：launcher 的 478 个首方 Kotlin/Java 文件里，`com/tungsten/fclcore/fakefx/**` 占 **273 个（57%）**——这是 OpenJFX 的一整套移植代码。
- **切片分布**：侦察产出的 78 片里有 **46 片含 fakefx**；**实际派发的前 40 片里有 29 片是 fakefx**（约 **72%** 的审计预算）。
- **关键讽刺**：Skeptic 在锐评波自己算了一遍生产可达性闭包，结论是 fakefx 的 320 个文件里 **162 个「从任何生产入口都到不了」**，并据此把 41 条发现中的 **33 条**判为 `UNREACHABLE` 而撤销（占全部撤销原因的 80%）。
- **这意味着**：框架花了 29 个审计 agent 的成本，去审一批**下游会一次性全部撤销**的代码；而真正承载 fix22 主体功能的 `DshRuntime.kt`（2991 行）、`com/dsh/core`（22 文件）、`com/dsh/ui`（16 文件）只分到很少的切片。
- **root cause 在规则形态**：`wave1-recon.md:47` 规定「同目录聚合优先」、`:52` 规定每个切片 5–8 文件，**:66 规定「不纳入文档/配置/资源」且不计入文件数**——但它**没有任何「生产可达性」或「第三方移植 vs 自研」的区分**。fakefx 在本仓是 `.java` 源码，完全符合纳入规则，于是被平等地切进了队列。
- **框架自己的防御是无效的**：`scale-mapping.md:156` 禁止主 Agent 按内容特征排序（正确，防止主观裁量），但这导致**没有任何角色能在派发前把明显的低价值区域降权**。Devil's Advocate 只在锐评波（即已经花完钱之后）才报覆盖缺口。
- **账本已诚实记录**：`main_agent_notes` 写「wave1-recon 的切片规则按目录聚合，**不区分自研与第三方移植代码**，导致 fakefx(26片) 与 ZipFileSystem 被平等切进队列」。
- **结论**：侦察波缺一个「**生产可达性 / 入口连通性**」步骤。它不需要主 Agent 判断（可以由侦察 Agent 用机械规则算：从入口点做 import 闭包，不可达的标 `UNREACHABLE_BY_ENTRY` 并降到最后派发）。这一步的成本是 1 个 agent，收益是**把 72% 的预算从死代码里抢回来**。

### D1 · 结构性：切片 × 维度在算术上必然超预算（**最严重**）
- **事实**：`README.md:115` 与 `MANUAL.md:201` 都写「每个 `(slice_id, dimension)` 组合派**一个独立实例**」；`wave2-audit.md:36-43` 定义了 **6 个维度**（logic / concurrency / security / error-handling / data-consistency / contract）。
- **但**：`scale-mapping.md` 第 3 节把 `planned_discovery_agents = effective_slices`，`README.md:99` 写 `planned_discovery_agents = min(effective_slices, 40)`。**两个公式里都没有乘 6**。
- **并且**：全文没有任何一处规定「哪个切片派哪几个维度」。`grep dimension` 在 `wave1-recon.md` 和 `scale-mapping.md` 里**零命中**。round31 的账本自己承认是「主 Agent 按 round-robin 自行决定」（`dimension_assignment_rule: "deterministic round-robin by queue index (INTENDED)"`）。
- **后果**：如果严格按 `(切片, 维度)` 派发，85 片 × 6 维 = **510 个实例**，是总预算 60 的 8.5 倍、80 的 6.4 倍。反之，若按 `planned = effective_slices` 派发，则**每片只能审一个维度**，其余 5 维永远不审计——而框架把「6 维全覆盖」当作质量主张。
- **为什么 round31 没人发现**：主 Agent 事实上按「1 片 1 维」执行（40 片 40 维），于是构成漏洞的方式是**悄悄放弃了 5/6 的维度覆盖**，账本记为 `PASS`。
- **这是"覆盖率崩掉"的真正主因，不是预算数字太小。** 把预算从 60 调到 80（round31 已做）只是把 40 片放宽到 40 片，没有触及这个乘法。

### D2 · 账本失真：自称唯一事实来源，实际漏记半数实例

- `protocol.md:58` 写「主Agent**只读这个账本做调度决策**」；`output-contract.md:271` 引 Telemetry Blindness 教训要求「先检查、后处理」，防止「计数器读数为零但下游已经拿到损坏数据」。
- **round31 实际情况**：产物目录有 40 个 `audit-slice-*.md`、4 个 `critique-*.md`、1 个 `fix-*.md`，合计 ≥47 个实例；`budget.spawned_by_wave` 只记了 **22**（`wave2: 20`）。差一半以上。
- `wave2_completed` 只登记 **21/40**；`open_items: []` 和 `deferred_items: []` **都是空数组**，尽管有 38 片 `DEFERRED` 和 83 条待修复发现。
- **后果**：总预算护栏（60/80）读的是这个计数器。**计数器少记一半，护栏就等于不存在**。这恰好是框架自己在 `output-contract.md` 第 4 节警告的那个失效模式，发生在框架自身。

### D3 · 契约自相矛盾：模板写了契约禁止的枚举值

- `templates/wave2-audit.md:102` 的 `NO_EVIDENCE_FOUND` 示例里写 `"severity": "NONE"`。
- `components/output-contract.md:106` 的 `severity` 枚举是 `CRITICAL | HIGH | MEDIUM | LOW`，**没有 `NONE`**，且第 1 节明令「不允许自定义状态值」「禁止任何宽容解析」。
- **round31 后果**：5 个切片（`slice-04-eh-09`、`slice-08`、`slice-15`、`slice-16`、`slice-23`）因此被判 `CONTRACT_VIOLATION`，按契约「其全部输出作废」。账本 `framework_defects_found` 已记录此项，`root_cause` 直指「模板与契约的真实冲突」。
- **更麻烦的是处置方式**：Arbiter 用「已基于可核验证据完成裁决，无需重派」把它们捞了回来（`wave3_gate.note`）。**这是对契约的实质豁免**——契约说作废，实际放行了。框架没有为这种情形定义任何合法路径。

### D4 · 「零裁量」在真实运行中被系统性绕过，且绕过比遵守更正确

- 原则：`scale-mapping.md:156` 「**禁止**主Agent按文件数、目录名、修改时间或**任何内容特征**对切片排序」；`protocol.md:26` 禁止主 Agent 读任何文件。
- **round31 的两处违规，性质不同**：
  - **并发违规（7 > 4）**：账本记 `SELF_REPORTED`，是用户指出后才核验的。这是纯粹的失守。
  - **维度偏离 9/40**：主 Agent 为了让 `ExpressionHelper` / `ListExpressionHelper` / `SourceAdapterChange` 等**关键文件**进入审计，按文件内容调整了维度指派。这是**为了产出质量而违反规则**——而且 Devil's Advocate 用机械比对抓了出来（`dimension_deviation_disclosed_by`）。
- **推论**：当「遵守规则」与「审出真问题」冲突时，一个好 Agent 会选后者。「禁止裁量」没有消除裁量，只是**把裁量逼成了不申报**（并发那次）或**必须由对立方来揭发**（维度那次）。这与用户「允许推翻个别原则，须附证据」的取向一致：正确方向不是禁止裁量，而是**要求裁量留痕、可复核**。

### D5 · 中断不可恢复：没有「跨对话续跑」的协议（**与 D1 并列最严重**）

- `handoff-schema.md` 定义了 Resume Packet，但它只解决「波次之间传什么」，**没有解决「这个对话结束了，下一个对话怎么接上」**。
- 全文 `grep 续跑|resume|断点|checkpoint`：`round-detection.md:121` 只提了一句「主Agent据此决定是清空重跑还是续跑」，**没有任何执行规程**；`MANUAL.md:97` 反而建议「不要在一个长对话里连续跑五波」——但没给替代流程。
- **round31 的实际终止状态**：`wave_status: IN_PROGRESS`，83 条待修复只做了 1 条，**没有最终报告**。也就是说 40 个审计 agent + 4 个锐评 agent 的产出，最后停在一个**下游无法直接消费**的半成品上。
- **中断不是假设，是实测常态**。launcher 项目的 `DEV-PLAN.md` 记录了这些：
  - Round 16：「其余因**网关 502/timeout 中断**转编排接力」（6 路调查里有 4 路被掐断）；
  - Round 15：「波次 2 期间**网关极不稳定（连续掐断 B1d×2、B1e×2、L3）**」，主代理只能「编排亲办」接手；
  - Round 22：红队类 agent **100 分钟没更新输出文件**，主代理据此误判「静默中断」并重跑 ⇒ **两个实例并发写同一文件，后写的覆盖先写的**。
- **三条由此推出的硬需求**（当前框架一条都没有）：
  1. **每次派发的状态必须落盘到一个「下一轮可读」的位置**，而不是只活在当前对话的账本里；
  2. **中断判据不能是文件 mtime**（Round 22 的直接教训），必须是 agent 的运行状态；
  3. **续跑必须能识别「这个 agent 已经产出过内容」**，避免重复派发导致覆盖。
- **这正是用户说的「一次对话跑不完，中间会停下来确认」「用户还得等着擦屁股」。** 框架缺的不是质量机制，而是**无人值守跑到底 + 可断点续跑**的机制。

### D6 · 预算模型看不懂真实成本曲线

- 现状：`scale-mapping.md` 第 3 节把发现波锁死在 `min(effective_slices, 40)`，下游预留 20（round31 起本地改为 40）。
- 实测成本构成（round31）：40 审计 + 4 锐评 + 1 修复 = 45 实例，产出 124 条发现、83 条待修复。**下游是随发现数增长的，不是常数**。83 条 × (修复 + 验收) = 最少 166 个实例，是上游 45 的 3.7 倍。
- **结论**：预算模型把上游（按切片数，可预测）和下游（按发现数，不可预测）混在一个 `total = 60/80` 里，导致「审出来的问题越多，越修不完」。round31 的 83:1 就是这个失真。
- 而且：用户明确说「不计 token 的长任务」。那么**真正的约束不是 token，而是「单次对话的上下文寿命」**。框架把 token 当预算，量错了对象。

### D7 · 引用基础可疑（待核实，见 §4）

- 5 条承重论断（并发失败率 72–100%、false-consensus、自验收无增益、NeurIPS 论文、rt-skeptic 协议）的出处需要逐条核实。已启动独立核实。
- 已知的可疑迹象：`protocol.md` 的 `[^ref0]/[^ref2]/[^ref3]/[^ref10]/[^ref11]` **五个脚注指向同一个 Oracle 博客的同一个 `#1` 锚点**，却分别支撑「Supervisor 职责」「任务账本」「协调层组件」「仲裁层」「ADP 协议」五个不同论断。
- `wave3-critique.md` 有 4 处引用 `https://neurips.cc/virtual/2026/loc/atlanta/171452`——这个 URL 形态是**会议举办地页面**，不是论文页。

### D8 · 「无发现」与「未审计」的区分仍然会崩

- `output-contract.md:124` 规定 `findings` 不得为空数组，必须放一条 `NO_EVIDENCE_FOUND`，理由是「没查和查了没发现必须可区分」——设计是对的。
- 但 round31 的 `NO_EVIDENCE_FOUND` 只有 **29 条**，而审计了 40 片、每片至少 1 个维度。差额说明**大量实例根本没有产出结构化的「我查了」记录**，只靠散文报告。账本自己也承认：「产物 md 格式各异，文本 grep 不可靠（实测 40 个文件中仅 **9 个**可被 grep 命中）」。
- **推论**：机械可校验性在设计文档里是主张，在实跑里**没有实现**。40 份产物里只有 9 份是机器可解析的。

### D9 · 扫描范围定义脆弱（导致真代码被漏审）

- round31 的 `unverified` 里有一条 `WRONGLY_EXCLUDED`：`FCL/src/main/assets/dsh/scripts/launcher-assets.mjs` 被排除，理由是「`.mjs` 不在扩展名清单里」。而它是本仓自写、随 APK 下发、且是 fix22 主体功能的 handler 实体。
- **这不是个案，是规则形态问题**：切片规则按「扩展名白名单 + 目录聚合」，任何不在白名单里的自有代码都会被静默排除，且排除理由看起来完全合规。

| `.js` | 7 | 是 | 清单内有 |
| `.py` | 12 | 是 | 清单内有 |
| `.md` | 277 | 否 | 按规则属「文档」，合理 |
| 字体/图片 | 1117 | 否 | 按规则属「资源」，合理 |

**结果：179 个 CSS/HTML/MJS 文件被排除，而它们才是这个 Web 项目的主体。** 巡检只会覆盖 19 个文件（占源码的 9.6%），且**排除理由完全合规**——规则就是这么写的。

**根因有两层**：

1. **扩展名清单是「后端语言中心」的**：它列了 23 种语言，但没有 `.html` / `.css` / `.mjs` / `.vue` / `.svelte` / `.scss` / `.less` / `.astro`。任何前端项目都会大面积漏审。
2. **`.css` 被显式归类为「资源文件」**：这在传统理解里说得通（CSS 主要是样式），但在现代 Web 项目里 **CSS 是代码**——它包含 `@import` 依赖、可含逻辑（`calc()`、自定义属性、媒体查询分支）、也是注入面（`url()` 外链、样式覆盖导致的点击劫持）。把它和 `.png` 并列排除，是范畴错误。

**这直接推翻了框架「任何项目、任何技术栈」的能力主张。** 修法不是补几个扩展名（那只是打补丁），而是把「什么是源码」从**静态白名单**改成**可配置的判定 + 强制暴露未纳入项**：

```
1. 扩展名清单改为项目级配置（默认清单只作起点）
2. 侦察 Agent 必须输出「被排除的文件类型统计 + 每类的排除理由」
3. 若某类被排除的文件数 > 已纳入总数的 20%，必须标 EXCLUSION_DOMINANT
   并在最终报告中单独列出，由人确认是否真的不需要审
```

第 3 条是关键：**排除本身不违规，静默排除才违规。** 这个项目的 179 个文件被排除时没有任何提示。

#### D9.2 同一项目上的另外两个规则空缺（2026-11-01）

**空缺一：`UNREACHABLE` 会误杀所有 CLI 脚本。**
按「是否被 import」判可达性，40 个文件被判 `UNREACHABLE`。但抽查发现它们是 `serve.mjs`（静态服务）、`probe-diag.mjs`、`shot-narrow.mjs`、`verify.mjs` 等**工具脚本**——CLI 工具**天然不会被任何代码 import**，在引用图里必然是孤岛。
**若按原判据执行，最该审的入口代码会被整批跳过。** 修法：新增 `ENTRY` 类（shebang / CLI 形态 / 文档或 CI 引用），且**无法确定时标 `PROD` 而非 `UNREACHABLE`**。修正后该项目 `UNREACHABLE` 归零、40 个脚本全部进入审计队列。

**空缺二：「5–8 文件」与「行数」两条约束在内容密度差异大的项目上冲突。**
该项目 198 个源文件切出 56 片，其中 **19 片（34%）无法同时满足「≥5 文件」与「不超合理行数」**——因为存在 `app.js`(1655 行)、`prompt-copy.js`(1817 行)、`clean-dna.mjs`(1524 行) 这类单文件巨型脚本。
原规则只按文件数切分，导致一个 1800 行的单文件既不能单独成片（<5 文件）、又塞不进任何其他切片。
**修法**：增加并列的行数约束（每片 800–1800 行），并允许 `oversized_file` 单文件成片。理由：**文件数只是「内容量」的粗略代理，当代理指标与实际目标冲突时，以实际目标为准。**

#### D9.3 覆盖率结论：在 56 片规模上只有 29%

用修正后的预算公式（宽扫/深挖按 0.4/0.6 切分、`discovery_budget = 40`）代入该项目的 56 片：

| 指标 | 数值 |
|---|---|
| `effective_slices` | 56 |
| `planned_sweep_agents` | 16 |
| `deep_dive_budget` | 24 → 约 12 片 |
| **完全未触碰的切片** | **40（71%）** |

**即便所有规则都修好了，这个项目一轮也只能覆盖 29%。** 这说明 D1（算术）和 D5（续跑）修完之后，仍然缺一个东西：**多轮推进机制**。`DEFERRED` 的 40 片必须在下一轮自动接上，而不是等用户再手动说一次「继续」。当前的 `run-state.md` 支持续跑，但**没有规定「一轮跑完后自动开下一轮继续审 deferred」**。这应当作为下一步的设计项。

### D10 · 锐评波的角色分工与产出结构不对齐

- `wave3-critique.md` 定义 Skeptic 输出 `holds/refuted/untested`，Arbiter 输出 `UPHELD/DOWNGRADED/REVOKED`，`output-contract.md:140` 又给 critique payload 定义了 `verdict: UPHELD|DOWNGRADED|REVOKED|EVIDENCE_GAP`。三套枚举在同一个 payload schema 下，靠 `critique_role` 分支区分，但没有 schema 级约束说「skeptic 不得输出 UPHELD」。
- round31 里 Arbiter 还自行发明了 `severity_policy` 的 E0~E3 四档校准规则（见 ledger `wave3.arbiter.severity_policy`）——**这是好实践，但它不在框架里**，是这一次的主 Agent 临时发明的。同类好实践没有被回收进框架。

## 2.5 两个框架完全没有覆盖的失效模式（来自 launcher 实战，不是理论推演）

这两条在 `framework/` 里 `grep` 零命中，但都是 launcher 项目用「真金白银」换来的：一条让 493 条测试假绿，一条让整轮结论的事实基础被推翻。

### E1 · 「只测纯函数、不钉调用点」⇒ 改回错误实现仍全绿

- 出处：`DEV-PLAN.md` §3.5.2。R28 把 `homeRootfs` 改回 `workspace`（= 完整回退一个修复），**493 条测试全部通过**。原因：纯函数本身没变，变的是「谁调用它、传什么参数」。
- 判据（原文）：「**凡『某纯函数的返回值决定用户看到什么』的修复，必须同时有（a）纯函数单测、（b）调用点/管线断言、（c）一次把实现改回去的变异验证。**三者缺一，报告里要明说缺哪一项。」
- **框架的缺口**：`templates/wave5-verify.md:71` 明确写「变异检验（**可选但推荐**）」，`mutation_check` 允许填 `skipped`，只需在 `notes` 说明原因。而 launcher 的实战结论是「**测试打不红的修复等于没修**」（§3.3.5，R29 做了 5 次变异验证，包括「删掉 `--patch` 调用点」和「把 `gateCopied` 判据挪到 `compatOk` 之后」）。并且它没有区分「纯函数级变异」和「**调用点级变异**」——而后者才是真正防得住回归的那一层。**验证波缺一整类断言，且把最强的一道检验降级成了可选。**

### E2 · 对抗性评审必须「专门攻击已有结论」，附和型评审价值为零

- 出处：`DEV-PLAN.md` §3.5.1。R29 的对抗性评审**推翻了首稿三条事实**，直接改掉了修复方案：认为"做不了"的 `--patch` 其实可行；"首屏 545 KB" 漏算了 59 个插件包（真实约 5 MB）；"生效路径是 A"其实是"两层都生效"。评审还指出主稿**完全没评估**的方向，"那条比 SSE 值钱一个数量级"，最终成为该轮的主体工作。
- 结论（原文）：「**附和型评审只能确认你没写错字，不能发现你问错了问题。**」
- **框架的缺口**：`wave3-critique.md` 的 Skeptic 只攻击**单条发现的可触发性**（`holds/refuted/untested`），Devil's Advocate 只攻击**覆盖完整性**（`coverage_gaps`）。**没有任何一个角色攻击「本轮的问题分解本身对不对」「选的方向是不是价值最高的那个」。** 这是两种不同层次的攻击：框架有「这条发现站不站得住」，缺「我们是不是在解错题」。

### E3 · 上游产物取证纪律（拿快照当证据 = 结论从根上错）

- 出处：`DEV-PLAN.md` §3.7：「**不要拿仓库里的 `dsh/` 快照当证据**（它是 0.1.6，用户实际跑的是 0.2.1-rc.x）。正确做法：`npm pack @deepseek-ai/<pkg>@<用户实际版本>` 解包，或对已装产物实测。引上游代码必带 `包名@版本/文件:行号`；版本对不上就明写『未在该版本复核』。」
- **框架的缺口**：`evidence-policy.md` 第 5 节要求「记录读取时的文件哈希或 `git diff` 摘要（如果 harness 支持）」，但那是**可选的**、且只解决「读取后文件变了」的问题，**不解决「读的是不是用户实际在跑的那份」**。对多仓库/多版本/依赖包审计，这是致命的。
