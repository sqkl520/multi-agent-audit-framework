## 2. 本轮最有价值的三条

### 2.1 同一形态第三次出现：`animation ... both` 锁死状态类

`S08` / `S16` / `S22` 三处，用户点击后画面完全没反应，根因相同：

```css
/* 动画带 both 填充态，结束后继续占据 transform */
[data-rise].in { animation: riseIn ... both; }

/* 这条永远不生效 —— CSS 动画值在层叠中高于普通声明 */
.sheet.is-folded .face--verso { transform: rotateY(-96deg); }
```

**三次都伴随同一个倒挂**：降级档里 `animation: none`，所以**开了"减少动态效果"的用户能看到功能，普通用户看不到**。

全仓统计：**11 个 CSS 文件同时具备「animation…both」与「状态类改 transform」**。

### 2.2 同一个 bug 的注释还留在仓库里，另一个文件没照着改

`check-texture.mjs` 的注释逐字记录过：

> 「第一版用正则 `/(^|\})\s*([^{}]+?)\s*\{([^{}]*)\}/g`，`}` 被匹配消耗后下一个模式要求 `^` 或 `}`，于是**相邻规则只看到隔一条**。实测 S02 的 `body { … background-image: url(...) }` 落在被跳过的一半里，闸门报「违规 0」。……**测试盲区保护了缺陷**。」

`check-texture` 改成了状态机。**`verify-prototype.mjs:76` 原封不动还在用第一版的正则**：

```javascript
for (const m of C.matchAll(/(?:^|\})\s*(body|html)\s*\{([^}]*)\}/g)) {
```

后果比"漏报"更糟——**它报反了**：

| 时点 | S02 实际状态 | verify-prototype 报的 |
|---|---|---|
| 修复前（ab02f43^） | 有真实违规 | ✓ 通过 |
| 修复后 | 已合规 | ✗ 报警（误报） |

**唯一那条 ✗ 是误报，真问题当年被漏掉了。** 而 README 把这条命令列为"提 bug 前必跑的三条复算命令"之一，还硬编码了期望值 29——实测是 28，任何按 README 复算的人都会去修一个不存在的缺陷。

### 2.3 静默数据丢失：BOM → 署名清零 → 无保护覆写

`fetch-scheme-assets.mjs` 的 `CREDITS_ONLY` 分支（脚本头部注释明确列出的用法）：

```javascript
try { credits.push(...JSON.parse(readFileSync(p, 'utf8'))); } catch { /* 忽略 */ }
...
writeFileSync(join(assets, 'credits.json'), JSON.stringify(credits, null, 1), 'utf8');
writeFileSync(join(assets, 'CREDITS.md'), lines.join('\n'), 'utf8');
```

我核实过：

```
$ head -c 3 .../build/raw/credits.json | od -An -tx1
 ef bb bf                          ← 带 BOM
$ JSON.parse(原样)  → 失败: Unexpected token ''
$ JSON.parse(剥BOM) → 7 条署名
```

**跑一次那条命令，S16 的 7 条 CC 署名被写成 0 条，`CREDITS.md` 被重写成「本目录没有真实照片」，退出码 0。**

CC BY / CC BY-SA 的**法定署名义务**在产物里消失。而该仓库 README 把署名完整度当作已披露的边界项——这条 bug 会让它变成谎报。

**同类风险**：全仓 **7 个活跃脚本**裸 `JSON.parse` 未剥 BOM（`collect-schemes` / `render-scheme` / `summarize-all` / `verify-prototype` 等）。3 份 `build/raw/credits.json` 里 3 份带 BOM。

## 4. 框架更新（本轮沉淀）

### 4.1 新增 4.6.4 层叠级联冲突检查

`animation ... both` 的填充态锁死后续状态类。含检测脚本与判定规则（同一元素？动画是否已结束？状态类是否真改该属性？），以及四种修复方向。

**为什么必须写进框架**：三次失效都发生在"页面看起来完全正常"的地方——CSS 语法没错、选择器没错、值也没错，只是层级关系被动画态压过。**纯文本审查几乎不可能发现。**

### 4.2 新增 4.7 自带自检必须先验证它自己

四步抽验：`a` 有无失败路径 → `b` 断言是否空转 → `c` 断言目标是否真实存在 → `d` **注入故障看它变红**。

配套两条：
- **"降级即失明"原则**：代码里有 `catch` 转日志的地方，验证必须订阅那个日志通道；
- **交付证据时效校验**：证据 mtime 早于被测代码 → 标 `STALE_EVIDENCE`。

### 4.3 强化 4.6 标识符对账

本轮新增两类对账对象：
- **正则字面量**：`consistency.mjs` 匹配 `有别的一个`，生产串是 `另有一个` → 断言永假；
- **BOM / 编码**：7 个脚本裸 `JSON.parse`，遇到带 BOM 的输入会走 `catch` 分支。

## 5. 一条方法论教训：**注释里的历史是最好的缺陷线索**

本轮两条 HIGH 都来自"读注释"：

1. `check-texture.mjs` 的注释记录了正则 bug → 顺着它发现 `verify-prototype.mjs` 没修；
2. `check-stale.mjs:48-53` 的注释记录了"`at` 缺失不能当新鲜" → 顺着它发现产品分支没修。

**这类"修了一半"的缺陷特别危险**：它给人"这个问题已经处理过了"的错觉，而实际上同类代码路径仍然裸露。

**建议加入框架**：审计 Agent 读到一个"已修复 X"的注释时，**必须检查 X 这个模式在其他地方是否也存在且未修**。这比从零找 bug 高效得多——**修复者已经帮你定位了缺陷形态**。
