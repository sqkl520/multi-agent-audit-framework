### `severity` 那条值得单独说

**这是最严重的一条**，因为它让整个降级机制失去依据。

```markdown
<!-- wrappers/audit-specialist.md:58 -->
关于"没有发现怎么办""严重性怎么定"这类行为问题，
全部在 templates/wave2-audit.md 中定义，本文件不复述

<!-- 但 wave2-audit.md:279 实际写的只是准入条件 -->
`severity` 的克制原则：审计Agent不得将任何发现的 severity 标记为 CRITICAL，
除非它同时提供了调用链证据或可复现的触发条件。
```

**「必须有调用链证据才能标 CRITICAL」是准入条件，不是「什么情况下该标 CRITICAL」。**

后果：三个 LLM 用自然语言争论一个本可计算的数字。round31 的 83 条待修复中 **23 条被降级**，降级依据不可复算、不可复现。

## 三、它主张保留的四块（我认为这部分最准确）

**「剥掉之后剩下 1200–1600 行，四块，全是静态工具做不了的」**：

| # | 保留内容 | 为什么工具做不到 |
|---|---|---|
| 1 | **语义入口判断**（`ENTRY` vs `UNREACHABLE`） | 引用图上**没有边**的东西——`serve.mjs` 的用途写在自然语言注释里 |
| 2 | **注释考古** | 「读一条修复注释 → 反推缺陷形态 → 泛化到全仓」。**模式本身藏在注释里**，Semgrep 从零得不出 |
| 3 | **承诺 vs 实现** | 要求同时理解**人类散文**与**机器代码**，并判断二者是否指同一件事。占实测发现的 **22%**，零工具覆盖 |
| 4 | **减法与归并** | 把 128 条收敛成 4 个根因、判定哪些**不修**。**工具的天然倾向是做加法，只有 LLM 会做减法** |

**这四块我认同**。而且第 4 块，它说中了要害——「这应该成为框架的主干，而不是报告的最后一节」。

## 四、它最尖锐的一句（我认为是对的）

> 这套框架最有说服力的段落，几乎都是它**自己撞上工具边界**时写下的——
> `wave2-audit.md:366` 报告 45% 误报，
> `wave3-critique.md:190` 承认 grep 命中不等于同类缺陷，
> `wave2a-sweep.md:172` 承认 72% 预算花在死代码上。
>
> **每一条都在指向同一个结论，只是框架选择了「再加一节规则」，而不是「这一段该换成工具」。**
>
> 框架积累的是**关于自身失效的知识**，而这些知识本该沉淀成检测器。

**这解释了为什么这个框架会长到 5916 行**：每次遇到失效，我的反应都是「加一节规则」，而不是「这段该换工具」。5916 行里，有大量是**补丁的补丁**。

## 五、我的判断：接受方向，但要打折

**接受的部分（约 70%）**：
- 工具该做的事交给工具——这一条我认同且有数据支撑（45% 误报、72% 预算浪费、22% 逻辑未定义）
- 四块真正独有价值的部分要保留并提升为主干

**要打折的部分**：

1. **「72–75% 可删」这个数字偏乐观**。它按行数线性估，没算**去掉这些后连带失效的交叉引用**——比如换成 SARIF 后，`output-contract` 的六个角色分支、`handoff-schema` 的 `open_items` 十种 kind、`wave3` 的裁决枚举全部要重写。**改造成本被低估了。**

2. **「换成工具」有一个它没提的前提**：这套框架的设计目标是**纯提示词、任何 harness**。接 Semgrep/Playwright 就意味着**用户必须装并配置这些工具**——这直接违背了框架"零依赖"的立身之本。**它是一个真实的产品取舍，不是纯粹的技术优劣。**

3. **它的「300 行提示词」估计**：如果真的要保留那四块（语义入口、注释考古、承诺对齐、减法归并），每一块都需要相当篇幅的规则。300 行装不下，**600–900 行更现实**。

**但它有一条我完全接受且必须立刻改**：**`severity` 没有定义**。这不是取舍问题，是硬缺失。

## 六、这份锐评暴露的、我自己的模式

回看这轮对话，我做了这些事：

| 我遇到的情况 | 我的反应 |
|---|---|
| 切片×维度算术不可行 | 加了「两遍制」一节 |
| 预算被死代码吃掉 | 加了「可达性标记」一节 |
| 静态检测漏案 | 加了「必须用 DOM」一节 |
| 守卫永远 exit 0 | 加了「四步抽验」一节 |
| 发现太散 | 加了「缺陷族归并」一节 |

**每一次都是「加规则」。5916 行就是这么长出来的。**

而第 9 视角说的是：**其中至少一半，本该是脚本或工具调用，不是规则**。

这个批评我接受——**但有个反例它没考虑**：加规则的成本是 0（写进 md 就行），加工具的成本是「用户要装 Semgrep」。**在一个"任何 harness 都能用"的目标下，加规则是理性的选择，只是它会让文档膨胀到 5916 行。**

**真正的解法可能是分两层**：
- **核心层（~800 行）**：纯提示词，零依赖，保留四块独有价值
- **增强层（可选）**：接 Semgrep / SARIF / Playwright / 变异测试，把机械活交出去

这样既保持"任何 harness 可用"，又不再用自然语言重新描述流水线。
