## 一、最危险的一处：一个「零裁量」的数字，五个文件给五个答案

`planned_sweep_agents`（宽扫派多少个 agent）——这是**协议明文禁止主 Agent 自行判断**的那个数字。

| 位置 | 公式 | 85 片时派 | 后果 |
|---|---|---|---|
| **A** `scale-mapping:74` | `= effective_slices` | **85** | 超预算 2 倍，撞穿 60 硬护栏 |
| **B** `scale-mapping:273` | `min(片数, discovery_budget)` | **40** | 宽扫吃光预算，**深挖归零** |
| **C** `wave2a:188` | `min(片数, sweep_budget)` | **16** | 两遍制按比例分配 |
| **D** `MANUAL:207` | `min(片数, 40)` | **40** | 同 B |

**B 和 D 这两种写法，已被 `wave2a:194` 自己判定为错误**：

> 「如果直接写 `planned_sweep_agents = min(effective_slices, discovery_budget)`，那么当 `effective_slices ≥ discovery_budget` 时（round31 就是 85 ≥ 40），宽扫会**吃光全部预算**，深挖可用预算为 0」

**为什么这是最危险的**：

1. **它是唯一被声明为「零裁量」的数字**——主 Agent 无论选哪个，都在违反另外三处
2. **它决定后续全部算术**：`total_wave2`、`affordable_slices`、`deferred_slices`、覆盖率统计全部由它派生
3. **两种错误写法都通向坏结局**：按 B/D 深挖归零；按 A 派 85 个
4. **没有任何运行时机制能发现它错了**——症状是「深挖一片没做」或「预算突然耗尽」，两者在报告里都表现为正常的覆盖率不足，**`final-report.md` 的诚实性原则反而会给它背书**

## 二、第二致命：`ENTRY` 被契约判成违规

这是全套矛盾里最讽刺的一处。

```
wave2a-sweep.md 有整整一节 5.0，论证 ENTRY 是关键修正：
  「把它们判为不可达会导致最该审的入口代码被跳过」

但同一个文件的 JSON 示例、output-contract.md:125、run-state.md:55 三处都没有 ENTRY
```

| 位置 | 取值集合 |
|---|---|
| `wave2a-sweep.md` 正文（5.0 节） | `PROD / ENTRY / TEST_ONLY / UNREACHABLE / GENERATED` |
| `wave2a-sweep.md:66`（同一文件的 JSON 示例） | `PROD / TEST_ONLY / UNREACHABLE / GENERATED` ❌ |
| `output-contract.md:125` | `PROD / TEST_ONLY / UNREACHABLE / GENERATED` ❌ |
| `run-state.md:55` | `PROD / TEST_ONLY / UNREACHABLE / null` ❌ |

**契约是闭集 + 「不允许自定义值」+ 第 4 节第 7 步枚举校验。**

→ 宽扫照模板写 `reachability: "ENTRY"` → 判 `CONTRACT_VIOLATION` → **全部输出作废**

**而那 40 个被误判 `UNREACHABLE` 的 CLI 脚本，正是模板说要救的那批。模板要求救它们，契约把救法判成违规。**

## 五、一个我完全没意识到的元问题

这份锐评在取证时发现：

> **这批文件正在被并发修改**（我读取期间 `wave2-audit.md` 从 543 行变成 535 行、`wave3-critique.md` 从 451 行变成 398 行）。所有行号均以我冻结在 `/tmp/snap/framework` 的快照为准。

**它是对的。** 我在它运行期间删掉了两处重复段（`wave3` 的 2.3 重复、`wave2` 的误插段）。

**这暴露了一个我没考虑过的问题**：我在做「审计框架」这件事时，**自己就在被审对象上边审边改**。而这正是框架第 0 节「零写入原则」要防的事——只不过被审对象从"用户仓库"变成了"我自己的框架仓库"。

**它还给了一个解释**，我认为很准：

> 这也解释了为何矛盾多以「改了一半」的形态出现：**修复动作只落在了被点名的那一处，同步维护的其他副本没有跟上。**

这正是过去几轮我做的事——每次收到锐评就改被点名的那一处，但**同一规则的其他副本没同步**。24 处矛盾里，至少 10 处是这个成因。

## 六、我的判断

**这份锐评的价值不在于它列了 24 条，而在于它证明了一个模式**：

> **每修一处，就多一处未同步的副本。**

回看我的修改历史：
- 加了「两遍制」→ `planned_sweep_agents` 的公式在 5 个地方各写了一遍
- 加了「`ENTRY`」→ 只改了正文，没改 JSON 示例和契约
- 加了「4.5~4.7 节」→ 报告五节的骨架改了，但 `report-naming`、`MANUAL` 没跟上
- 把「5 个角色」改成「6 个」→ 只改了契约，README 和 MANUAL 速查表没改

**所以最有价值的修法不是逐条修 24 处，而是**：

**消灭副本。** 同一个事实只在一处定义，其余全部引用。这正是竞品分析那份锐评说的——**该换工具的换成工具，该合并的合并**。

如果 24 处里有一半是因为「同一规则写了 3-5 遍」，那么合并后矛盾自然消失，而不是修 24 遍。

## 七、按"是否值得单独修"分类

| 类型 | 条数 | 处理 |
|---|---|---|
| **副本冗余导致的矛盾**（同一事实多处写） | ~12 | **合并源头**，不逐条修 |
| **真逻辑错误**（如 [14] 诚实上报被惩罚） | ~5 | 逐条修 |
| **改了一半的残留**（如 [23] 索引缺 4 个文件） | ~4 | 补齐 |
| **可接受的表述差异** | ~3 | 不改 |
