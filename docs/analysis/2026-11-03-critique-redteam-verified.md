## 🔴 已核实的致命项 1：主 Agent 被禁止使用它被要求使用的工具

**这是本轮最硬的一条。我自己写的两条规则直接打架，却从没对照过。**

```markdown
<!-- protocol.md:258-261 -->
### 1.5 主 Agent 的工具白名单（放宽后）
允许：spawn_agent / read_result / write_ledger / write_report / update_state
禁止：Read(源代码) / Grep(源代码) / Edit(源代码) / 任何代码分析工具
```

```markdown
<!-- protocol.md:95-102 -->
### 0.6 每次运行的自检
主 Agent 在生成最终报告前必须执行并记录：
  git -C <被审仓库> status --short | grep -E '^ ?[MDARC]' && ...
把这条输出原样附在报告末尾。
```

**白名单里没有 `Bash`，但 0.6 要求跑 `git status | grep`。**

**为什么这比"没有机制"更危险**：它在纸面上看起来有防护。实际结果是——主 Agent 要么跳过这条自检（报告缺一节），要么**伪造一段格式完全正确的输出**。而后者无人能分辨，因为校验者就是写报告的人。

**这不是孤例，是四处同族缺陷之一**：

| 要求 | 出处 | 冲突 |
|---|---|---|
| 跑 `git status` 做零写入自检 | `protocol.md:95-102`、`final-report.md:170-179` | 白名单无 Bash |
| 派发前用 `wc -l` / `ls` 核实行数与文件存在性 | `wave2a-sweep.md:288-297` | 白名单无 Bash |
| 校验 `artifact_paths` 指向的文件存在 | `handoff-schema.md:294` | 禁 Read/Glob |
| "从产物目录重建后重算"覆盖率 | `final-report.md:154`、`run-state.md:349` | 禁一切文件系统访问 |

> **讽刺之处**：零写入自检的设计初衷是"不只声称，给出可复核的证据"（`protocol.md:102`），而它本身成了最容易被伪造的一段文本。

## 🟠 已核实的严重项：锐评波的橡皮图章没有硬门槛

`wave3-critique.md:37` 写的是**措辞**，不是**判定**：

> 「如果它确认了所有发现，这个 session 对它是失败的。」

但全框架**搜不到任何**撤销率下限、移除条数阈值、或"全 `holds` 即作废重派"的硬规则。门控只要求 Skeptic 和 DA 都 `SUCCESS` 且无 `PENDING`——**一个 100% `holds` 的 Skeptic 是 `SUCCESS`**。

**更糟的是结构性偏向**：五个「不可自信」领域明文规定"没有直接矛盾证据就必须 `holds`"（`:112`）。一个保守的 Skeptic 在这些领域**被动地全 `holds`**，而这恰好是审计里最重要的一类缺陷（内存安全、并发、声明一致性）。

## 🟠 已核实的严重项：切片做大能同时关掉覆盖率审查

复合利用路径：

```
侦察 Agent 每片塞 25-40 个文件
→ 切片数从 56 降到 8
→ 宽扫只要 8 个 Agent
→ 深挖阈值 lead_count >= 3 在大切片上更难命中
→ 实际阅读退化为抽样

且：切片数落到 1-5 档时，锐评角色自动降级为 Skeptic + Arbiter
    → Devil's Advocate（唯一的覆盖率攻击者）被裁掉
```

**把 60 片压到 5 片，同时消掉锐评波的覆盖审查。**

而门控**只校验 `slice_count == len(audit_slices)`**，不校验 `file_count` 范围——尽管该字段是必填。

## 为什么这些能成立：横切病灶

**验证者与被验证者同源。**

| 被比对的两方 | 谁写的 |
|---|---|
| `discipline_log` vs `state.json` vs `wave2_completed` | **全是主 Agent** |
| `files_read` vs 实际读取 | **全是子 Agent 自报** |
| `packet_digest` 校验 | 自算自校，伪造者顺手算一遍即可 |

**全框架没有一条「断言 vs 独立事实」的对照。** 唯一接近的是 `evidence-policy.md:113` 的可选哈希，但「如果 harness 支持」，且**没有任何角色被指派去核这个哈希**。

框架自己在 `wave3-critique.md:153` 承认了这个局限：

> 「若主 Agent 既做了裁量**又**同步伪造了派发记录，机械比对无法识别」

## 红队建议补的唯一机制：`spot-checker`

**一个持有 Read/Grep/Glob/Bash 的独立复核采样 Agent。**

```
触发：波次二B 闭合后、波次三派发前（与锐评波并行，不占锐评预算）
输入：只收 artifact_path + slice 的 files[]（不收任何自报的 files_read / quote）
抽样（写死，零裁量）：
  - 每切片随机 2 个文件 → 核 files_read 是否真包含
  - 每个 artifact 随机 3 条 evidence → grep -F 逐字核 quote
  - 每切片 1 条 UNREACHABLE → 复跑 import 检查
  - 全仓随机 3 片 → wc -l 是否在 800-1800、file_count 是否 5-8
判定：failed 非空 → 该 artifact 整份作废，切片回 PENDING，覆盖率按"未覆盖"计
输出：{checked, passed, failed: [{kind, file, expected, actual}]}
```

**为什么是这一个**：

1. 把"自报"变成"可核"，**一次堵住 4 条作弊**——它们只是同一句谎话的不同字段；
2. **不需要主 Agent 越界**：它只收到三个整数，上下文隔离原则不破；
3. **成本极低**：每片 3-5 次工具调用，40 片约 150 次读 ≈ 2-3 个审计 Agent 的预算；
4. **可机械执行、无解释空间**；
5. **顺带解决了横切病灶**——`git status`、`wc -l`、`ls` 这些主 Agent 无权做的检查，现在有了有权限的执行者。

## 我的判断

**必须接受的三条**（因为它们是我自己写的规则互相打架，不是主观判断）：

1. 工具白名单 vs 自检要求 → **必须修**
2. `reachability` 承诺无落点 → **必须修**
3. `files_read` 零成本伪造 → **必须修**

**需要权衡的一条**：橡皮图章没有硬门槛。「撤销率下限」这类硬指标有风险——**强行要求 Skeptic 撤掉 N% 会逼它滥杀**。但至少应加一条：「全 `holds` 且 `targets > 20` 时，必须第二次派发，两次都全 `holds` 才算通过」。

**`spot-checker` 我认为应该采纳**。它是本轮锐评里唯一一条「加机制而不是加规则」的建议，而前面几轮的经验是——**加规则不会被执行，加有工具的执行者才会**。
