# 自主性修复：从「每做完一段就停」到「自动往下走」（2026-11-04）

> **这份记录的不是代码缺陷，是流程的病。**
>
> 用户的原话：「最严重的是每做完一点就停下来向我汇报，然后告诉我要不要下一步做什么。」
>
> 根因在老版本（`git HEAD`）里，不是措辞问题，是**结构问题**：报告被当成了终止动作。

---

**老版本会出报告，但报告就是终点。** `MANUAL.md:49` 写「一轮跑不完，会有一部分切片标为 `DEFERRED` 留给下一轮」，`:449` 写「下一轮接着审」——两处都默认「下一轮会自己发生」，而全框架没有任何一处定义谁启动它、什么条件启动、什么时候停。

用户的体验因此是：拿到一份诚实但终止的报告，然后必须亲自说一句「继续 round31」。**一轮一句，5 轮链就是 5 次值守。** 这把「不计 token 的长任务」反转成了「按用户在线时长计的长任务」。

**为什么老版本特别容易触发它**：修复波在默认路径里，而修复是唯一有写权限、有副作用的角色，每一步都可能产生 `TEST_CONFLICT` / `ROLLBACK_UNAVAILABLE` / `escalation_required: true`。**生成「需要人裁决」这件事本身是默认流程的常规输出，不是异常。**

## 二、这轮找到并修掉的四处

### 1. `run-state.md` §6 与 §6.5 在 `PARTIALLY_CLOSED` 上打架（最严重）

**原文**

```
§6    : status 不是 CLOSED → 续跑它，不要新开 round{N+1}
§6.5.1: status 是 CLOSED 或 PARTIALLY_CLOSED → 若有 DEFERRED，自动开 round{N+1}
```

而第 5 节规定**预算耗尽 → `PARTIALLY_CLOSED`**。

于是最常见的那条路径上两条规则给出相反指令：按 §6 走，`DEFERRED` 永远不消化、链不推进，**外部表现就是「停下来等人」**——正是 §6.5 开头说要解决的那个问题。主 Agent 无论选哪条都是违规的。

**实证**（用真实 `state.json` 构造 `PARTIALLY_CLOSED` + 2 片 `DEFERRED` + 已出报告）：

```
修复前  旧 §6 判定 : RESUME_SAME_ROUND
        §6.5 判定  : OPEN_NEXT_ROUND
        结果       : ❌ 冲突 —— 已出报告却要续跑，DEFERRED 永不消化

修复后  §6   → OPEN_NEXT_ROUND
        §6.5 → OPEN_NEXT_ROUND
        ✓ 两条规则一致
```

**根因是判据选错了。** 正确分界不是「有没有 `CLOSED`」，而是**「本轮波次是否已经走完」**：

| 情形 | 状态 | 动作 |
|---|---|---|
| 波次走完、出了报告、留有 `DEFERRED` | `PARTIALLY_CLOSED` | **开新轮** |
| 跑到一半被中断（还没写报告） | `RUNNING` | **续跑同一轮** |
| 连续失败停下 | `BLOCKED` | 开新轮，失败切片进新轮 |

**关键区别**：已经出过报告的那一轮不该被续跑——续跑会让同一轮产出两份报告，且旧 `DEFERRED` 与新派发切片混在一起，无法判断谁覆盖了谁。

### 2. 续跑协议对 `PARTIALLY_CLOSED` 和 `RUNNING` 没有定义

`run-state.md` 第 182–183 行原文只有 `CLOSED` 和 `BLOCKED` 两条分支。落到 `PARTIALLY_CLOSED` 的续跑 Agent **无从判断该干什么**——实际表现就是要么重复续跑一个已收口的轮次，要么停下来问用户。

改成四条互斥且穷尽的分支表，并**删掉「等用户决定」**：

> 续跑的目标就是不让用户值守，在已知 `BLOCKED` 原因时停下来问，等于把这个目标取消掉。

同样删掉 `in_flight` 状态不明时的「先向用户报告」，改为标 `PENDING` 重派 + 记 `UNVERIFIED_AGENT_STATE`。

### 3. 多失败窗口要求「等待人工介入」（三份文件各写了一遍）

`protocol.md:96`（老版）、`MANUAL.md:434`、`README.md:184` 都写「暂停该波次新派发，等待人工介入」。

改为**自动降级四步**：失败切片标 `DEFERRED` → 连续 3 次同因则终止本轮 → 否则出报告并自动开下一轮 → 报告单列暂停原因。

> **不得「暂停并等待人工介入」——那会让一次可自动降级的技术故障，变成用户必须值守的停机。**

### 4. `attempt` 归零的死锁在另外三份文件里还活着

上一轮修了 `protocol.md` §4.1 的 `CONTRACT_VIOLATION` 无限重派，但同样的旧规则还在：

```
output-contract.md:444   → 派发全新实例，attempt 从 0 重新计数。
MANUAL.md:432            → attempt 从 0 计
README.md:182            → attempt 从 0 计数
```

**改一处必须同步 N 处，这是框架的固有成本。** 三处已全部改为 `attempt +1` 并指向 §4.1。

## 三、防止复发的机制

### `tools/lint-autonomy.mjs` —— 静态检查「不得要求用户值守」

| 规则 | 检查内容 |
|---|---|
| **L1** | 活规则里出现「等用户 / 等待人工介入 / 需要人工决定 / 先向用户报告」 |
| **L2** | `run-state.md` §6 的可执行规则块与 §6.5 判据一致，且覆盖 `RUNNING` 与 `PARTIALLY_CLOSED` |
| **L3** | `CONTRACT_VIOLATION` 的 `attempt` 不得归零 |
| **L4** | 自动续轮要素齐备（`max_rounds` / `DEFERRED` / `STALLED` / 自动开下一轮） |
| **L5** | 终止必出报告；`IN_PROGRESS` 不得作为终态 |

**这个检查器第一次跑就抓到三个我没注意到的活规则**：`run-state.md:192`、`handoff-schema.md:140`、`wave4-fix.md:136`。人工 grep 时它们混在别的上下文里，没被识别出来。

它同时也抓到了**我自己**刚写的一句话（引用旧规则的计数说明），提醒我加豁免判据——这说明它审的是文本，不是我的意图。

### `tools/simulate-round-chain.mjs` —— 规则自洽性模拟

23 个用例，把 §6 / §6.5 的规则**逐条编码成代码**跑：

| 用例 | 期望 |
|---|---|
| 56 片 / 每轮 16 | 4 轮覆盖完，无卡死 |
| 200 片 / `max_rounds=5` | 必须停在 `MAX_ROUNDS` |
| 每轮容量 0 | 必须 `STALLED`，**不能死循环** |
| `PARTIALLY_CLOSED` + `DEFERRED` | §6 与 §6.5 必须都判 `OPEN_NEXT_ROUND` |
| `RUNNING` | 必须 `RESUME_SAME_ROUND` |
| 0 片输入 | 立即停，不空转 |

**为什么要模拟而不是真跑**：真跑一轮要几百个 agent，成本高到不可能用来验证规则本身。而规则自洽性是一个**纯状态机问题**，几十行代码就能穷举。

## 四、必须承认的边界

**规则层修好了，真实运行没验证。**

我们这轮真跑只完成 1/40 切片，**从没走到「一轮闭合 → 检查 `DEFERRED` → 自动开下一轮」这条路径**。

所以正确的表述是：

- ✅ 老版本那个「报告即终点」的结构**已被替换**
- ✅ 新旧规则的冲突**已被机械检查钉住**
- ❌ **「长任务能无人值守跑完」没有被实测证明**

要验证它，得跑一次能真正闭合的轮次，观察它是否自己开下一轮。在那之前，`START-HERE.md` 里这条应该标「结构已改，未实测」。

**另外一条同类的边界**：这些规则约束的是**框架调度子 agent 时的终止行为**，不是我在对话里向你汇报的习惯。两者是不同层面的事，前者改好了不代表后者自动改变。
