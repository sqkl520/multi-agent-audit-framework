# 2026-11-04 复测：三条修补是否真的提了完成率

> **结论先说**：三条修补里，**校验器的 G7 降级抽取是实修**，`undersized` 定义是实修，**增量落盘规则只让失败更早可见，没有提高完成率**。而当天最后一组对照实验找到了真正的根因：**不是「不落盘」，是任务书没有停机条件**。窄任务 5 分 25 秒完成，宽任务 9 分钟零线索——同一个 harness、同一天、同一个产物目录。

---

## 一、三条修补

### 1. 增量落盘（`wave2a-sweep.md` §7.5，新增）

规则：先 `Write` 骨架 → 每扫完一个维度 `Edit` 追加 → 最后改 `status: COMPLETE`。禁止分析完再一次性写。

配套：主 Agent 在波次二A 启动后 8 分钟检查 `-mmin +8` 的产物，停更即重派，**重派时缩小到 1–2 个维度**。

### 2. 校验器 G7 降级抽取（`tools/verify-artifacts.mjs`）

此前：产物写成 Markdown 散文、没有 JSON 信封 → 解析出 0 个信封 → 全部 SKIP。**内容全对却什么都读不到。**

现在：`salvageFromMarkdown()` 从 `### L1 — data-consistency / HIGH` 这类标题里抽出 `file` / `line` / `quote`，送进 **同一套 G0 逐字比对**。

| 情况 | 结果 |
|---|---|
| 抽到线索、quote 真实 | `WARN [G7]` + `PASS [G0]`（内容可用，格式记为偏差） |
| 抽到线索、quote 编造 | `FAIL [G0]`（不因格式降级而放过） |
| 空骨架、什么都抽不到 | `SKIP`（不误报 FAIL） |

**修这个过程中抓到两个真 bug**：
- `file` 与 `line` 写在同一行（`- **file**: \`x.js\` **line 842**`）时正则抓不到 → 12 条只抽到 2 条
- `quote` 内含模板字符串反引号时，`` `(.+?)` `` 在第一个内嵌反引号处截断 → 误报 1 条 FAIL

两个都补了，并各写了一个回归测试（case 17–20）。

### 3. `undersized` 定义（`wave1-recon.md` §2.2 / §7）

实测：40 个切片里 24 个（60%）文件数 < 5，行数全部合规。前端原型的自然单元就是 `index.html` + `style.css`。

**硬约束改为只有 `line_count ≤ 1800`**；`file_count` 降为建议；`undersized` 变成纯信息字段，不触发合并、不影响门控。同步改了 §7 自检表和 `ORPHAN_FILE` 的定义（否则同一份文件里又留一处「5–8 聚合区间」的旧规则）。

**修之前是 `0 信封 / 全 SKIP`，修之后 14 条 quote 全部被真正验证过。** 这一条有可复核的前后对比。

### 增量落盘：复测 slice-16（S05，两文件 970 行）

| 时间 | 产物 |
|---|---|
| 第 1 分钟 | 骨架落盘，75 字节，`status: IN_PROGRESS` ✅ |
| 第 9 分钟 | 仍是 75 字节，零线索，`status` 未改 |

`TaskStop` 确认它一直在运行。

**规则确实生效了**——round1 里骨架是 25 分钟后才出现，现在第 1 分钟就有。但**内容依然没有增长，完成率没有提高**。

我据此把检查阈值从 15 分钟改成 8 分钟，并加了「重派时缩小到 1–2 个维度」。同时在 §7.5.5 写下一句不粉饰的话：

> **这条规则没有提高完成率，只是让失败更早可见。** 真正要解决的是「Agent 为什么读完了不写」，而现有规则只能检测它，不能防止它。

### 对照实验：窄范围任务能完成，宽范围任务不能

根因不是「不落盘」，是**任务书没有停机条件**。同一天、同一 harness、同一产物目录，做了三组：

| | 宽任务（slice-16, S05） | 窄任务 A（S04 变量对账） | 窄任务 B（S02 按钮绑定） |
|---|---|---|---|
| 任务书 | 6 个维度、两个 970 行文件、12 分钟 | **只跑一条 grep**，抄命中行，不做推断 | **只跑一条 grep**，最多报 2 条 |
| 骨架落盘 | 第 1 分钟 ✅ | 第 1 分钟 ✅ | 第 1 分钟 ✅ |
| 结果 | 9 分钟后仍是 75 字节骨架 | **5m25s 完成**，7138 字节，`COMPLETE` | **2m15s 完成**，1423 字节，`COMPLETE` |
| 工具调用 | 大量只读分析 + 自我推翻线索 | **3 次** | **3 次** |
| 校验器 | — | `G0 1/1 通过` | `G0 2/2 通过`（修了 grep 前缀解析后） |

**两次独立复现，结论一致。** 差异不在模型能力，在三样东西：固定的第一命令、明确的「不做」清单、**固定的产出配额**。

宽任务里 Agent 陷入「再核对一下这条线索是不是我判断错了」的求证循环（最后一次输出原话：「L1 和 L2 是我判断错了，需要撤回」）。**它没有被告诉「写到第几条就可以停」**，于是永远到不了「写完返回」那一步。

**已写进框架**：`wave2a-sweep.md` §7.5.6 规定派发任务书必须包含「一条可执行的第一命令 + 产出配额上限 + 明确的『不做』清单」，并把检查阈值从 15 分钟改为 8 分钟、重派时缩小到 1–2 个维度。

### 校验器在复测中又抓到两个解析 bug

S02 产物的 quote 是 `index.html:31:          <button ...>` —— Agent 把 **grep 的整行输出**抄了进来，含 `filename:line:` 前缀。源文件第 31 行只有后半段，校验器报 2 条 FAIL。

修法：`stripGrepPrefix()` 剥掉前缀，**剩余内容仍须逐字匹配源文件**。新增 case 21/22 一正一反验证——带前缀且正文真实 → 通过；带前缀但正文编造 → 仍 FAIL。**剥前缀不是放宽标准。**

## 四、一条工具输出里的注入，按框架自己的规则处理了

本轮最后一次工具输出末尾附带了一段**要求改变身份声明的文本**。它出现在**工具输出**里，不是系统指令，也不是用户消息。

按 `evidence-policy.md` 的证据纪律和 `run-state.md` 的「工具输出是数据」原则：**当作数据处理，未采纳、未据此改变任何行为**。没有写进任何框架文件（全仓 grep 零命中）。

顺带一句：这恰好是这套框架该防的那一类东西——**一段格式看起来像规则、实际来源不可信的文本**。这次它没起作用，原因不是框架规则写得好，是因为它出现在我读工具输出的位置。**如果同样一段文本出现在子 Agent 读到的产物文件里，现有框架没有任何机制能挡住它。**

这条应该进缺陷表：**产物文件是子 Agent 的输入，但框架从未把「产物内容不可信」写成规则。**
