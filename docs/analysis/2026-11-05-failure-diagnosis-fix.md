# 失败诊断修复：从「只知道失败」到「知道为什么失败」（2026-11-05）

> 链式实测暴露了两个问题：失败切片没有原因字段、宽扫失败率 25%。
> 这份记录的是修复，以及修复有效性的实测证据。

---

## 问题一：`state.json` 只记 `FAILED`，不记为什么

### 实测发现

链式实测里 8 个切片失败 2 个（25%），但 `state.json` 里两次都是裸的：

```json
"slice-02": { "state": "FAILED", "files": [...] }
"slice-06": { "state": "FAILED", "files": [...] }
```

**这两个失败是完全不同的形态**，但当时无法区分：

| 切片 | 产物字节 | 现象 |
|---|---|---|
| slice-02（round2） | **0**（文件不存在） | 从未写入 |
| slice-06（round2） | **44**（骨架） | 写了骨架就没再动 |

两者的重派策略应该不同——前者疑似瞬时故障，后者是结构性问题。**没有字段，主 Agent 只能盲目重派。**

### 修法

`slices[].failure` 新增四个字段：

```json
"failure": {
  "error_type": "SCRIPT_TIMEOUT | TOOL_REJECTED | NO_OUTPUT | EMPTY_RESULT | CONTRACT_VIOLATION | null",
  "observed": "骨架 status 停在 IN_PROGRESS，mtime 00:20，41 分钟后仍无 Edit",
  "artifact_bytes": 44,
  "last_write_at": "2026-11-05T00:20:00+08:00",
  "inferred_cause": "读完 grep 后未产出任何 Edit 调用，陷入分析循环"
}
```

**`artifact_bytes` 和 `last_write_at` 是关键的区分字段**：0 字节 vs 44 字节，「从未写过」vs「写了就停」。

### 配套：`tools/classify-failures.mjs`

把「看现象 → 定类型」的机械部分拿下来，不靠人读 transcript 去猜。

| `error_type` | 判据 | 重派策略 |
|---|---|---|
| `NO_OUTPUT` | 产物不存在或 0 字节 | `RETRY_AS_IS`（先查路径） |
| `SCRIPT_TIMEOUT` | 骨架 + `status: IN_PROGRESS` + 零线索 | `SPLIT_BY_DIMENSION` |
| `EMPTY_RESULT` | `COMPLETE` 但零线索 | `DO_NOT_RETRY` |
| （有线索但未标 COMPLETE） | — | `ACCEPT_PARTIAL` |

**对真实数据的输出**：

```
round1:  slice-02 → SCRIPT_TIMEOUT  (44 字节骨架)
round2:  slice-06 → SCRIPT_TIMEOUT  (44 字节骨架)
         slice-02 → NO_OUTPUT       (产物不存在)
```

同一次链里出现了两种类型——**这就是为什么必须有这个字段**。

`classify-failures.test.mjs` 有 16 个用例，全部基于实测出现过的形态。

### 配套：连续失败规则

| 情形 | 动作 |
|---|---|
| 同一 `slice_id` 连续 2 轮失败，且 `error_type` **相同** | 停止重派，写 `unverified` |
| 连续 2 轮但 `error_type` **不同** | 允许再试一次 |
| 已重试 3 次 | 无论原因，`PERMANENT_FAILURE` |

**实测依据**：slice-02 在 round1 和 round2 连续失败两次。按旧规则无法判断是同一原因还是不同原因——现在能判断了（round2 是 `NO_OUTPUT`，与 round1 的 `SCRIPT_TIMEOUT` 不同，可以再试）。

## 问题二：宽扫 agent 25% 失败率，两次都是「写了骨架就停」

### 从 transcript 挖出的根因

slice-06 的 transcript 显示：

| 观测 | 值 |
|---|---|
| 声明的工具调用 | 4 次 Write + 3 次 Edit |
| **实际生效的写入** | **1 次**（只有骨架） |
| 5 次 `Bash` / 3 次 `Grep` / 3 次 `Read` 之后 | **无任何 Edit 调用** |
| `user-rejected` | 0（不是权限问题） |
| 线索数 | 0（不是配额问题，配额是「最多 3 条」） |

**它读完了，然后没有下文。** 不是被拒绝，不是没配额，是**陷入了分析循环**。

### 修法：任务书里插入强制中间落盘点

**旧任务书**（失败的）：
```
扫这 6 个维度，找出可疑点，最多 3 条线索。
```

**新任务书**（5 个固定步骤）：
```
第 1 步  Write 骨架
第 2 步  跑第一条 grep → 立刻 Edit 把 grep 原始输出贴进去
第 3 步  跑第二条 grep → 再 Edit 一次
第 4 步  从已贴入的原始输出里挑线索 → Edit 写成 ### L1 ...
第 5 步  改 status: COMPLETE
```

**关键差异**：第 2、3 步要求的是「**把工具输出原样贴进去**」，不是「分析后写结论」。

| 任务形态 | agent 要做的事 | 会卡住吗 |
|---|---|---|
| 「扫 6 个维度，找出可疑点」 | 先理解、再判断、再产出 | **会**——判断没有终点，可以无限求证 |
| 「跑这条 grep，把输出贴进去」 | 复制粘贴 | **不会**——动作有终点 |

### 实测验证

**同一个切片（slice-06 的 S06），之前卡了两次，换任务书后**：

| 版本 | 任务书 | 结果 |
|---|---|---|
| round2 | 「扫 6 维，找可疑点」 | 44 字节骨架，10 分钟超时，`TaskStop` |
| round3 | 「5 步，第 2/3 步贴 grep 输出」 | **7372 字节，4 分钟完成，3 条线索，`status: COMPLETE`** |

机械校验：**3/3 quote 真实，0 FAIL**。

**这是修复有效的直接证据**——不是推断，是同一目标的对照实验。

## 累计实测数据

| 任务书类型 | 完成 | 失败 | 失败率 |
|---|---|---|---|
| 「扫 N 个维度找可疑点」（宽） | 0 | 3 | **100%** |
| 「跑固定命令 + 贴输出 + 配额 3 条」（窄） | 9 | 2 | **18%** |
| 「5 个固定步骤，含强制落盘点」 | 1 | 0 | **0%（样本 1）** |

> **样本量必须说明**：最后一行只有 1 个样本，不足以证明 0% 失败率。但**宽任务的 3/3 全失败**与**窄任务的可用**形成了鲜明对比，而「贴输出」这个修法有明确的机制解释（判断有无限空间，复制粘贴有终点）。

## 一个必须记下的教训

**「聪明的任务书」在这套框架里是负债。**

我最初给宽扫写的任务书是「扫这 6 个维度，判断哪里可疑」——这听起来是对一个审计 agent 该有的要求。但它给了 agent 无限的判断空间，而 agent 在判断空间里会一直判断下去。

**改成机械步骤后，它反而完成了。**

这与整个项目的核心结论一致：**机械归代码，判断归提示词**。而这里更进一步——**即使必须由 LLM 做的部分，也要把它切成有明确终点的机械步骤**，否则 LLM 会卡在没有边界的判断里。
