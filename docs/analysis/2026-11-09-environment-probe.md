## 一、为什么这个原则是对的

上一轮我给的选项全是「选一条路走到底」，隐含假设是「环境是已知的」。但实际上：

| 参数 | 不同环境的取值 |
|---|---|
| 并发上限 | Claude Code workflow **16**（受 CPU 影响）；subagent **20**；`CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS` 可调 **1–256** |
| Workflow 是否可用 | 取决于版本，起始版本 `v2.1.150` |
| 单任务耗时 | 实测同类任务 **47 分钟**，但我曾按 8 分钟判断 |
| 是否要中途签核 | Workflow **不支持**（`No mid-run user input`），纯 subagent 可以 |
| 模型 | 逐阶段可指定，但默认行为随 harness 版本变 |

**写死任何一个都是错的。**

## 二、加了什么

### 2.1 `framework/orchestrator/environment-probe.md` —— 给主 Agent 的探测协议

核心是**先问四个问题，再动手**：

```
1. 你用的哪个 harness？支持 Workflow 吗？
2. 并发上限是多少？（不知道就说不知道，不要猜）
3. 这类任务预期跑多久？
4. 要不要每波结束后确认？
```

第 4 问最关键：**要中途签核 → 不能用 Workflow**（官方限制）。这一条决定了整个执行路径。

### 2.2 `tools/detect-harness.mjs` —— 能跑就测

探测项与结果（本机实测）：

```
OS            win32 (10.0.19045), 20 核
harness       claude-code (2.1.289)
Workflow 可用  likely

并发上限:
  workflow    16   ← 官方默认（受 CPU 影响，实际可能更低）
  subagent    20   ← 官方默认
  建议使用      16

超时:
  stall       未设置，使用 harness 内部默认
  重试        5（官方文档：stall retry 最多重启 5 次）
```

**探测不到一律标 `unknown`，不猜。**

### 2.3 并发与超时的计算规则

```
并发上限 = min(用户告知的值, 探测到的值, 256)
           都拿不到 → 4（保守），第一次触顶后调整

超时     = 不设自己的超时
           一律等 harness 报告终态
           无此能力 → 记 state_unknown，继续等

重试     = 优先用 harness 的
           无则按 protocol.md §4.1 的 attempt 计数
```

**永远不要发明一个比 harness 更小的超时值。**

## 四、探测器的版本比较 bug（值得单独记）

第一版把版本比较写成了：

```js
const cmp = (a, b, c) => (maj - a) * 1e6 + (min - b) * 1e3 + (pat - c);
if (cmp(2, 150, 0) >= 0) { ... }
```

**两个错误叠加**：

1. `cmp(2, 150, 0)` 把 `150` 当成 **minor**，而 `v2.1.150` 里 150 是 **patch**
2. 加权比较 `(min-b)*1e3` 在 patch 超过 999 时会溢出进位

结果：本机 `2.1.289`（明确支持 Workflow）被误判为**不支持**，进而给出完全错误的执行路径建议。

**修法**：改逐级比较，阈值传 `(2, 1, 150)`。

```js
const cmpTo = (a, b, c) => {
  if (maj !== a) return maj - a;
  if (min !== b) return min - b;
  return pat - c;
};
if (cmpTo(2, 1, 150) >= 0) { ... }
```

**`detect-harness.test.mjs` 有 11 个用例锁住它**，含边界（2.1.150 支持、2.1.149 不支持）、minor 优先（2.0.999 不支持）、patch 过千（2.1.1000 支持）。

> **这个 bug 的教训**：它看起来完全合理，人工 review 发现不了。**而它的后果是让人按错误的路径执行**——比崩溃更危险。
