# harness 优先：一次导致误杀的测量错误（2026-11-09）

> **这份记录的核心不是「加了条规则」，是「我发明的测量工具是错的，并用它杀掉了正常工作的 agent」。**

---

## 一、触发这件事的数据

用户在讨论「每个 harness 都有独属于自己的多 agent 方案」时，给出了一张真实运行时截图：

| 工作流 | agent 数 | 单个 agent Runtime | 总 token |
|---|---|---|---|
| `round3-verify-batch1` | 5 | **28m36s / 47m48s / 47m48s / 47m48s / 40m31s** | 243.8K |
| `round3-fix-batch2` | 7 | 33m40s / **47m34s** / 11m29s / 20m08s / 8m33s / 16m29s / 22m51s | 638K |

**47 分钟是这批任务的常态。**

---

## 二、我据此做过的错事

### 错误 1：发明了一个比真实工作量小一个数量级的阈值

| 我定的规则 | 真实常态 | 差距 |
|---|---|---|
| 「8 分钟无更新即重派」（`wave2a-sweep.md` §7.5.5） | 47 分钟 | **6 倍** |
| 「10 分钟无输出即 `TaskStop`」（我实际执行的） | 47 分钟 | **5 倍** |

按这两个阈值，截图里那 12 个 agent 有 **9 个会被杀掉，而它们全都在正常工作**。

### 错误 2：把 mtime 当成活性证据

`run-state.md` §4.4 里我写过三级证据（A：harness 状态 / B：进程表 / C：文件 mtime），并明确标注 C 级「最低，且会骗人」。**然后我自己用了 C 级**。

harness 直接提供精确 Runtime，我不用，去 `stat` 文件的 mtime。

### 错误 3：把误杀的结果解释成「agent 有问题」

2026-11-04/05 的链式实测中，我用 `TaskStop` 终止了 4 个 agent，把其中 2 个记成 `SCRIPT_TIMEOUT`，并据此写了：

- 「宽扫 agent 失败率 25%」
- 「根因是任务书给了无限判断空间」
- 「贴 grep 输出的任务书能提升完成率」

**前两条现在不可信。** 那些 agent 可能只是还没跑到写产物那一步。第三条有独立证据（round3 对照实验确实成功），但它也可能是「活得更久所以写完了」，而不是「任务书更好」。

---

## 三、改了什么

### 3.1 超时判据：从「主动杀」改为「不主动杀」

`run-state.md` §4.4.2 完全重写：

```
【默认：不主动杀】
在 harness 报告终态（完成 / 失败 / 超时）之前，主 Agent 不得主动终止 agent。
```

**唯一允许主动终止的三种情形**：

1. 用户明确要求
2. 预算硬触顶且须腾槽位（按 FIFO 终止最长的，记 `TERMINATED_BY_BUDGET`）
3. 确认是重复实例（产物已由另一实例正确产出）

`wave2a-sweep.md` §7.5.5 的 8 分钟规则**直接作废**。

### 3.2 失败分类：从「断言原因」改为「描述事实」

| 旧 | 新 |
|---|---|
| `SCRIPT_TIMEOUT` | `SKELETON_ONLY` |
| 推断：「写了骨架后未再产出内容（陷入分析循环或上下文耗尽）」 | 推断：「**不确定**：可能仍在运行 / 被提前终止 / 陷入循环。**不得据此判定 agent 失败**」 |
| 重派策略：`SPLIT_BY_DIMENSION` | 重派策略：`CHECK_HARNESS_STATE_FIRST` |

**名字本身就带着错误推断**——`SCRIPT_TIMEOUT` 暗示「超时了」，而实测表明它更可能是「还没写完」。

对真实历史数据重跑，输出现在是：

```
slice-06  →  SKELETON_ONLY
    推断: 不确定：可能是仍在运行 / 被提前终止 / 陷入分析循环。
          **不得据此判定 agent 失败**，需先查 harness 的运行时状态
    重派: CHECK_HARNESS_STATE_FIRST
```

### 3.3 编排层降级为 harness 对照表

`protocol.md` 新增 **§0.0 harness 优先原则**，位置在全文最前面（凌驾于其余调度规则）：

| 能力 | 本框架原本怎么做 | harness 提供什么 | 用哪个 |
|---|---|---|---|
| 并发上限 | `concurrency_window` 查表 | 原生并发批次 | **harness** |
| 重试计数 | §4.1 attempt + digest | 原生重试语义 | **harness** |
| 任务状态 | `state.json` 推测 | 原生终态 | **harness** |
| 耗时统计 | 手工 `stat` mtime | **精确到秒** | **harness** |
| token 计量 | **完全没有** | **精确计数** | **harness** |
| 模型选择 | **完全没有** | 逐任务标注 | **harness** |
| 审什么 / 证据标准 / 交付物形状 | 各 templates | **不提供** | **本框架** |

`scale-mapping.md` 新增 §0：**harness 有原生能力时，第 2~6 节的并发与预算算术全部跳过。**

## 四、一个必须承认的量化事实

改动前统计了框架的构成：

| 类别 | 行数 | 占比 |
|---|---|---|
| **编排类**（调度 / 状态 / 契约 / 命名 / 握手） | 2809 | 47% |
| **判断类**（怎么审 / 证据标准 / 报告） | 2752 | 46% |
| wrapper（角色声明） | 552 | 7% |

**将近一半的篇幅在重新发明 harness 的运行时。**

而 harness 提供的那部分（并发、耗时、token、模型选择）**它做得精确得多**：

| 项 | 本框架 | harness |
|---|---|---|
| 耗时 | `mtime` 推测，会骗人 | `47m48s`，精确 |
| token | 从不计量 | `638K`，精确 |
| 模型选择 | 概念都不存在 | 逐任务标注 |
| 任务状态 | `state.json` + 判断 | 原生 `✓` |

**这不是「简化版」，是「更差的版本」。**

## 五、我认为正确的分层

```
harness 负责（它做得更好）：
  扇出、并发批次、相位、模型选择、耗时、token、任务终态

框架负责（harness 管不了）：
  审什么（切片规则、维度划分）
  什么算证据（门 0）
  什么结论不成立（锐评 / Skeptic）
  报告长什么样（交付物规范）
  严重性定级（本框架至今未解决）
```

**6113 行里真正值钱的是「判断」那一半。** 编排那一半在 harness 面前是负债——不但是重复劳动，而且我的版本会误导（8 分钟阈值）。
