# 安全策略

## 这个仓库是什么（以及这里的「漏洞」指什么）

这是一套**提示词框架 + 零依赖的 Node.js 校验器**。它不提供服务、不监听端口、没有运行时依赖。
因此现实的安全关注点比应用类项目窄：

| 类别 | 例子 | 是否在范围内 |
|---|---|---|
| **凭据泄漏进 git 历史** | API key 被提交、后来删掉 | **在范围内 —— 最高优先级** |
| **校验器绕过** | 契约标为强制的规则，检查器静默跳过 | **在范围内** |
| **通过产物触发任意代码执行** | 校验器用未转义的产物内容去 shell | **在范围内** |
| **针对校验器的拒绝服务** | 构造的产物触发灾难性正则回溯 | **在范围内** |
| 被审计目标仓库的漏洞 | — | **不在范围内** —— 请报给那个项目 |

## 如何报告

**不要开公开 issue。**

请用 GitHub 的私密公告流程：
**Security → Advisories → "Report a vulnerability"**
(<https://github.com/sqkl520/multi-agent-audit-framework/security/advisories/new>)

如果无法使用该流程，请发邮件到维护者 GitHub 主页上的地址，标题里写 `SECURITY`。

请包含：受影响的提交或文件、触发它的输入、以及你观察到的行为与契约规定行为的差异。

## 你会得到什么

| 阶段 | 目标时间 |
|---|---|
| 确认收到报告 | **3 天内** |
| 初步评估（是否在范围内、严重性） | **7 天内** |
| 确认的凭据泄漏或校验器绕过的修复或缓解 | **30 天内** |

这是一个单人、业余时间维护的项目。如果时间线延误，会明确告知，而不是让你干等。

## 如果你发现了泄漏的凭据

**只需要告诉我们提交哈希和凭据前缀** —— 不要把完整密钥贴进 issue、PR 或公告正文。
我们会轮换它并重写历史。

注意本仓库已经发生过一次这样的事故：四个 provider 的 API key 进入了本地提交，
在任何内容被推送之前，通过重写全部历史清除。这也是为什么本仓库把「重写历史」
视为既定的、可接受的应对手段——**在后一个提交里删掉密钥是不够的**，
因为对象仍可在 packfile 中访问到。

## 支持的版本

目前没有发布 tag；`main` 分支就是受支持的版本。
