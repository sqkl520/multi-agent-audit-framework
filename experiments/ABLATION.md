# 消融实验：到底哪个干预在起作用

**最后更新**：manifest v3.0.0 重算版（2026-11-11）
**数据集**：injected，20 条缺陷（注入 13 + 原生 7）

---

## 先说这一轮改了什么，为什么必须改

之前的分类是错的。错的不是数字，是**分类标准本身**：我用「我记得我注入了什么」来标记注入型/原生型，而 GT-016、GT-018 被标成「base 自带」，实际是注入的。

现在改成机械判定。`verify.mjs` 对每条缺陷跑行为探针，在 base 和 injected 里各跑一遍：

| base | injected | 判定 |
|---|---|---|
| PASS | FAIL | 注入型（injected 独有） |
| FAIL | FAIL | 原生型（base 自带，injected 继承） |
| FAIL | PASS | 器具缺陷（只在 base，不计分） |
| PASS | PASS | 探针无效，manifest 不成立 |

**被审计物是 injected**——实验各组从 `%TEMP%` 拷走的就是它。所以一切计分以 injected 为准。

重算结果：**20 条（注入 13 + 原生 7）**。另有 1 条器具缺陷（GT-022）不计分。GT-019 与 GT-008 是同一行同一条缺陷，已合并。

## 结论 1（最强）：模式 1/2/3 有完美的分离度

这是全部数据里最干净的一条信号，不依赖平均值，也不受批次影响：

**GT-011 / GT-012 / GT-013 三条原生缺陷：**

| 组类型 | 组数 | 命中 GT-011/012/013 |
|---|---|---|
| 自由发挥 | 6 | **0 组** |
| 仅运行时验证 | 1 | **0 组** |
| 模式 1/2/3 | 3 | **3 组，且都是 3/3 全中** |

这三条分别是：

- GT-011 `peek()` 返回内部活引用（模式 1：返回值暴露内部状态）
- GT-012 `remove(id)` 缺 id 校验，与 `enqueue` 不一致（模式 2：同族函数守卫一致）
- GT-013 `capacity` 校验让 NaN 通过（模式 3：数值边界校验）

**七个不给清单的组，一次都没找到；三个给了清单的组，全部找到。** 这不是概率上的差异。

## 结论 2（中）：总 recall 提升 5.8 点

只比较同一批次的组：

| | n | recall 均值 | sd |
|---|---|---|---|
| 自由发挥 | 6 | 70.8% | 8.0 |
| 仅运行时验证 | 1 | 70.0% | — |
| 仅模式 1/2/3 | 3 | **76.7%** | 2.9 |

**+5.8 点，Cohen's d = 0.97**（大效应，但 n 小、区间重叠）。

原生型：15/42 = **35.7%** → 14/21 = **66.7%**，**+31 点**。

**为什么总提升小、原生型提升大**：模式 1/2/3 只能覆盖三类缺陷，在 20 条里占 15%，理论上限就在那里。原生型提升大是因为这三条恰好全落在原生型里。

## 结论 3：运行时验证单独用，等于没有

| 组 | recall | 原生型 | 命中的原生型 |
|---|---|---|---|
| 仅运行时验证 | 70.0% | 3/7 | GT-014, GT-017, GT-020 |
| 自由发挥（6 组均值） | 70.8% | 2.5/7 | — |

**在基线范围之内。** 它命中的三条都是「跑一下就暴露」的：GT-014 超时从不生效、GT-017 文件为 null 就崩、GT-020 空数组抛错。

它**一条 GT-011/012/013 都没找到**——那三条跑正常路径永远不报错。

但也不是一无是处：AB-RUNTIME 的注入型是 10/13，高于模式组的 9/13 均值。**它能发现「行为明显出错」的缺陷，发现不了「想不到要试」的缺陷。两者是不同层面，不是替代关系。**

## 结论 4：模式 4–7 的作用仍然未知

P1/P2/P3 是模式 1–7 全给的组，但它们的审计目录祖先链里有 `base/` 和 `manifest.json`，属于答案泄漏，**不能用来推断模式 4–7 的贡献**。

要回答「模式 4–7 各贡献多少」，需要 4 组单加实验，每组 n≥3 = 12 次运行。**没做。**

---

## 诚实的局限

1. **AB-RUNTIME 只有 n=1**，70.0% 这个数可能只是运气
2. **基线 6 组、模式组 3 组**，样本量不对等
3. **全部实验同一个模型**
4. **原生型只有 7 条**——一条差异就是 14 个百分点
5. **从未测成本**：模式清单让每个 agent 多花多少 token / 时间，没有任何记录
6. **被审计代码只有一份**（fixture1 的 injected）。fixture2 的交叉检验显示模式清单在另一份代码上**降低**了精确率，说明效果依赖代码库特征
7. **precision 不可信**：分母（真实缺陷总数）仍未知。这一轮又发现 4 条漏登记，说明「穷举」这件事我做得并不好。recall 和原生型检出可信，因为分子分母都确定。

## 器具缺陷：base 不能当正确答案用

重算过程中发现 **GT-022**：

```js
// base/src/store.js:4
import { writeFileSync, readFileSync, existsSync, mkdirSync, rmSync } from 'node:fs';
//                                                                  ↑ 没有 renameSync

// base/src/store.js:57
renameSync(tmp, this.#path);
```

**base 的 `JsonStore.set()` 一调用就抛 `ReferenceError`。**

这条为什么重要：

1. **它说明 base 不能作为「无缺陷」的参照物**，任何用 base 做 diff oracle 的审计都是错的
2. **它说明旧版 15 条验证有系统性盲区**——没有一条走过 `set()` 这条写入主路径，所以一直没发现
3. **它是"没用导入却调用"这个模式的一个真实样本**，这个模式值得进清单（模式 8 候选）

injected 里没有这个问题（injected 的 `#persist` 改成了 `rmSync` + `writeFileSync`），所以不计入 recall。
