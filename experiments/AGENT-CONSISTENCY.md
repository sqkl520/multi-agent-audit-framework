# 多 Agent 一致性实测：框架的核心主张站得住吗

**日期**：2026-11-12
**问题**：整个框架建立在「多个独立 agent 审同一份代码，结论会收敛」这个前提上。**这个前提从来没被验证过。**

如果一致性只是「报告都很大所以重叠多」，那么锐评波、Skeptic、Arbiter 的存在理由就站不住——它们只是在给随机噪声投票。

---

## 实验设计

**严格控制组**：4 个独立 agent，**提示词逐字相同**、同一份代码（fixture2，18 条已知缺陷）、隔离目录不同、不给任何模式清单、不给缺陷数量提示。

**为什么必须这样**：之前 12 份报告用了 4 种不同提示词，混在一起算一致性会把提示词差异算成 agent 差异。

---

## 结果：Jaccard 0.742 —— 但这个数会骗人

### 表面数字

| | |
|---|---|
| 全部两两平均 Jaccard | **0.742** |
| 最高一对（C2/C4） | 0.875 |
| 最低一对（C1/C2 等） | 0.688 |

看起来「高度一致」。

### 但必须对照随机基线

一个 agent 平均报 13.5 条（共 18 条），四份报告有 12–15 条。**这么大的报告，随机抽也会重叠很多。**

用超几何期望 `E[|A∩B|] = |A|·|B| / N` 算随机基线，并用蒙特卡洛 20 万次交叉验证：

| | Jaccard |
|---|---|
| **实际** | **0.742** |
| **随机（同样大小的随机抽样）** | **0.598** |
| 理论上限（两者都精确时最多能重合多少） | 0.867 |

**实际一致性只比随机高 1.25 倍。**

蒙特卡洛验证：20 万次随机采样得到 0.5981，解析式给出 0.5950，逐对计算 0.5945。**三条路径吻合，基线可信。**

### 达成度：86%

「达成度」= 实际 Jaccard / 理论上限 Jaccard。上限是 `min(|A|,|B|) / max(|A|,|B|)`——即使两个 agent 都只报真缺陷且完全不误报，它们最多也只能重合这么多。

**86% 的达成度意味着：两个 agent 各自找到的那批缺陷，大部分是同一批。**

这是支持「有共识」的一面。但对比随机只有 1.25 倍，是反对的一面。

**两个数字都对，只是回答不同的问题：**
- 达成度高 → 它们**倾向于找到同一批**东西
- 相对随机倍数低 → 但这个「同一批」在**数量这么多的情况下本来就会重合**

## 更细的视角：哪些缺陷是共识，哪些是噪音

每条缺陷被几个 agent 找到（4 个 agent）：

| 检出数 | 缺陷 | 说明 |
|---|---|---|
| **4/4** | F2-01, F2-05, F2-06, F2-07, F2-09, F2-12, F2-15, F2-18, F2-20 | **9 条真共识**（50%） |
| 3/4 | F2-10, F2-13, F2-17, F2-21 | 4 条（22%） |
| **2/4** | F2-14, F2-16, F2-19 | **3 条不稳定**（17%） |
| 0/4 | F2-11, F2-22 | 2 条全员遗漏 |

**有 9 条缺陷，4 个独立 agent 全部找到。** 这需要验证是不是随机也能做到：

用 10 万次蒙特卡洛，让 4 个 agent 各随机抽 12/15/12/15 条（共 18 条），统计「几个缺陷被全部 4 个抽中」：

| | 全中条数 |
|---|---|
| 随机，10 万次均值 | **5.56** |
| 随机，95 分位 | 8 |
| 随机，最大值 | 11 |
| 随机，出现 ≥9 条的概率 | **0.68%** |
| **实测** | **9** |

**所以 9 条全中确实超出随机水平（约 1.6 倍），但并不夸张**——随机平均就有 5.56 条全中，因为报告太大了。

**但也有 3 条只有 2/4 找到**，其中包括 F2-16（`renderListView` 对 `options` 不校验）——这是个 HIGH 级别的真实缺陷。

---

## 三个层次的结论

### 1. 共识确实存在，但比「看起来」弱得多

- **9/18（50%）是 4/4 全中**，随机基线是 5.56 条 → **约 1.6 倍**
- Jaccard 0.742 vs 随机 0.598 → **只有 1.25 倍**
- **有 2 条是 0/4（全员遗漏）**

三个指标都指向「有共识但幅度不大」。

**我最初在文档里写「没有一条是 0/4」——那是错的，而且错得很有代表性。**

当时我只统计了 agent 报过的缺陷求交并集，于是「谁都没报的」自然不在里面。这是**循环论证**：用「被报出来的条目」判断「有没有漏报」。

按完整真值集（18 条）重算：

| 缺陷 | 检出 |
|---|---|
| F2-22（`{{#if constructor}}` 恒真） | **0/4** |
| F2-11（`slice` 浅拷贝污染源数组） | **0/4** |

**4 个独立 agent 全部漏掉了 F2-22 和 F2-11。**

这一条的检出率在多轮历史里也一直很低（12 份历史报告里只有 2 次）。它是个真缺陷，base 里也有，但没人自然想到要去测「字段名恰好是原型链成员」。

**这条对框架有利**：它证明「多派几个 agent」确实补不上某些系统性盲区——那需要**专门去查**（正是模式 4a 想做的事）。

### 2. 分歧主要集中在少数缺陷上

3 条只被 2/4 找到，2 条 0/4。这些是**框架该标记为「需要复核」的**，而不是简单多数表决。

**没有任何一条缺陷是「只有一个 agent 找到」**——所有被找到的，至少 2 个 agent 独立发现。这是个好信号：没有哪个 agent 在报别人完全看不见的东西（那更可能是幻觉）。

反过来说，**否决一个只被 2/4 提出的发现是危险的**——F2-16 就是个 HIGH 级真缺陷，只被一半看到。

### 3. 「一致性高」这个说法必须带基线

**这是最重要的方法学教训**：Jaccard 0.742 单独看像是「高度一致」，加上随机基线（0.598）之后，增益只有 1.25 倍。

**任何报「agent 之间一致性 X%」的实验，如果不报随机基线，那个数字没有意义。** 报告越大、代码里缺陷越多，随机重叠越高。

## 这对框架意味着什么

### 锐评波（Skeptic / Arbiter）的价值被部分证实

9/18 的 4/4 共识说明：**多个 agent 确实会独立地收敛到同一批结论**。这部分是真的（相对随机 1.6 倍）。

但同时，3/18 的 2/4 分歧 + 1/18 的 0/4 说明：**如果只靠多数表决，会漏掉一半。**

**所以锐评波不该做「多数决」，该做「分歧标记」。** 一个只被 1–2 个 agent 提出的发现，不该被投票否决——恰恰相反，它是**最需要人看**的，因为那是真正有信息差的地方。

**而 0/4 的那条（F2-22）连分歧标记都救不了**——所有 agent 都没提，锐评波没有东西可评。这类只能靠**预先写死的检查清单**（模式 4a 的「原型链键名」）来兜。

**这给框架一个清晰的结论**：

| 情形 | 靠什么解决 |
|---|---|
| 多数 agent 都找到 | 不需要额外机制 |
| 只有 1–2 个找到 | **分歧标记 + 人工复核**（锐评波该做这个） |
| 0 个找到 | **只能靠清单**（多 agent 无效） |

### 「多 agent 一定比单 agent 强」这个假设不成立

| | 命中 |
|---|---|
| C1 | 12/18 |
| C2 | **15/18** |
| C3 | 12/18 |
| C4 | **15/18** |
| **4 个并集** | **16/18（88.9%）** |

**并集只比最好的单个 agent 多 1 条。** 四个 agent 合起来几乎没超过最好的那个——这个规模下并行审同一份代码的边际收益很低。

（并集漏的 5 条里，F2-02/03/04 是已撤下的、F2-08 是器具缺陷，**只有 F2-11 是真缺陷**。所以按真实可检缺陷算，并集是 16/17。）

### 但并集确实更稳

单个 agent 成绩在 12–15 之间波动（sd ≈ 1.5）。并集 16。

**没有哪个 agent 找到别人完全找不到的独特东西**——最多是「有人漏了某条，别人补上」。这说明分歧的来源是**覆盖遗漏**，不是**视角差异**。

如果分歧来自视角差异（不同 agent 关注不同维度），并集应该远大于最好的单个。实测不是。**这条对框架不利**：它意味着多派 agent 主要是在对抗随机遗漏，而不是在获得互补视角。

## 诚实的局限

1. **n=4，只有一组**。4 个 agent 跑一次，不能排除这一组特别巧
2. **同一模型**。换模型可能一致性更低（也可能更高），完全没测
3. **只有一份代码**（fixture2，18 条缺陷）。fixture1 有 20 条，没做同样的实验
4. **提示词是「自由发挥」**。给了模式清单后一致性是否会提高，没测
5. **「达成度」这个概念是我自己定义的**，没有在文献里见过，读者应审慎对待
6. **Jaccard 忽略了严重性**。两个 agent 报同一条缺陷但一个说 HIGH 一个说 LOW，在 Jaccard 里算完全一致

第 6 条值得单说：**这轮完全没看「定级一致性」**。而严重性分歧在实际审计里可能比「找没找到」更重要。

**`tools/consistency.mjs` 的输出格式**：

```
实际 Jaccard   0.742
随机基线       0.595
相对随机       1.25x   ← 这个数才是「有没有共识」的答案
理论上限       0.867
达成度         86%
```

**为什么必须带基线**：这个工具的 14 个自测里有一条专门钉住这件事——「报告占满真值集时，Jaccard 必然 = 1，但那是没得选，不是有共识，此时倍数必须 = 1」。

## 我在这一轮犯的三个错

### ① 用报告的并集判断「有没有漏报」（循环论证）

第一次统计时我写「没有一条缺陷是 0/4 检出」。那是因为我只取了所有 agent 报过的缺陷求交集——**谁都没报的，自然不在里面**。

用完整真值集（18 条）重算后：**F2-11 和 F2-22 都是 0/4**。

用「被报出来的条目」判断「有没有漏报」，是这次最典型的错误。

### ② manifest 的 id 不连续，按 `F2-01..F2-18` 生成真值集会算错

fixture2 的缺陷 id 有跳跃（F2-02/03/04 已撤下、F2-08 是器具缺陷）。我按序号生成 18 个 id 去统计，得到「0/4 有 5 条」，把已撤下的也算进去了。

必须从 `manifest.json` 读真实 id。

### ③ 自测阈值定得太死

写「倍数应接近 1」时把阈值定成 `< 1.5`，而实际值是 1.75——那不是 bug，是我的预期错了。改成 `< 2`。

**三次错误里，两次是「我拿了一个方便的集合当成真值集」，一次是「把预期当成了事实」。** 共同点：都是我想要的结论跑在了验证前面。
