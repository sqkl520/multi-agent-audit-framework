# base 不干净：4 条缺陷在基准版本里就有

**日期**：2026-11-10（重建后验证发现）

---

## 事实

双向验证（base 通过 + injected 失败）只通过了 **11/15**。剩下 4 条在 base 里也存在：

| ID | 缺陷 | 在 base 里? |
|---|---|---|
| GT-011 | `peek()` 返回内部活引用 | **是** |
| GT-012 | `remove(id)` 缺 id 校验 | **是** |
| GT-013 | `capacity` 校验让 NaN/Infinity/小数通过 | **是** |
| GT-014 | `timeoutMs` 从未被用作超时 | **是** |

---

## 为什么会这样

**第一次建 base 时**：我手写了它，跑 22 项测试全过。但测试只覆盖了「我想到的行为」，没覆盖这四个。

**重建 base 时**：从 `injected` 反推（撤掉注入）。而反推动作只能撤掉**注入的那部分**——GT-011/012/013/014 从来没被注入过，所以反推后依然存在。

---

## 这改变了什么

### 1. 「base = 完全正确」这个前提是错的

我原本的设计（`DESIGN.md` §1.1）：

> 先写一份**完全正确**的代码，验证它确实没有缺陷，**然后**注入 N 条缺陷。

实际执行时，`base` 只是「**没有我注入的缺陷**」。它还有 4 条我没发现的问题。

### 2. 但这未必是坏事

这 4 条缺陷变成了**额外的测试点**：

- 它们是真实的、非注入的缺陷
- 如果审查员能发现它们，说明能力是真的（不是被注入模式引导的）
- 如果发现不了，说明方法确实漏这类

**而且它们恰好覆盖了我原本缺失的类别**：
- GT-011/014 = 缺失型（返回值未防御、能力整块缺失）
- GT-012 = 同类不同守卫
- GT-013 = 边界值校验不全

### 3. 打分时要分层看

| 类别 | 条数 | 说明 |
|---|---|---|
| **注入型**（可双向验证） | 11 | 我造进去的 |
| **原生型**（base 自带） | 4 | 我写 base 时无意留下的 |

**两类的 recall 要分开报**——前者测「框架能不能找到已知的注入缺陷」，后者测「能不能找到没人告诉它的真实缺陷」。

后者更接近真实场景。

---

## 待办

1. **给这 4 条补 proof**：不能双向验证，改用「在 base 上也能复现」的单向证明
2. **重新设计 base**：如果要严谨的「完全正确」基准，需要先修掉这 4 条，再重新注入
3. **但先别做**——现在这 4 条是宝贵的真实缺陷样本，修掉就没了

---

## 一个可推广的教训

**「我验证过了」和「它是对的」是两件事。**

我的 base 通过了 22 项测试，其中没有一项覆盖 `peek()` 会不会返回内部引用——因为**我没想到要测这个**。

测试只能证明「测到的都对」，不能证明「没有没测到的错」。这和审计框架本身面对的问题是同一个。
