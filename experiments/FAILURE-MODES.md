# 失败模式清单：AI 察觉不到 agent 已经做完的五种情形

**日期**：2026-11-12
**来源**：全部来自这次会话的实际踩坑，不是设想出来的。

---

## 一个总纲

这五种情形的共同点：**判据和「任务成功」不是同一个东西。**

| 情形 | 我用的判据 | 真实判据 | 后果 |
|---|---|---|---|
| 1 | JSONL 转录大小 | 产物文件存在 | 误差 35 分钟 |
| 2 | `in_flight` 数组长度 | 产物是否落盘 | 账本忘了更新就一直等 |
| 3 | 转录 0 字节 = 没跑 | 工作目录有没有文件 | 22 个 agent 被误判 |
| 4 | 未遇到 | — | — |
| 5 | 未遇到 | — | — |

---

## 情形 1：拿「转录文件大小」当进度

**实测**：一个 agent 2022-11-12 21:49 启动，22:39 写完产物（40 KB）。而它的 JSONL 转录文件从启动起**一直是 0 字节**。我据此连续说了 35 分钟「它还在跑」。

**根因**：JSONL 转录记录的是会话对话，产物写在各自的工作目录。**两者完全独立。**

**已修**：`tools/agent-status.mjs` —— 四态判定，优先级严格按「产物存在 > 工作目录活动」：

| 优先级 | 判据 | 结论 |
|---|---|---|
| 1 | 产物存在且非空 | `DONE`，不要再等 |
| 2 | 产物没出但工作目录近期有活动 | `RUNNING` |
| 3 | 产物没出且工作目录也久没动 | `STALLED`，别干等 |

11 个测试用例，其中 case 5 专门钉住优先级：**产物已在，即使工作目录很旧也必须判 DONE**。

---

## 情形 2：`stop-hook` 只数 `in_flight` 数组长度

**问题**：`in_flight` 是主 Agent **自己维护**的。它忘了把已完成的 agent 移出去，`stop-hook` 就一直认为「还在飞」——和情形 1 是同一个错的两种表现。

**已修**：按 `artifact_path` 是否落盘判定。产物已在 → 提示「账本没跟上」，不再说「还在飞」。2 个新测试固定这个区别。

---

## 情形 3：转录 0 字节 = 判定「它没跑」

**实测**：本次会话 80 个子 Agent，**22 个（27.5%）转录是 0 字节**。

我多次据此认为它们「没启动 / 挂了」。核查发现：用过的 8 个 scratch 目录里**全都有文件**（4–10 个），包括那些转录同为 0 的。

**根因**：转录大小对某些 harness / 派发方式是**恒 0** 的，它根本不含「有没有干活」的信息。

**已修**：`tools/scan-agent-outcomes.mjs` —— 把「转录大小」和「工作目录文件数」当作**两个独立事实**并列，不拿一个冒充另一个。

关键设计：**`scratchFiles: null`（不知道）和 `0`（确认空）必须分开。**

| 转录 | 工作目录 | 判定 |
|---|---|---|
| 0 | 有文件 | `WORKED_SILENTLY` ← 核心用例 |
| 0 | 确认空 | `NEVER_STARTED` |
| 0 | **未知** | **`UNKNOWN`** ← 不许说「没跑」 |

7 个测试用例，其中一个专门断言「0 和 null 判出的结局必须不同」。

**跑真实数据的输出**：

```
扫描 80 个子 Agent（工作目录已知 0 个 / 80）
  TRANSCRIBED_WORK_UNKNOWN  58  72.5%
  UNKNOWN                   22  27.5%

转录为 0 字节的: 22 / 80（27.5%）
  ⚠ 这些 agent 的工作目录都未知——不能据此说它们没跑。
```

**它宁可报 UNKNOWN 也不猜。**

## 情形 4 和 5：我查过了，没有实际发生

上一轮我提过两类：「agent 报了错但我没看见」「agent 产出但我理解错了」。**这次专门去查，没找到真实实例。**

- 对唯一一份完全合规的产物逐条核对 9 条发现，**内容都是对的**（包括我一开始以为「没匹配上真值」的那条——它比我的真值表更准，是我把行号标在了 118，它标 112）
- 22 个 0 字节转录的 agent，没有发现「报了错但被忽略」的证据

**所以不写工具。** 没发生过的失败模式，凭空造一个检测器，大概率是错的。

---

## 一个反复出现的元问题

这五种情形里，真正被修好的（1、2、3）都是同一个模式：

> **我用了一个「看起来相关」的指标，替代了「真正定义成功」的那个。**

而两次差点犯的错（都发生在同一天）：

- 把 `check-all` 的 `exit=143` 当成测试失败 —— 实际是我的 `timeout` 杀了子进程
- 把 G0 的 FAIL 当成规则生效 —— 实际是规则误伤了正确产物

**共同点：结论跑在了验证前面。**

机械检查能防的，是「指标取错」这一类（情形 1、2、3 都是）。但「看到红灯就以为有火」这一类，机械检查防不了——**那需要在下结论前先看一眼原始数据**。
