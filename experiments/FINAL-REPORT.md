# 多智能体审计框架：实证研究总报告

**日期**：2026-11-11
**目的**：回答一个此前从未被回答的问题——**这套框架里哪些规则真的有用？**

---

## 一句话总结

**19 条规则里，只有 1 类干预经对照实验证实有效（模式 1/2/3），另有 2 条被证实有害或无效，还有 5 条至今没有任何有效数据。**

最强的证据不是平均值，是**完美分离**：GT-011/012/013 这三条原生缺陷，7 个不给清单的组（6 组自由发挥 + 1 组运行时）**全部 0 命中**，3 个给了模式 1/2/3 的组**全部 3/3 命中**。

---

## 1. 实验方法

### 1.1 为什么要做这个

框架有 9000+ 行规则、19 条静态检查。但 CRITIC-11 指出：

> 支持 8662 行规则的全部实证证据，来源是 1 个仓库、4 个实验、约 30 次 Agent 派发、n=3 到 n=6 的样本，其中「13/13 CONFIRMED」这类核心数字**没有对照组、没有负样本、没有 ground truth**。

**所以造 ground truth，做对照实验。**

### 1.2 数据集

| fixture | 领域 | 缺陷数 | 注入型 | 原生型 |
|---|---|---|---|---|
| fixture1 | 任务队列 / 重试 / JSON store / 并发池 | **21** | 11 | **10** |
| fixture2 | 模板引擎 / 事件总线 / 分页 / 校验器 | 8 | 5 | 3 |

**「原生型」是我写基准代码时无意留下的缺陷**，比注入型更接近真实场景。

**验证**：`node verify.mjs` → 20 条缺陷全部按行为探针分类验证，21/21 一致（含 1 条器具缺陷）。

### 1.3 判分

```bash
node score.mjs <报告> [--manifest <清单>]
```

- 命中 = 文件匹配 + 行号 ±3（支持行范围 `:51-57`）
- 会分层报「注入型 / 原生型」

### 1.4 隔离

**每次实验前必须做泄题检查。** 这个错误犯了两次：

1. `base/` 和 `injected/` 同级 → D 组引用了 base 做 diff
2. `manifest.json` 在被审目录的父目录 → F 组明确说它找到了

已写成 `setup-run.mjs`：从被审目录向上遍历到根，命中答案类文件即中止。

## 2. 实验矩阵

**全部数字已按 manifest v3.0.0（机械分类）重算。**

| 实验 | 干预 | 组数 | recall | 原生型 |
|---|---|---|---|---|
| 基线 | 无 | 6 | 70.8% | 35.7%（15/42） |
| **消融：仅模式 1/2/3** | 模式 1/2/3 | **3** | **76.7%** | **66.7%（14/21）** |
| **消融：仅运行时** | 运行时验证 | 1 | 70.0% | 42.9%（3/7） |
| 模式 1–7 | 1–7 | 3 | 91.7% | 81.0% — **作废**，见下方泄漏说明 |
| fixture2 交叉验证 | 模式清单 / 无 | 各 1 | 100% / 100% | 3/3 / 3/3 |

> **模式 1–7 那三组（P1/P2/P3）的审计目录祖先链里有 `base/` 和 `manifest.json`，属答案泄漏，不能用来推断模式 4–7 的贡献。** 表中数字仅备查。

## 3. 结论

### 3.1 被证实有效的（1 条，但证据最强）

**模式 1/2/3**：返回值暴露内部状态 / 同族守卫一致性 / NaN 边界。

**最强的一条证据不是平均值，是完美分离：**

| 组类型 | 组数 | 命中 GT-011/012/013 |
|---|---|---|
| 自由发挥 | 6 | **0 组** |
| 仅运行时验证 | 1 | **0 组** |
| 模式 1/2/3 | 3 | **3 组，全部 3/3** |

这三条原生缺陷，七个不给清单的组一次都没找到；三个给了清单的组全部找到。**这不是概率差异。**

原生型检出率：35.7% → 66.7%，**+31 点**。

### 3.2 被证实有害或无效的（2 条）

**① 「运行时验证必须调用公开 API 主路径」**

- 两次实验支持降级：强制要求的组 recall 70.6%，比自由发挥还低
- 已降级为建议，`main_path` 从硬性必填降为 WARN

**② 「缺失型缺陷 = 承诺 vs 实现」**

原本的依据（GT-014 `Object.freeze`）**是错的**——GT-014 六组里四组都命中了。真正的零命中是 GT-011/012/013。

已改写依据。

### 3.3 未验证的（4 条）

模式 4/5/6/7（解析形状 / 能力实现 / 转义顺序 / 边界符号）。

**唯一支持它们的证据（P1/P2/P3 的 91.7%）因答案泄漏作废。所以现在这四条没有任何对照实验数据。** 要补，需要 4 组单加实验、每组 n≥3，共 12 次运行。没做。

**模式 8（引用的绑定是否存在）** 是这一轮新加的，有一个真实样本（GT-022，base 的 `store.js` 调用未导入的 `renameSync`），但同样没有对照实验。

### 3.4 一个重要的负面发现

**在 fixture2 上，七模式清单完全没有增益**：

| 组 | recall | precision |
|---|---|---|
| 有清单 | 100% | 47.1% |
| 无清单 | 100% | **88.9%** |

**我不知道边界在哪。** 最可能的解释（推测）：清单的价值是提醒 agent 去查它**本来想不到**的地方。fixture1 的「同族守卫」「NaN 边界」是非直觉的；fixture2 的「转义顺序」「XSS」是常识。

## 4. 工具的实际能力

| 工具 | 测试 | 真实能力 |
|---|---|---|
| `check-promises.mjs` | 12 | 只查 JSDoc 明写的三类，散文里的承诺看不到 |
| `check-blindspots.mjs` | 9 + B4 | B1/B2/B3 只认 fixture1 的三种形态（fixture2 上 0 命中）；**B4（调用未导入的名字）在 base 上精确命中 1/1、另两份代码上 0 误报** |
| `stop-hook.mjs` | 12 | 相位未闭合就拒绝结束回合 |
| `lint-autonomy.mjs` | 12 | 19 条静态检查，每条做过故障注入验证 |
| `verify.mjs` | 21 | 用行为探针判定每条缺陷归属（注入/原生/器具/不存在），并做双向验证 + manifest 覆盖检查 |

**`check-blindspots` 已在输出里加了明确警告**：未命中 ≠ 没有缺陷。

**B4 是唯一一个跨代码库通用的规则**——「调用了作用域里不存在的名字」不依赖任何代码库特有的形态。它现在只在一个样本上验证过（GT-022），但那个样本是真实的：base 的 `store.js` 调用 `renameSync` 却没导入，整个写入路径 100% 失效，而旁边 15 条验证脚本没一条走过那条路径。

## 5. 我犯的错（方法论层面）

| 错误 | 后果 | 已修正 |
|---|---|---|
| 从单个案例过度归纳 | 把「专门派 agent 查某类」当成「加一条规则有效」 | ✓ |
| 先改框架后做验证 | §4.5.0 写进框架后才发现有害 | ✓ |
| 答案表放在考场上（两次） | E/F 两组作废，P1/P2/P3 的 91.7% 也作废 | ✓ 写成脚本 |
| 测试判据本身没验证 | `verify.mjs` 里的正则转义失效，导致假通过 | ✓ |
| 用 n=1 下结论 | AB 消融实验只有一组 | 补重复实验 |
| **拿「我记得注入了什么」当分类依据** | GT-016/GT-018 被误标为原生型；GT-019 与 GT-008 重复登记 | ✓ 改实测判定 |
| **把实现方式当成缺陷** | 4 条探针用「源码里有没有某段文字」判定，别人换个写法就误判 | ✓ 全改行为探针 |
| **误以为 base 是干净的** | fixture1 的 base 里 `set()` 一调用就崩；fixture2 的 base 自带 **6 条**缺陷 | 记为器具缺陷，加 B4 规则 |
| **以为 ground truth 是「我记得的那几条」** | fixture2 数据集从 8 → 7 → 14 条，补了两次 | 见下 |

**最根本的一条**：我之前的每一条规则，依据都是「某个 agent 发现了某个东西」，**没有一条做过对照**。

**第二根本的一条（也是最严重的一条）**：ground truth 本身是我想出来的，不是测出来的。

| 数据集 | 最初 | 现在 | 补了几次 |
|---|---|---|---|
| fixture1 | 20 条设计 | **20 条**（注入 13 + 原生 7） | 4 次 |
| fixture2 | 8 条 | **14 条**（注入 4 + 原生 10） | 2 次 |

**每次都一样**：某个 agent 报了我没登记的缺陷，我核实后确认是真的；或者某个 agent 报的东西我以为是误报，一测发现它是对的。

**这带来的后果不是数字不准，而是结论会反转：**

| 结论 | 旧数据集 | 补全后 |
|---|---|---|
| 清单在 fixture2 上有效吗 | 无差异，precision 更差 | **recall +21.4 点**，precision −24.2 |
| 「清单效果依赖代码库特征」 | 成立 | **不成立**，两份 fixture 方向一致 |

**所以：**

| 指标 | 可信吗 | 为什么 |
|---|---|---|
| recall | **相对可信** | 分子分母都经过行为验证，但分母仍在增长 |
| 原生型检出 | **相对可信** | 同上 |
| **precision** | **不可信** | 分母（真实缺陷总数）未知。上一轮「precision 88.9%」的组，在补全数据集后掉到 78.6% recall——那些"误报"里混着真的 |
| **任何两组之间的差异** | **要打折看** | 数据集每补一次，差异就变一次 |

## 6. 还没回答的问题

1. **模式 4/5/6/7 各自贡献多少**——已做完，见 `SINGLE-PATTERN.md`：4 组 × 3 轮。结论是 P7 最稳（sd 3.2）、P6 最准（目标 2/2）、P4 波动最大（sd 16.8，须拆成 4 个子问题）、P5 目标不稳定但副作用最大（该当追问方向而非检查项）
2. **模式 8（B4）在别的代码库上有效吗**——只有 1 个样本
3. **成本**——模式清单让每个 agent 多花多少 token / 时间，完全没测
4. **换模型**——全部实验都是同一个模型
5. **precision 怎么才能可信**——需要一个独立的缺陷穷举方法，而不是靠「我又想起来一条」
6. **「注意力重新分配」这个解释能推广吗**——在模式清单上成立（原生型 +31、注入型 −7.7），在运行时规则上不成立（两类都降约 5 点，无定向）。两个干预的失效方式不同，不能用一个机制解释

## 7. 单模式消融：模式 4/5/6/7 各值多少

在 fixture2（18 条缺陷）上跑了 4 组 × 3 轮。完整数据见 `SINGLE-PATTERN.md`。

| 组 | recall 均值 | sd | 目标缺陷三轮都中 |
|---|---|---|---|
| P4 形状 | 64.8% | **16.8** | 4/8 |
| P5 能力 | **72.2%** | 9.6 | **0/1** |
| P6 转义 | 27.8% | 14.6 | **2/2** |
| P7 符号 | 53.7% | **3.2** | **3/3** |

**按 recall 排：P5 > P4 > P7 > P6。按目标命中稳定性排：P6 = P7 > P4 > P5。完全相反。**

**该信后者。** recall 会被「追着一条线索发现的邻居问题」抬高，而目标命中稳定性才说明这个模式给了之后是否**可复现**。

三条对框架的改动：

1. **模式 4 拆成 4a/4b/4c/4d**（原型链键名 / 假值 vs 缺值 / 数值边界 / 嵌套结构），4 个子问题各自给结论。sd 16.8 说明「笼统地问一句」时 agent 会挑容易的做。
2. **模式 5 从检查项降为「追问方向」**。它目标命中 0/3 稳定，但总 recall 最高——因为它的价值是启动搜索链，不是找到某个东西。写成 checklist 会让 agent 对着一处发呆。
3. **模式 6、7 标为「已证实」**，和 1/2/3 同级。

**现在「已证实可靠」的有 5 条：1、2、3、6、7。**

## 8. 这一轮最该记住的方法论

数据集补全的过程本身是一个结果：

| 数据集 | 最初 | 现在 | 补了几次 | 结论反转过吗 |
|---|---|---|---|---|
| fixture1 | 20 条设计 | 20 条 | 4 次 | 是（分类错了） |
| fixture2 | 8 条 | 14 条 | 2 次 | **是（清单从「无效」变成「显著有效」）** |

**每一次补全都来自同一个动作：怀疑某个「误报」其实是真的，然后去实测。**

**所以我给后来者的建议只有一条**：在相信任何一个 recall/precision 数字之前，先把被打分器标成「误报」的条目逐条实测一遍。那不是误报，那是**考卷漏了的题**。

这个动作在 fixture2 上做了 3 次，发现了 7 条真缺陷，其中一条（F2-12 `emit` 吞掉所有单个监听器的错误）是 HIGH 级。
