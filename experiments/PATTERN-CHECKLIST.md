# 必查模式清单：实测效果与边界

**最后更新**：manifest v3.0.0 机械分类后重算

---

## 先说结论，以及这个结论被削弱过一次

**最初的说法**：「给出必查清单，recall 从 74.5% 提升到 98.0%，原生型从 42% 提升到 94.4%。」

**这个说法现在不成立了。** 原因有两个：

1. P1/P2/P3 那三组的审计目录祖先链里有 `base/` 和 `manifest.json`，属**答案泄漏**，结果作废
2. 缺陷分类之前靠我记忆，GT-016/GT-018 被误标成原生型，GT-019 与 GT-008 重复登记

**重算后的结论**：

| | n | recall | 原生型 |
|---|---|---|---|
| 自由发挥 | 6 | 70.8% | 15/42 = 35.7% |
| 仅运行时验证 | 1 | 70.0% | 3/7 = 42.9% |
| **仅模式 1/2/3** | 3 | **76.7%** | **14/21 = 66.7%** |

**recall +5.8 点，原生型 +31 点。**

## 但有一条证据比平均值强得多

**完美分离**：

| 组类型 | 组数 | 命中 GT-011 / GT-012 / GT-013 |
|---|---|---|
| 自由发挥 | 6 | **0 组** |
| 仅运行时验证 | 1 | **0 组** |
| 仅模式 1/2/3 | 3 | **3 组，全部 3/3** |

这三条原生缺陷分别是：

- **GT-011** `peek()` 返回队列内部活引用 → 模式 1（返回值是否暴露内部状态）
- **GT-012** `remove(id)` 缺 id 校验，与 `enqueue` 不一致 → 模式 2（同族函数守卫一致）
- **GT-013** `capacity` 校验让 `NaN` 通过 → 模式 3（数值边界）

**七个不给清单的组，一次都没找到；三个给了清单的组，全部找到。** 平均值会被别的因素淹没，这个分离不会。

## 五个模式是什么（现已扩到 8 个）

```
1. 返回值是否暴露内部状态
   函数返回的对象/数组，是不是内部容器的同一个引用？
   调用方改了会不会反过来影响内部状态？

2. 同族函数的守卫是否一致
   同一个类里做同类事的多个方法，参数校验是否一致？
   为什么 enqueue 校验了 id，remove 不校验？

3. 数值边界是否完整
   「必须是正整数」的校验，排除了 NaN / Infinity / 小数吗？
   注意 typeof NaN === 'number' 且 NaN <= 0 为 false

4. 解析结果是否校验形状（未单独验证）
5. 能力是否真的实现了（未单独验证）
6. 转义/编码的顺序对不对（未单独验证）
7. 边界值的符号处理（未单独验证）
8. 引用的绑定是否存在（有一个真实样本，未做对照实验）
   调用的名字在这个作用域里真的存在吗？
   import 漏了某个名字，函数体照用不误，模块加载不报错，一调用就 ReferenceError
```

## 边界：另一份代码库上同样有效（但精确率下降）

| 代码库 | 有清单 | 无清单 |
|---|---|---|
| fixture1（队列/重试/store，20 条缺陷） | 76.7% | 70.8% |
| fixture2（模板/事件/分页/校验，14 条缺陷） | **100%** | 78.6% |

| 代码库 | recall 变化 | precision 变化 |
|---|---|---|
| fixture1 | +5.8 | — |
| fixture2 | **+21.4** | **−24.2** |

> **这条结论反转过一次。**
>
> 早期写的是「fixture2 上 recall 没有提升，precision 反而降了 42 个百分点」，据此判断「清单的价值依赖代码库特征」。
>
> **那个判断是数据集不完整造成的。** fixture2 当时只登记了 7 条缺陷，两组都找全了，看起来「无差异」；补到 14 条后，无清单组只找到 11 条，有清单组找到全部 14 条。
>
> **precision 下降的大部分不是误报**——补进 manifest 的 7 条里有 6 条正是从「未匹配的发现」里捞出来的。分母错了，精确率就没有意义。

**所以现在的判断**：清单在两份 fixture 上都提升 recall，代价是精确率。在审计场景里漏报比误报危险，这个交换通常是值得的——但要知道自己在换什么。

## 这个结论的局限

1. **模式组 n=3 vs 基线 n=6**，样本量不对等
2. **原生型只有 7 条**（fixture1）——一条差异就是 14 个百分点
3. **同一模型、同一份代码**
4. **没测成本**：清单让每个 agent 多花多少 token / 时间，一次都没记录
5. **模式 4–7 的数据刚刚才开始有**，见 `SINGLE-PATTERN.md`
6. **模式 8 只有 1 个样本**
7. **precision 仍然不可信**：分母（真实缺陷总数）每补一次就变一次。fixture2 从 8 → 7 → 14 条，第三次补完后 precision 数字全部作废重算

## 清单到底在帮什么：一个更强的解释

把全量数据按缺陷类型拆开看（fixture1，10 组）：

| 组类 | 注入型 | 原生型 |
|---|---|---|
| 自由发挥（6 组） | **70/78 = 89.7%** | 15/42 = **35.7%** |
| 模式 1/2/3（3 组） | **32/39 = 82.1%** | 14/21 = **66.7%** |
| 仅运行时（1 组） | 11/13 = 84.6% | 3/7 = 42.9% |

**清单让原生型 +31 点，同时让注入型 −7.6 点。**

这不是「加了什么」，是**注意力被重新分配**：模式清单把注意力从「显然坏掉的行为」拉向「看起来正常但有问题的代码」。前者本来就会被抓到，后者需要刻意去找。

**这也解释了为什么 fixture2 的增益更大**：它 14 条里有 10 条是原生型（71%），fixture1 只有 7 条（35%）。原生型占比越高，清单越划算。

**验证**：按这个解释，清单组在 fixture2 的注入型上应该没有提升。实测 T1（有清单）4/4，U1（无清单）4/4 —— **零提升，符合预期**。

但要注意 fixture2 只有 2 组，且注入型本来就只有 4 条（两组都全中），**这条验证的证据强度很弱**。

### 一个可预测的模型

如果上面的解释成立，那么清单的净收益应该可以由缺陷类型配比算出来：

```
净效应 = 31.0 × (原生型占比) − 7.7 × (注入型占比)
```

| 数据集 | 原生型占比 | 模型预测 | 实测 |
|---|---|---|---|
| fixture1 | 7/20 = 35% | **+5.8 点** | **+5.8 点** |
| fixture2 | 10/14 = 71% | **+19.5 点** | **+21.4 点** |

**两个数据点都落在预测值 2 个点以内。**

**但这个模型不能当成结论**：
- 系数 31.0 和 −7.7 是**从这两个数据集里拟合出来的**，只有两个数据点，拟合两个参数等于没有约束
- 它最多算一个事后描述，不是预测
- 要验证它，需要在**第三个**原生型占比不同的数据集上盲测

**它的价值在于给出一个可证伪的形式**：如果将来在原生型占比 50% 的代码库上测，应该看到 +11.7 点左右。偏离太远就说明这个解释是错的。
