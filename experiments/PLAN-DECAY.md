# 为什么模型「越到后面越不列计划」——本地实测 + 文献

**日期**：2026-11-12
**方法**：一边派 agent 上网查，一边用本机 347 个真实会话记录做统计。两条线独立进行，结论互相校验。

---

## 先说结论

**你观察到的现象存在，但它的主因不是「模型越跑越懒」。**

本机数据里，TodoWrite 的调用分布呈**两极分化**，而不是单调衰减：

- 一部分会话：**开头连列几次，中段某个点之后再也不列**（`ba24adc3` 最后一次在 50% 处，`aed8ec22` 在 71% 处）
- 另一部分会话：**前面完全不用，后段才突然开始用**（`ea338c0e` 前 66% 零调用，后 34% 用了 6 次）

而且触发 todo 的**不是会话进度，是「离上次人类输入过了多久」**。见下面第 2 节。

---

## 1. 本机数据的基本盘（这是个意外发现）

扫了 `~/.claude/projects/` 下 **347 个会话文件**：

| | |
|---|---|
| 提到过 `"TodoWrite"` 的文件 | **14 个** |
| 真正有 `tool_use: TodoWrite` 的会话 | **5 个**（全在同一个项目里） |
| 全部真实调用次数 | **82 次** |

**本会话（`a122e6cc`，5880 轮）一次 TodoWrite 都没调过**，只在文本里提到了 15 次。

> 这意味着：本机的 Claude Code 环境里，TodoWrite **不是默认会用的工具**。截图里那种 plan 列表在这个环境里根本不产生。
>
> 所以「为什么越到后面越不列 plan」这个问题，在**本机数据上无法直接回答**——样本只有 5 个会话，且集中在一个项目。下面的分析基于这 5 个，结论只能说「在这 5 个会话里观察到」。

---

## 2. 真正的机制：不是衰减，是「人类不在场时才想起来要计划」

这是全部数据里最强的一条规律。看每次 TodoWrite 距离**上一次人类输入**隔了多少轮：

| 会话 | 总轮 / 人类输入次数 | todo 距上次人类输入的轮数（均值 / 最大） | 超过 50 轮才调的比例 |
|---|---|---|---|
| `14b93c91` | 884 / 99 | **18.9 / 146** | 2/29 |
| `ba24adc3` | 1776 / 168 | **19.3 / 146** | 2/30 |
| `35b62a78` | 270 / 11 | **18.0 / 41** | 0/3 |
| `aed8ec22` | 1705 / 144 | **93.4 / 262** | **8/14** |
| `ea338c0e` | 767 / 122 | **103.2 / 210** | **4/6** |

**前三个会话：人类频繁介入（99–168 次），模型平均 19 轮内就恢复用 todo。**
**后两个会话：人类很少介入，模型一口气跑 93–103 轮才调一次 todo。**

`ea338c0e` 的细节最能说明问题——它的 6 次 todo 调用全部出现在**连续 210 轮没有人类输入**的那一段里，间隔是 2, 32, 72, 132, 171, 210。**这是唯一一段模型需要自己撑住长程任务的时候，它才想起了计划。**

### 另一种看法

如果只按「会话前 50% / 后 50%」统计，会得到「3 个衰减、1 个上升、1 个持平」，看起来像衰减。

**但按「人类输入间隔」切，规律完全不一样**：不是时间越久越不列，而是**人类一介入，模型就回到「跟着指令走」的模式，不再自己列计划**。

这跟「模型变懒」是两种解释，我倾向后者，理由是：`14b93c91` 在轮 1%–98% 全区间都有新建计划（落点 1, 33, 34, 41, 43, 80, 82, 85, 85, 90, 93, 94, 95, 98），根本没有衰减。

---

## 3. 另一个被数据推翻的假设

我原本猜「连续自主执行太久，模型会忘掉自己有个计划工具」。**数据不支持：**

| 自主段长度 | todo 密度 |
|---|---|
| ≤20 轮/段 | 1.8% |
| 21–100 轮/段 | 1.4% |
| >100 轮/段 | **2.4%** |

**长自主段的 todo 密度反而略高。** 所以不是「跑太久就忘」，更像是「跑久了才想起来需要」。

---

## 4. 网上查到的：三条独立原因

派出去的 agent 检索了整个文献和从业者讨论。以下按证据强度分档。

### A. 有实证研究支撑

| 发现 | 出处 | 与本问题的关系 |
|---|---|---|
| 多轮对话平均掉 **39%**；拆解为「能力损失仅 ~15%，不可靠性暴增 112%」；机制是 **premature commitment**（早期锁死方案，之后不再回头重规划） | Laban et al., Microsoft, arXiv:2505.06120 | **最直接**——解释了「为什么后面不重新规划」 |
| 上下文中的失败尝试会拖拽后续生成，−10~20%，自我改进会 collapse | arXiv:2602.04288 | 对应「被自己最近的输出模式带偏」 |
| Goal drift 随**部署时长**单调上升 | Apollo Research, arXiv:2505.02709 | 长跑确实会漂 |
| 指令密度↑ → 遵循率↓ | IFScale, arXiv:2507.11538 | 长上下文里指令被稀释 |
| 推理能力↑ → **约束遵循反而↓** | MathIF, arXiv:2505.14810 | 反直觉，但和「强模型不爱按套路」吻合 |

### B. 有出处但无法核实一手页面

agent 明确报告：**WebFetch 在本环境被全域拦截**，所有网页都打不开，只能看搜索摘要。所以下面这些要打折：

- **TodoWrite 在 2026-01 被官方移除，换成 Tasks 系统**。官方理由是「模型变强了，不需要脚手架」（用词 "unhobble"）。来源：`x.com/trq212` + 中文二手报道
- Anthropic 删掉了 Claude Code **80%+ 的 system prompt**
- 上下文压缩后各类指令的**存活差异**：root `CLAUDE.md` 存活 / 子目录 `CLAUDE.md` 丢失 / 已调用的 skill 在共享预算内「最旧的先丢」

> **第三条对本问题最重要。** 如果「复杂任务先列 todo」这条要求写在 skill 或子目录 CLAUDE.md 里，压缩后它就没了；写在根 CLAUDE.md 里才活得下来。这是一个**可操作的修复点**。

### C. 查不到的（诚实标注）

agent 说得很清楚：

- **没有任何论文测量过「planning tool 调用频率随 trajectory 位置下降」这条曲线**。搜了 plan abandonment / perseveration / momentum bias / action bias / tool call frequency decline，全部无结果
- **没有公开 issue / Reddit / HN 讨论「会话越长越不列 todo」**
- `autoregressive self-conditioning` 这个术语不存在
- 网传「50 个连续任务 pass rate 从 85% 掉到 20%」——**agent 判定高度可疑，不建议引用**

## 5. 合起来的解释

三条原因叠加，权重从大到小：

**① 人类在场与否（本机数据支持，权重最大）**
人类频繁提问的会话，模型跟着指令走，不主动列计划；人类长时间不介入时，模型才会用 todo 撑长程任务。**这不是退化，是模式切换。**

**② 压缩按优先级丢弃程序性指令（文献支持，机制清楚）**
「先列计划」这条习惯如果不在根 `CLAUDE.md` 里，压缩后会丢。丢了之后模型没有「我的习惯丢了」这个信号，它只是接着干。

**③ premature commitment + contextual drag（文献支持）**
模型在早期就锁死一个方案，之后不再回头重规划。**即使它还记得该列计划，它也不会去重新审视已经定下的路线。**

**这三条里，只有②是可以用配置修好的。**

---

## 6. 可以立刻做的三件事

1. **把「复杂任务先列出步骤再动手」写进根 `CLAUDE.md`，不要放 skill 或子目录**
   理由：压缩后根 CLAUDE.md 会被重读并重新注入，skill 和子目录的会丢。

2. **在 Stop hook 里检查「本轮有没有产生过计划」**
   本仓库已经有一个 `tools/stop-hook.mjs`（相位未闭合就拒绝结束回合）。同样可以检查 `current_plan` 是否为空——**把「该有计划」从模型的自律变成 harness 的强制**。这是本框架一贯的做法：能机械检查的不要靠自觉。

3. **如果确实需要计划，用外置文件而不是工具状态**
   本机 82 次 TodoWrite 全部是 per-session 内存状态。改成写 `PLAN.md` 落盘，压缩、重启、换 session 都不会丢，而且人可以随时看到。
