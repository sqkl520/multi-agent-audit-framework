# §4.5.0 规则有效性：六组实验结论

**日期**：2026-11-11
**设计**：3 组有规则 + 3 组无规则，严格隔离（`/tmp/iso-*/code/`，祖先链无答案文件）

---

## 结论

**§4.5.0「运行时验证必须调用公开 API 主路径」这条规则，让 recall 下降 5.0 个百分点，效应量中等。**

> **数字已按 manifest v3.0.0 重算。** 上一版写的是「下降 7.9 点，Cohen's d = 1.63」。口径变化后效应量从「大」降到「中等」——方向没变，但证据比之前认为的弱。

| 组 | 规则 | recall | precision |
|---|---|---|---|
| G | 有 | 55.0% | 83.3% |
| G2 | 有 | 75.0% | 92.3% |
| G3 | 有 | 75.0% | 93.3% |
| **G 均值** | | **68.3%**（sd 11.5） | **89.6%**（sd 5.5） |
| H | 无 | 75.0% | 92.9% |
| H2 | 无 | 75.0% | 80.0% |
| H3 | 无 | 70.0% | 70.6% |
| **H 均值** | | **73.3%**（sd 2.9） | **81.2%**（sd 11.2） |

- recall 差值 **−5.0 点**，Cohen's d = **0.59**（中等效应）
- precision 差值 **+8.5 点**，Cohen's d = **0.96**（大效应）

**规则提升了 8.5 点的 precision，代价是 5.0 点的 recall。** 在审计场景里，漏报比误报危险——所以这个交换仍然是亏的。

**但这条结论有多稳，要看漏报的构成：**

| 组 | 漏报条数 |
|---|---|
| G | **9** |
| G2 | 5 |
| G3 | 5 |
| H | 5 |
| H2 | 5 |
| H3 | 6 |

**G 组是唯一的离群点，其余五组全在 5–6 条之间。** 去掉 G，有规则组是 5.0 条，无规则组是 5.3 条——**规则反而略好**。

再看漏的是哪些：

**全部 6 组都漏：GT-011 / GT-012 / GT-013 / GT-021。** 这四条与规则无关，是所有组的共同盲区。

**G 组独有的额外漏报：GT-007 / GT-010 / GT-014 / GT-017 / GT-018（5 条）。** 规则的全部负面影响集中在这 5 条上，而且全在一组里。

**所以「这条规则有害」这个判断，实际上是「G 组表现得特别差」这一个观察。** n=3 里有一个离群点，不足以支撑一个因果结论。

**结论不变（降级为建议），但理由要改成**：没有任何数据表明这条规则有益，且有一组显示明显有害——**保持降级是对的，但不该说成「已证实有害」**。

## 六组全漏的三条缺陷（与规则无关）

| ID | 缺陷 | G 组 | H 组 |
|---|---|---|---|
| **GT-011** | `peek()` 返回队列内部活引用 | 3/3 漏 | 3/3 漏 |
| **GT-012** | `remove(id)` 缺 id 校验，与 `enqueue` 不一致 | 3/3 漏 | 3/3 漏 |
| **GT-013** | `capacity` 校验让 NaN/Infinity/小数通过 | 3/3 漏 | 3/3 漏 |

**六组、十八次审查，这三条零命中。**

它们的共同特征:

| 缺陷 | 为什么难 |
|---|---|
| GT-011 | 需要推演「调用方拿到引用后能做什么」——不是看代码本身 |
| GT-012 | 需要**同文件横向对比**两个函数的守卫差异 |
| GT-013 | 需要想到 `typeof NaN === 'number'` 且 `NaN <= 0 === false` |

**这三条才是真正的系统性盲区。** 而它们恰好是「缺失型 / 一致性 / 边界值」三类，正是我写 §4.8 想覆盖的。

|---|---|---|

## 我错在哪

### 错误 1：从单个案例过度归纳

D2 组发现了 GT-001，A/B 没发现。我判断「D2 是专门查承诺 vs 实现的，所以方法有效」，然后把它推广成「在通用提示词里加一条运行时验证规则」。

但 D2 的任务书是**专门**让它查那一类——它当然会发现。

**「专门派一个 agent 查某类」和「在通用提示词里加一条规则」是两件不同的事。**

### 错误 2：先改框架，后做验证

我先写了 §4.5.0（模板 + 校验器 + 72 项测试里的 3 项），**然后**才做对照实验。

正确顺序应该是：小规模对照 → 确认有效 → 再改框架。

## 该删掉 §4.5.0 吗

**该删，但保留一部分。**

| 部分 | 处理 | 理由 |
|---|---|---|
| 「必须调用公开 API 主路径并打印返回值」 | **降级为建议** | 证据显示它挤占注意力 |
| `main_path` 强制字段 | **降级为 WARN** | 硬性必填会挤压其他工作 |
| 「必须有一个已知会失败的输入」 | 保留 | 没有证据说它有害 |
| 「必须有对照用例」 | **保留且强化** | 见下 |
| 「node --check/import 不算」 | 保留 | 这条没造成负担 |

### 唯一值得强化的：对照用例

六组里唯一稳定有效的信号是**对照**：

- G 组的 `backoffDelay` 发现：「上限夹取正确，缺陷仅在指数项」——它用对照排除了另一半
- D2 组的 `runWithConcurrency` 返回值证明探针有效
- 所有正确排除负例文件的组，都做了对照

**对照不占额外注意力，它只是「用同样的方法多测一个已知答案的对象」。**

## 诚实的局限

1. **n=3 每组**——效应量 d=0.59 只是中等，且 G 组是离群点，sd 11.5
2. **同一模型**——换了模型结论可能不同
3. **同一份代码**——20 条缺陷里 7 条是原生型，分布不均
4. **GT-011/012/013 六个无规则组全漏**——说明这份 fixture 里有超出当前方法能力的东西，可能拉低了两组的绝对值
5. **没有做「删掉规则后会怎样」的验证**——现在的 H 组就是「没有规则」，但框架里还有 §4.5（「必须真跑」）没删
6. **precision 不可信**——分母（真实缺陷总数）仍未知。这一轮又发现 4 条漏登记的缺陷，说明「穷举」做得不好。真正确定的只有 recall 和原生型检出
