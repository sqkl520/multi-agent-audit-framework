# 定级一致性：4 个 agent 给同一个缺陷打的分，一样吗

**日期**：2026-11-12
**背景**：上一轮测「找没找到」用的是 Jaccard，它完全忽略严重性。两个 agent 都报了同一条缺陷、一个说 CRITICAL 一个说 LOW，在 Jaccard 里算**完全一致**。

而在实际审计里，**定级分歧可能比漏报更危险**——它直接决定这条缺陷排不排进修复队列。

---

## 结果：完全一致只有 43.8%，0 个严重分歧，但整体偏高一档

4 个 agent、同一份代码、16 条至少被 2 个 agent 报过的缺陷：

| 指标 | 数值 |
|---|---|
| 定级**完全一致** | **7/16 = 43.8%** |
| 相差 1 级（轻微分歧） | 9/16 = 56.3% |
| **相差 ≥2 级（严重分歧）** | **0/16 = 0%** |

**没有一条缺陷出现「一个说 CRITICAL、一个说 LOW」的情况。** 这是个好信号——agent 的定级分歧是「一档之差」，不是「完全对不上」。

### 但整体系统性偏高

把 agent 的定级和 manifest 里的真值比：

| | 次数 | 比例 |
|---|---|---|
| 与真值相同 | 27 | 52.9% |
| **标高了** | **17** | **33.3%** |
| 标低了 | 7 | 13.7% |

共 51 个（报告 × 缺陷）定级判断。**标高的次数是标低的 2.4 倍。**

这和框架 §3.3 里写的「严重性通胀」担忧吻合——但注意，**这条担忧所指的现象确实存在，只是不严重：没有跨两个档位的通胀。**

---

## 三个「全体一致地错」的案例

这是这轮最值得看的部分：

| 缺陷 | 真值 | 所有 agent 的定级 | 情况 |
|---|---|---|---|
| **F2-18**（`total=0` 时 `totalPages` 被兜成 1） | LOW | **HIGH**（4/4） | 全体一致地高一档 |
| **F2-19**（非法 `options` 导致分页信息错） | HIGH | **LOW**（2/2） | 全体一致地低一档 |
| **F2-20**（`page=0` 时 offset 变负） | MEDIUM | **HIGH**（4/4） | 全体一致地高一档 |

**「完全一致」在这里是假象。** 4 个 agent 都对，但它们一致地偏离我的真值。

**问题在于：谁对？**

- F2-18：`totalPages` 兜成 1，用户看到「共 1 页」但列表是空的。标 HIGH 不算离谱
- F2-19：分页信息与实际数据不符但不报错。我标 HIGH，**两个 agent 都标 LOW**
- F2-20：`page=0` 让 offset 变 -3，`slice(-3, 0)` 语义翻转。四个 agent 都标 HIGH，我标 MEDIUM

**这说明 manifest 里的「真值严重性」是我凭感觉定的，没有依据。** 拿它当评判标准本身就不成立。

---

## 根因：框架只定义了 CRITICAL，没定义另外三档

查 `wave2-audit.md` 第 3 节，只有 §3.3 一条硬门槛：

> **`CRITICAL` 的准入门槛**：不得把任何发现标为 `CRITICAL`，除非同时提供调用链证据或可复现触发条件。仅有定义位置 + 推断的，最高 `HIGH`。

**HIGH / MEDIUM / LOW 三档，框架里没有任何定义。**

所以 agent 定级偏高不是「犯错」，是**没有标准可依**。它只能靠直觉。

---

## 我验证了 §3.3 是否被执行：**逐条看过后，它们大多「技术性合规」但精神上不合规**

4 个 agent 里 3 个给了 CRITICAL，共 4 次。逐条查依据：

| Agent | 缺陷 | 依据是什么 | §3.3 判定 |
|---|---|---|---|
| C1 | `template.js:118` 转义顺序 | `escapeHtml('<b>')` → `&amp;lt;b&amp;gt;` 的实测输出 | **技术合规**（有可复现触发条件），但只是单元级 |
| C1 | `template.js:98` 插值不转义 | 实测 `compile(...)` → 原样输出 + 点名 `renderListView` 注入路径 | **合规**（有触发条件，也提了调用路径） |
| C3 | `template.js:77` 嵌套块失效 | 实测嵌套模板渲染出原始标记 | **技术合规**，但只是单元级 |
| C4 | `template.js:77` 同上 | 同上，还测了 `{a:0}` 的边界 | **技术合规** |

**按 §3.3 的字面意思（「调用链证据 **或** 可复现触发条件」），它们全都通过了。** 因为每个都给了「输入 X → 输出 Y」的实测。

**但 §3.3 想防的是「看上去吓人」的东西。** 一个只在单元测试里复现、没有说明「谁会在什么情况下调到它」的问题，仍然可能是「看上去吓人」。

**所以真正的缺口不是「规则没被执行」，是规则里的「或」字太松**——只要跑一行 `node -e` 贴个输出，就能拿 CRITICAL。

这和我上一轮写的判断不同。上一轮我说「§3.3 从未被机械校验」，那只说对了一半：**它确实从未被机械校验，但即便校验了，按字面也拦不住。**

---

## 修复：给 §3.3 加机械校验（并承认它只能拦住最裸的那种）

`check-payload.mjs` 新增规则 `critical_without_call_chain`：`severity === 'CRITICAL'` 时，`inference.claim` / `basis` / `runtime_evidence` / `alternatives` 里必须能找到调用链或触发条件的关键词。

**三个回归测试**（case 73–75）：无任何依据的 CRITICAL 被拦、有触发条件的通过、有调用链的通过。**80/80 全绿。**

**但要说清楚这条规则能做什么、不能做什么：**

| 能拦 | 拦不住 |
|---|---|
| 只写「看起来会二次转义」就标 CRITICAL | **只要贴一行实测输出，就通过**——哪怕它只是单元级 |

**这是关键词匹配的固有弱点。** 和「注释不是证据」那轮是同一类问题：判据写得越松，越容易被敷衍；写得越紧，越容易误伤。

真正要收紧，得把「调用链」定义成**可机械验证的结构**（例如要求 `runtime_evidence` 里给出从入口函数到目标函数的实际执行路径，并能被复跑验证），而不是匹配一个词。**这是设计工作，这轮没做。**

## 这轮真正的结论

### 1. 「定级一致」这个指标必须区分两种一致

| | 含义 | 好坏 |
|---|---|---|
| agent 之间一致 | 4 个 agent 打同样的分 | 好——说明有共同直觉 |
| **与真值一致** | 打得对不对 | **无法评估**——真值没有依据 |

**43.8% 的「完全一致」和 52.9% 的「与真值相同」是两个不同的问题，不能混为一谈。**

### 2. 没有评级标准时，一致性只反映共同的直觉偏差

4 个 agent 对 F2-18 一致地标 HIGH、对我标的 LOW。**这不是共识，是共有的偏差。**

**多 agent 一致性在「有客观标准」时有效（找没找到），在「没有客观标准」时只能测出「它们的直觉像不像」，不能测出「对不对」。**

### 3. 定级该有的标准，框架还没有

要让它可验证，需要一份**可机械判断的评级表**，例如：

| 档位 | 判据（可机械检查） |
|---|---|
| CRITICAL | 有调用链 + 可复现触发 + 影响数据完整性或安全边界 |
| HIGH | 有可复现触发，但无调用链；或影响单条数据 |
| MEDIUM | 有明确错误行为，需特定输入才触发 |
| LOW | 只影响可读性/一致性，无行为错误 |

**但我没有做这件事**——因为它需要先想清楚每一档的判据，而那是设计工作，不是实验能得出的。**这轮只做到「发现框架缺这块」，没做到「补齐」。**

---

## 诚实的局限

1. **n=4，只有一组**
2. **「真值严重性」是我主观定的**，用它评判 agent 的定级不成立——上面三个「全体一致地错」很可能是**我对**
3. **只测了 fixture2**，18 条缺陷、3 个档位
4. **抽取器按行号 ±3 匹配**，可能把相邻发现的严重性认错（未逐条核对）
5. **§3.3 的机械校验只查关键词**，「调用链」这个词出现在句中就算通过——可以敷衍

第 5 条值得单说：新加的 `critical_without_call_chain` 用的是正则匹配关键词，一个 agent 写「调用链：无」也会通过。**这是关键词检查的固有弱点，和「注释不是证据」那轮的教训是同一类：判据写得越松，越容易被敷衍。**

## 一个比定级更严重的问题：16 份产物，0 份符合契约

做完定级分析我顺手想用 `check-payload.mjs` 验一遍这些报告，结果发现：**它们全是纯 Markdown，一个 JSON 信封都没有。**

| 批次 | 数量 | 含 JSON 信封 |
|---|---|---|
| 历史 SP-P4/P5/P6/P7 | 12 | **0** |
| 本轮 CS-C1..C4 | 4 | **0** |
| 合计 | **16** | **0** |

而框架 `wrappers/audit-specialist.md` §4 明确写着：

> **你的产物文件必须以一个 ```json 代码块结尾**，里面是 `output-contract.md` §1 定义的信封。
>
> > **为什么写这条**：2026-11-09 实测 15 个真实产物，**0 个含 JSON 信封**。根因是契约和模板只在示例里出现过一次 JSON，从没有一句「必须写」。代价是下游写了 73 行 `salvageFromMarkdown()` 去猜——**补丁，不是护栏**。

**框架已经发现过一次「0/15 没有信封」，加了这条规则，然后这一轮的 16 份仍然是 0/16。**

### 为什么规则没生效

**因为我派 agent 时根本没有让它加载 `audit-specialist.md`。**

我的提示词写的是「输出 `## 发现 N` 格式：file / 类型 / 严重性 / 问题 / 依据」——这是一份**手工简化的任务书**，绕过了整个 wrapper 的强制加载（`evidence-policy.md`、`output-contract.md`、`wave2-audit.md`、`report-naming.md` 一个都没加载）。

**规则写在加载清单里，但我没触发加载。**

### 这意味着什么

这一轮和之前几轮的所有实验，测的都是**「一个拿到简化任务书的 agent 表现如何」**，不是「框架规定的审计 agent 表现如何」。

具体地说，下面这些框架特性**从未在实验中生效过**：

| 框架要求 | 实际生效 |
|---|---|
| JSON 信封 + payload schema | ❌ 全部 Markdown |
| `check-payload.mjs` 事前门 | ❌ 没有产物可校验 |
| `searched_scope` / `self_checks` / `files_scanned_without_findings` | ❌ 字段根本不存在 |
| 门 0 的 `evidence` / `inference` 分离 | ❌ 混在一段散文里 |
| `severity` 的 CRITICAL 准入门槛 | ❌ 无 payload 可查 |

**所以：前面几轮加的那些校验规则（G7、注释不是证据、critical_without_call_chain），在这批数据上一次都没被触发过。**

它们是对的东西，但**实验没有测到它们**。

### 这是我这轮最该承认的错误

我花了大量时间验证「门 0 能不能被绕过」「searched_scope 能不能编造」，用的都是**我自己手造的合规模板**。而真实的 agent 产物**连信封都没有**——它们根本走不到那些检查。

**换句话说：我在关上二楼的窗户，而一楼的门开着。**

### 该怎么办

这不是「再写一条规则」能解决的。要做的是：

1. **所有审计实验的派发提示词，必须让 agent 先加载 `wrappers/audit-specialist.md`**，而不是我手工写简化版
2. 或者反过来承认：**如果 harness 不支持子 agent 加载框架文件，那整个 wrapper 体系在实践中是失效的**

第 2 条更可能接近真相。我派的 agent 拿到的是我写的提示词，它不会去读 `framework/wrappers/audit-specialist.md`。

**如果真实使用场景也是这样（人把一段提示词粘给 Claude），那么框架里所有「强制加载」的规则都不会生效。** 这是一个关于框架可用性的根本问题，比任何单个校验规则都重要。

**这一轮没有解决它。** 我只做到了把它指出来。
