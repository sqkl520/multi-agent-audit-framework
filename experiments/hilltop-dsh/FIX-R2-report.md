## 四、这份入口文档能不能真的防止「1 个 agent 串行修 5 条」

**分层回答，不合并成一句。**

### 4.1 它能防住的：**「不知道该派几个」**

这是本次诊断定位到的最上游原因，也是最便宜的一环。`START-FIX.md` 把三件事从「靠临场判断」变成「照抄即可」：

1. **该加载什么**——八份清单，`triage.md` 排第一。此前它从未出现在任何加载清单里（`START-HERE.md:43-46` 只有三个文件，都不含它），而它的 `loaded:` 字段依赖 `TASK_RECEIVED` 这个纯提示词方案里不会发生的事件。
2. **该派几个**——`planned_fix_agents = |UPHELD| - Σ(申报合并)`。不是 K、不是「按需」、不是「看工作量」。
3. **那句话怎么写**——第五步整段可粘贴，其中「派发要求」是独立段落，含「本轮共 N 条……必须派 N 个独立修复实例」「不得由一个实例承担多条」。

**为什么第 3 点是关键而不是修辞**：实测三行对照（我在文档 5.2 也放了这个表）——

| 任务书写了什么 | `subagent` 调用数 |
|---|---|
| 「并行派 3 个 subagent，每个负责一个模块」 | 3 |
| 「按风险分成 3 组，并行派 3 个 subagent」 | 3 |
| 五条**编号**缺陷，全文不提 subagent / 并行 | **0**（196 step / 303 次工具调用） |

**编号子项本身不触发分解。** 五个编号缺陷在结构上比「三个模块」更像可分解任务，却没有触发——差别不在任务形状，在任务书里有没有「派」这个动作。所以文档里我把「派 N 个」写成了**任务书的一个独立小节**，而不是散落在流程说明里的一句建议。

### 4.2 它防不住的：**「读了但不执行」**

必须承认，这是这份文档的硬边界，我在文档末节也写了：

- **它是提示词，没有加载器。** `framework/README.md:240` 已承认：「纯提示词方案下，加载靠模型自律。」如果用户的任务书不指向 `START-FIX.md`，这份文档一个字都不会进上下文——**和 `fix-worker.md` 过去一个月的处境完全一样**。这是本次缺陷的**同一个根因**，我没有能力在这一层修掉它，只能把「指向它」写成第一步模板的一部分。
- **「派 N 个」仍是提示词要求。** 提示词是弱手段。强手段是 `tools/stop-hook.mjs:209-228`：`wave4` 相位里 `fix_contracts` 有 ≥2 条不同 `finding_id` 而 `budget.spawned_fix_agents ≤ 1` 时，拒绝结束回合。**这是唯一不依赖自律的一环**，但它在 R1 里才刚接上，且只在 harness 真调 stop hook 时生效。
- **对账数字可能被估算。** `spawned_fix_agents` 要求「实际计数，不得估算」，字段缺失按 0 处理（不按 1）。这条纪律与 `budget.spent` 同源（round31 记 22、实际 ≥47 就是估算的后果）。但我无法机械证明这个数是真派出来的——只能证明它「记了」且「≥2」。

### 4.3 我的判断：**比现在好很多，但不是闭环**

分三档说：

| 场景 | 我估计的结果 | 依据 |
|---|---|---|
| 用户照抄第一步的模板 | **大概率会派**（≥ 2 个实例），因为模板里「派 N 个」是独立段落且给了具体数字 | 对照组：任务书写「并行派 3 个」时 3/3 次都派了，无一例外 |
| 用户自己写任务书、但读过 `START-FIX.md` | **不确定**。可能被「上下文压缩」或「这次改动很小」稀释 | 修复 session 的 5 次压缩每次都保留了「5 条缺陷 + 测试纪律」，但**摘要里没有的东西会消失**——若「派 N 个」只出现在压缩前的某一处，它有丢的风险 |
| 用户完全不知道这份文档存在 | **仍然是 1 个 agent 串行**，与修复前无差别 | 这是同一根因的复发，入口文档解决不了 |

**所以最诚实的结论是**：`START-FIX.md` 把「修复相位的入口缺失」这个**结构性缺陷**补上了——从此「启动修复要加载什么、派几个、任务书怎么写」有唯一答案了。上一个缺陷的形状是「框架在审计相位是一个产品，在修复相位是一个零件库」（`DIAG3-prompt-structure.md:1008` 原话），这份文档让修复相位第一次有了入口。

但它**不改变「提示词靠自律」这个更底层的局限**。真正的闭环需要三件东西同时在场：① 本文档（清单与模板）、② `stop-hook.mjs` 的 `wave4` 硬门（R1）、③ `check-payload.mjs` 的 `disposition` 覆盖校验（R3）与 `check-disposition-coverage.mjs`（R4）。**四份改动缺一份，链路就还有缺口**——本份只是最上游那一份。

一个具体的剩余风险：如果执行者**只读模板、不读第二步的加载清单**（模板第 0 步要求读八份，但这仍是提示词要求），那么 `triage.md` 可能再次被跳过，TIER 判定就不会发生。文档里我已把「先加载，再动手」放在模板第 0 步、并写明「不许读摘要版」，但这条同样只有自律保障。
