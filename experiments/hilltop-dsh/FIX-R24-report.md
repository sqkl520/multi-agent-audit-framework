## 缺口 1：构建可能需要 JVM 参数

**落点**：`framework/templates/wave4-fix.md`，第 4 节（验证命令的纪律）末尾，新增 `### 4.1 构建失败先分清「产物问题」和「环境问题」`。

逐字内容：

```
### 4.1 构建失败先分清「产物问题」和「环境问题」

> **构建失败先分清「产物问题」和「环境问题」。**
> 典型的环境问题：`Could not initialize plugin: interface org.mockito.plugins.MockMaker`
> ——Mockito 的 inline mock maker 需要 self-attach，JDK 17+ 默认禁止。
> 处理：`JAVA_TOOL_OPTIONS=-Djdk.attach.allowAttachSelf=true`（或 `JDK_JAVA_OPTIONS`）重跑。
>
> 判据：**报错发生在测试框架初始化阶段、且与你的改动无关** → 环境问题，换参数重跑；
> **报错是断言失败或编译错误** → 产物问题，改代码。
>
> 2026-11-16 实战：某次修复的第一次全量构建 11 个 ERROR 全是 MockMaker，
> 加参数后 905/0/0。**不要把环境问题当成「这个项目的测试跑不了」而跳过全量。**

**为什么这条必须写进模板**：区分这两类失败，直接决定接下来该动代码还是动环境。判错的代价是双向的——把环境问题当产物问题会去改无关代码（并消耗掉三次尝试预算），把产物问题当环境问题会换参数重跑、换到第三次才承认失败。更糟的第三种结局是：判成「这个项目的测试跑不了」，然后在 `verification_commands` 里写 `not_run` 交出相位。**环境问题不是 `not_run` 的合法理由**——它有一个确定的重跑方式，就在上面。
```

放这里而不是别处，是因为第 4 节已经在管 `result` 的枚举（`passed` / `failed` / `not_run`）和 `not_run` 的合法性。缺口 1 的实质就是「一次 `failed` 到底该记成什么、下一步做什么」，与那一节的职责同构。

## 缺口 2：`.work/` 算不算「写进被审仓库」

**落点**：`framework/orchestrator/protocol.md` §0.2 之后，新增 `#### 0.2.1`。

逐字内容：

```
#### 0.2.1 `.work/` 算不算「写进被审仓库」——算允许的工作目录

**不算违规。`.work/` 属于允许的工作目录**，与「改被审代码」是两件事。

理由三条，缺一不可：

1. 它通常被 `.gitignore` 排除，不进入版本控制；
2. 它的语义就是「工作过程中的临时产物」，不是产品的一部分；
3. §0 的**目的**是「不污染被审代码、不改变仓库状态」——`.work/` 不构成两者的任何一种。

> **这条是补一个真实暴露的缺口**：2026-11-15 某次任务的产物 `<OUTDIR>` 指定在框架仓库，执行者却写到了 `<TARGET_REPO>/.work/round1/`。§0 只写了「不得对被审仓库做任何写入」，没写 `.work/` 算不算，于是执行者要么不敢写、要么写得心里没底。**含糊的边界会同时制造越界和瘫痪两种失败。**

**但 `.work/` 例外仅限产物与账本。** 以下仍然禁止：

- 修改 `.work/` 以外的任何文件
- 在 `.work/` 里放可执行的构建配置（会被误认为是项目的一部分）
- 用 `.work/` 绕过「产物必须可被 OUTDIR 定位」这条（产物路径必须写进 `state.json`）

**降级路径（合法，但必须声明）**：如果 harness 的 workspace 限制导致写不进 `<OUTDIR>`（实战中就是这样——`workspace-write` 拒绝了框架仓库的路径），**写入 `.work/` 是合法的降级**，但必须在最终报告里**显式声明**「因 workspace 限制，产物落在 `.work/` 而非 OUTDIR」。**不声明的降级等于私改落点**——下一个读实验记录的人会在 OUTDIR 里找不到东西，且不知道去哪里找。
```
