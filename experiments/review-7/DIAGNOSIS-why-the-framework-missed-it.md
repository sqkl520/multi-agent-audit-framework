# 诊断：这个框架反复失败的机制是什么

**时间**：2026-11-17 03:30
**起因**：2026-11-16 那次实战，7 条修复全部通过 905 个测试 / 26 个校验套件 / 14/14 契约合规，
随后 5 个独立 agent 红队评审判定 **5 条有缺陷、2 条严重**。

本文不是那份评审的续集。它回答的是另一个问题：
**为什么一个专门为「防止 agent 偷懒」设计的框架，会稳定地放过这些缺陷？**

---

## 一句话

**这个框架的规则数量远超它的检测数量，而且两者的差额是隐形的。**

规则写在提示词里，检测器在 `tools/` 里，中间没有对账。
一条规则消失了，没有东西会响；一条规则从来没被实现过，也没有东西会响。
所有缺口都长得像「已经做了」。

---

## 证据：三个计数

### 计数 1 —— 规范语句 vs 点名了机器的规范语句

| 模板 | 含「必须/不得/禁止/一律」的行 | 其中同时点名了校验器/工具的行 |
|---|---|---|
| `wave2-audit.md` | 79 | **4** |
| `wave4-fix.md` | 53 | **3** |
| `wave5-verify.md` | 50 | **0** |

`wave5-verify.md` 有 50 条硬性规定，**没有一条指明由哪个工具执行**。

### 计数 2 —— 校验器规则 vs 契约里写的规则

`tools/*.mjs` 里实现了 **96** 条具名规则。其中 **66 条**在
`framework/components/` 与 `framework/templates/` 里**一个字都没有**。

反方向更致命：契约明文写的规则，工具里**没有实现**。

### 计数 3 —— 变异实验

| 变异 | 有机器反应吗 |
|---|---|
| 在必查清单里插一条假模式 9 | **无**（`check-pattern-coverage.test.mjs` 14 通过 / 0 失败）|
| 把模式 5 从「追问方向」改成「硬检查项」 | **无** |
| 契约范例使用被契约禁止的 `implementation_only` | **无**，而且被盖了「已经过验证」的章 |

---

## 四个实例，同一个形态

### 实例 1 —— 模式 A：禁止改测试，零检测

`wave4-fix.md:200` 逐字写着：

> 修复Agent**不得**通过删除、跳过、弱化或重写测试断言来让检查"通过"……
> 必须在 `residual_risks` 中标记 `TEST_CONFLICT`

`grep -rn "TEST_CONFLICT" tools/` → **0 命中**（连注释都没有）。

### 实例 2 —— 模式 B：测试输入来源，从无人问

实战产出 **20 个新测试文件 + 58 条新断言**，全部零质疑地拿下「937 全绿」。

而 F1 的修复「只测 `items:` 头被截断这一种形态，注释却写成『截断已被拦住』」——
评审用 **192 个真实行边界截断样本穷举**才证明它只堵住 1.0%。
仓库里**没有任何**等价物（`grep "substring(0, i)"` / 穷举循环 → 0 命中）。

框架里也没有任何地方问「你这个测试的输入从哪来」。

### 实例 3 —— 模式 C：注释承诺 > 代码实际

`wave2-audit.md:629` 的模式 5「能力是否真的实现了 —— 注释/配置项/函数名声称的能力，实现里真做了吗？」
是 8 条必查项里唯一相关的，而它被**明确排除在检查项之外**（标为「追问方向，非检查项」）。

### 实例 4 —— 模式 D：契约范例自己违反正文

`verify.md:185` 硬要求：`implementation_and_callsite`「**必须为后者**，否则须在 `notes` 说明」。

框架给 agent 照抄的范例（`gen-contract-examples.mjs:192`）用的是 `implementation_only`，
且 `notes` 一句解释都没有。

而那个「已经过 check-payload.mjs 验证，可以直接照抄再改」的章
（`gen-contract-examples.mjs:273`）是**真的跑了校验器**才盖上的（`:243`）——
校验器不看 `mutation_scope`，所以它通过了。

---

## 最关键的那一处

`wave5-verify.md:122-127` 有一整节「测试有效性排除」，列出**四条**验收 Agent 必须执行的排除：

> - 测试被修复Agent修改过（对照 `files_touched` 与测试文件清单）；
> - 测试断言被弱化（例如断言从精确匹配改为 `assert result is not None`）；
> - 测试被跳过或标记 `skip` / `xfail`；
> - 测试依赖随机性或时序，且未固定种子（flaky 风险）。

**这四条，在 `verify.md` 的契约里一个承载字段都没有。**
`verify.md` 只有 `mutation_check` 和 `mutation_scope` 两个字段，后者还没被校验。

这不是新病。`audit.md:180` 记录过一模一样的形态，措辞是：

> 这和「15 个产物 100% 没有 JSON 信封」是同一类缺陷：
> **要求写在模板里，格式里没有位置**。

那次修好了（`self_checks` 三态）。**新写的 `wave5-verify.md` 又犯了一次。**
四条排除项被完整地、逐条地写进了散文，一条都没进契约。

---

### 计数 3 —— 全库规则句的出口率：8.5%

上面三个计数都是抽样。这把整个 `framework/` 扫了一遍。

口径：`framework/templates/*.md` + `framework/components/**/*.md`，剔除代码块，取含
`必须|不得|禁止|一律|must|shall|never` 的行；若该行 ±3 行内出现以下任一则算「有出口」：
点名了 `tools/*.mjs` 脚本、点名了 `tools/` 里真实存在的规则名、或显式标注 `DISCRETIONARY`。

| | 数量 |
|---|---|
| 规则句总数 | **625** |
| 有出口 | **53** |
| **无出口** | **572** |
| **出口率** | **8.5%** |

出口率最低的六个文件，全部是 **0%**：

| 文件 | 有出口 / 规则句 |
|---|---|
| `wave1-recon.md` | 0 / 35 |
| `components/evidence-policy.md` | 0 / 27 |
| `components/handoff-schema.md` | 0 / 31 |
| `output-contract/recon.md` | 0 / 27 |
| `output-contract/sweep.md` | 0 / 22 |
| `output-contract/verify.md` | 0 / 25 |
| `templates/wave5-verify.md` | **1 / 50** |

抽查这些「无出口」的句子，**它们确实都是真规则**，不是措辞噪声：

> `wave5-verify.md:41` 同一 `finding_id` 的两个并行验收实例 | **禁止**——它们会读同一份代码、写同名产物，后写的静默覆盖先写的
> `wave5-verify.md:90` 验收Agent是**只读**角色，没有任何写权限。它不得修复自己在验证中发现的问题
> `wave5-verify.md:59` `report.dir_ready != true` → **不得派发**

**所以模型是对的：规则句确实绝大多数没有机器出口。**

但这组数字同时否掉了「把它做成闸门」这个想法 —— 见下。

---

## 这组数字推翻了模式 D 的「闸门」形态

一份把三条缺陷模式变成机械检查的方案，把它作为元规则提了出来，判据是「每条含必须/不得的规则都要有工具出口，
或显式标 `DISCRETIONARY` 并给理由」。方案自己也担心「一次上线就红出几十处」，
所以设计了 `rules_ledger` + `PENDING` 预算来分批消化。

**实测是 572 处，不是几十处。**

一道上线首日就红出 572 条的闸门，命运是确定的：**它会被关掉，然后连带着把 A/B/C 三条真的能用的检查一起拖下水。**
框架自己记录过这个失效（`stop-hook.mjs:476-479`「豁免条目数 ≥ 待检总数 → 全量豁免等于把检查关掉」）。

所以模式 D 的正确形态不是闸门，是**仪表**：

| | 闸门（方案原设） | 仪表（实测后应采用） |
|---|---|---|
| 上线首日 | 572 条 FAIL | 一行输出：`625 条规则句 / 53 有出口 / 8.5%` |
| 对既有存量 | 需要 `rules_ledger` + `PENDING` 预算去消化 | 不判，只报 |
| 对**新增**规则 | 淹没在存量里看不见 | **可以判 FAIL** |

**唯一可闸门化的是增量**：新增/修改的规则句必须有出口或 `DISCRETIONARY`。
存量 572 条永远不判，只统计它的变化趋势。这样它上线不会红，而且从今天起
「新写一条没人执行的规则」会被当场拦住 —— 这正是 review-7 三条模式的**病因**，
而不是它的**症状**。

这与框架自己已有的教训一致（`stop-hook.mjs` 对 `legacy_artifacts` 的处理、
`run-state.md:449-451`「存量账本不因新增字段一夜不合规」）：**新规矩只对新东西生效，存量靠报告。**

---

## 框架已经知道这个病的名字，只是没给自己用

`tools/check-all.mjs:195` 逐字写着一条原则：

> 后者要求 state.json 与最终报告的裁决索引表（**外部基准**）逐条对齐——这是 R5 §5.1 指出的
> 「**两个自述互相对账不产生外部约束力**」的唯一解法。

这条原则被正确地用在「修复实例登记 vs 最终报告」上，还专门为它单开了一个检查器
（`check-fix-instances.mjs`，理由写在 `:191-195`）。

**但它没有被应用到「契约正文 vs 校验器实现」上。**

契约写「必须 `implementation_and_callsite`」是自述，校验器「我没实现这一条」也是自述 ——
**两者互不接触，所以没有外部约束力。** 于是范例能违反正文还盖上「已验证」的章。

同一个仓库，同一个原则，隔了六百行没接上。
`grep -rn "两个自述" framework/` → **0 命中**：这条原则只活在 `tools/` 的代码注释里，
从没进过任何模板或契约文档。

这算是本诊断的一个缩影：**框架写出了正确的原则，写在了错误的地方。**

---

## 为什么自动化闸门全绿却仍是错的

框架里 26 个校验套件、937 个测试，全部通过。

**它们验的是「格式对不对」，不是「做法对不对」。**
`RESULT.md` 里那句已经写对了：

> **闸门能保证「没有静默跳过验证」，不能保证「验证本身是对的」。**

本文补上它缺的下半句：

> **而且闸门验不到的东西，框架不会告诉你它没验。**

一条规则从「写在提示词里」到「有机器执行」，中间要过三关：契约有字段 → 校验器读它 → 有测试证明校验器真会报错。
**没有任何一关是有门的。** 掉在哪一关，产出的都是同一句话：「✅ 契约合规」。

---

## 所以该修的不是「再加几条规则」

review-7 的三条模式如果靠「给必查清单加模式 9/10」来解决，**不加「声明 → 执行」对账就无效**——
只是把更多字写进同一个没人读的地方。这一点已被变异实验证实：给清单加条目，机器毫无反应。

真正该补的是**一条元规则**：

> 契约里每一条带「必须/不得」的规则，都必须能在 `tools/` 里找到一个会因它而报错的规则名，
> 或者显式标注 `DISCRETIONARY`（自觉项）并说明为什么不需要机器执行。
> 缺这条对账的规则，本身就是一条 FAIL。

有了这条元规则：

- 实例 1（`TEST_CONFLICT` 零实现）→ 立刻报错
- 实例 4（`mutation_scope` 零实现）→ 立刻报错，且范例自动变红，假范例写不出来
- 实例 3（模式 5 被排除在检查项外）→ 必须显式写 `DISCRETIONARY` 并给理由，不能沉默地降级
- 实例 2（测试输入来源）→ 会暴露成一个需要显式决策的空洞，而不是无人知道

`gen-contract-examples.mjs` 已经证明了这条机制可行：它把范例喂给校验器，
不通过就不写。「契约规则 → 校验器」的对账是同一件事的更大范围版本。

---

## 一句话结论

**这个框架擅长防止 agent 偷懒，不擅长发现自己漏了检查。**
每一次它失败，失败点都在「规则写了、位置有了、机器没读」这个缝里，
而缝的外面永远是那句「✅ 契约合规」。
