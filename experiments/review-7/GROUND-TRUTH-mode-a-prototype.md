## 三、致命的：新增测试文件是彻底盲区

实测 **19 个新增测试文件 / 271 条断言 / 170 个 distinct subject**：
**检测器对它们全部报 0 findings（19 个文件，0 命中）。**

原因简单到不需要解释：`old` 侧为空，没有对照基线，什么都比不出来。

这意味着一个规避方式：**把断言写在一个全新文件里，这道闸门完全看不到。**

更具体的一击——**F1 的修复本身就是这么做的**。`ShopConfigCorruptFileTest.java` 正是本轮**新增**的文件。
也就是说：那道本该抓住 F1 形态的闸门，对 F1 的测试文件**没有任何判据**。

---

## 四、更糟的：它抓不抓得到「成功恢复原缺陷」

方案设想它能抓「断言被改弱」。原型构造了 6 个对抗实验：

| 实验 | 内容 | 报了吗 |
|---|---|---|
| E1 | 追加一个只钉住「已经能通过的那一种截断形态」的测试 | ❌ 否 |
| E2 | 同上，但测试名声称覆盖全面 | ❌ 否 |
| E3 | **删掉多条断言的那个测试，换成一行弱断言** | ❌ 否 |
| E4 | `assertEquals(1, price)` → `assertNotNull(item)`，方法名不变，基线 = HEAD | ✅ 是 |
| E5 | 同 E4 但**同时改了方法名**（真实世界的形态） | ❌ **否** |
| E6 | 同 E4，但基线取当前工作区（方法名稳定） | ✅ 是 |

**E3 和 E5 是决定性的。**

- **E3**：把有内容的测试删掉换成弱断言 = 恢复原缺陷。基线是「新增文件」，所以看不到。
- **E5**：把断言改弱**同时**改方法名 = 最自然的重构动作。**检测失败。**

**唯一能抓到的形态（E4/E6）需要「方法名不变」这个前提，而真实修复者改测试时几乎总会顺手改名**（`missingPriceDefaultsToOne` → `missingPriceDefaultsToOneWithWarning` 就是本轮真实发生的）。

## 六、结论该怎么用

**不该做**：按方案原样上线。它在真实数据上有 19/19 新增文件盲区、E3/E5 两个漏报，而这两条恰好覆盖了「恢复原缺陷」和「顺手改名」两个最常见形态。

**该做**：把它降级为**窄工具**，并在文档里写清射程。

| 它能做的 | 它做不到的 |
|---|---|
| 已有测试文件里，**改动的期望值**被反转且未申报 → 抓得住（假阳性 0）| 新增文件（含 F1 的测试）|
| 已有测试文件里，断言被改弱且方法名不变 → 抓得住 | 改弱同时改名 |
| 删除整个测试方法/文件 → 抓得住 | 删掉内容换成弱断言（若基线是新增文件）|
| 全部 603 个断言点的解析 | 「只测最容易通过的形态」这一行为本身 |

**而「它做不到的」这一栏，全部是模式 B 和模式 C 的地盘——那两条方案自己已经承认机械做不到。**

所以真正的结论是：

> **A 的机械检测能堵住一小块（有基线 + 方法名稳定 + 极性/期望值反转），
> 这块是真实的、假阳性为 0 的收益，应当上线。
> 但它不能替代独立红队评审——review-7 发现那 5 条缺陷，靠的是 5 个 agent 读代码 + 穷举探针，
> 不是任何可以写成 exit code 的东西。**

## 七、修正：新增文件的盲区有一半是我的测量口径造成的

上面第三节的结论用的是 `HEAD` 当基线，但框架的正式做法**不是** `HEAD`。

`run-state.md` §2.7 定义的 `fix_baseline` 明确写：

> `fix_baseline` 把 `actual` 从「相对 HEAD 的差异」改成「**现在的脏 − 基线里的脏**」，
> 即「这一轮新增的脏」，从而同时收窄两个方向的失真。

`run-state.md:425-432` 还给了一个精确的自证数据：被审的 Hilltop 仓库在修复开始时
**就已经有 25 行改动**，其中一部分不是本轮产生的。

所以正确的基线不是 `HEAD`，而是「进入 wave4 前的快照」。按那个口径：

| 盲区 | 是否仍然存在 |
|---|---|
| **19 个新增测试文件** | **仍然存在**（它们在 wave4 前不存在，`old` 侧照样为空）|
| **E3 删测试换弱断言** | **不存在**（wave4 前那个测试存在，会被看到）|
| **E5 改弱+改名** | **仍然存在**（匹配靠 subject_key，改名不影响；但若 baseline 内容正确，改名不影响判定——需实测确认）|
| 跨轮已脏文件 | 已有 `dirty_paths` 处理 |

**我的测量低估了框架，也高估了 E3 的严重性。**
这是我第二次犯同一个错（第一次是误判 F1 的 `not a mapping` 分支零覆盖）——
**没读既有机制就下结论**，正是本诊断在描述的那个病。

真正剩下的问题收窄成一条，但它是最重要的一条：

> **本轮新增的 19 个测试文件 / 271 条断言，没有任何对照基线。**

而 F1 的 `ShopConfigCorruptFileTest.java` 正在这 19 个里面。
换句话说：**框架现在能发现「你改了旧测试」，但发现不了「你新写了一堆只测容易形态的测试」。**
后者正是 F1 的形态。

这不需要新算法，只需要让这件事**可见**：报告里写
`本轮新增 N 个测试文件 / M 条断言，无对照基线`，而不是静静地 0 命中。

## 九、全仓扫描结果：口径必须写清，否则数字毫无意义

原型最后把**整个仓库**（97 个测试文件）都扫了，用来评估抽取质量在更大样本上的表现。

| 口径 | 文件数 | 断言调用点 | 不可解析 | 比例 |
|---|---|---|---|---|
| **全仓** | 97 | 2742 | 56 | **2.04%** |
| **本轮改动集** | 26 | 877 | 0 | **0%** |

**两个数字差 2 个数量级，而它们都是真的。** 这本身就是一个教训：
报告「不可解析率」时不写口径，等于没说。

不可解析的 56 条全部是**项目自定义断言辅助方法**，不是 JUnit 原生 API：

| 形态 | 次数 |
|---|---|
| `assertSuspect(...)` | 18 |
| `assertOk(...)` | 18 |
| `assertOnlyLeftIncrements(...)` | 5 |
| `assertFactoryOk(...)` | 5 |
| `assertNonWhitelistClicksAreInert(...)` | 4 |
| `assertWaveRowsRendered(...)` | 4 |
| `fail(...)`（不是 subject 断言）| 2 |

**这个发现对设计有直接影响**：仓库里的自定义断言 helper 是通用的反规避通道。
任何按「已知 JUnit API 名」白名单写的解析器，在这些 helper 上一律返回 `unparsable`。
而 `unparsable` 只会 WARN —— 也就是说，**把断言包进自定义 helper 就能让检测器沉默**。
这是必须写进工具文件头的已知绕过路径。

## 十、subject 碰撞：14.8% 的文件-主语对携带多个 predicate_class

全仓 2671 条断言里，有 **262 个「文件 + subject」对（14.8%）同时携带多个 predicate_class**。

最容易碰撞的 subject 是那些通用到几乎没有识别力的：

| subject | 出现次数 |
|---|---|
| `event.isCancelled()` | 54 |
| `goal.shouldActivate()` | 37 |
| `shop.countCurrency(player)` | 26 |
| `size(config.getItems())` | 24 |
| `got` | 18 |
| `size(spawns)` | 16 |

`got`、`config.hasUnsavedChanges()` 这类名字在不同测试方法里频繁复用。
**当同一个 subject 在同一文件里有 3 条 `existence_only` 和 1 条 `negative` 时，
「变档」这个判定本身就说不清是哪一个变了。**

用 `HEAD` 当基线跑本轮 26 个改动文件：

| | 数量 |
|---|---|
| 断言调用点 | 877（876 可解析）|
| 产生的 finding | **2** |

| 假阳性 | **0** |

**所以在这份数据上，这个检测器的输出 100% 是需要人裁决的合法反转。
它没有任何一条指向真正的作弊。**

这不否定它的价值——处 1、2 确实应该被申报为 `TEST_CONFLICT`，
而这个检测器把「需要申报」从一件靠自觉的事变成了会红的退出码。
但它清楚地说明了射程：**它产出的不是「抓到作弊」，是「这里有个需要解释的改动」。**

## 十三、丢方法的召回：55.3%（这是最接近真实作弊的形态）

前面所有实验都是「改一条断言」。但真正省力的作弊是**删一整个测试方法**——
它让一条缺陷彻底失去守卫，而 diff 上看起来只是「删了一点代码」。

原型做了 leave-one-method-out 实验：把 38 个 `@Test` 方法逐个删掉，看检测器报不报。

| | 结果 |
|---|---|
| 被删的测试方法 | 38 |
| 报了（`assertion_target_dropped` 等） | **21** |
| **召回** | **55.3%** |

按文件分布很不均匀：

| 文件 | 召回 |
|---|---|
| `TabListManagerTest` | 1/1（100%）|
| `ConfigManagerTest` | 2/3 |
| `ExplodeBeetleGoalTest` | 3/10 |
| `AirdropSpawnGoalTest` | **2/9（22%）** |

`AirdropSpawnGoalTest` 的 7 个漏报里，`backsOffWhenNoDropLocationFound`（3 条断言）、
`validAndTypoStillHandled`（3 条断言）都是**多断言方法**，删掉它们一条都没被抓到。

**为什么漏**：那些方法的断言 subject 与其他方法**重名**（`got`、`event.isCancelled()`、
`goal.shouldActivate()` 在整个文件里出现十几次）。按 subject_key 聚合到文件级时，
「这个 subject 还在不在」的答案是"还在"——因为别的测试方法里也有同名 subject。

**按方法匹配（v4）召回 55.3%，按「方法 + subject 多重集」匹配（v5）是 60.5%。**
提升有限，因为根本问题是**通用 subject 名在文件内高度复用**（实测 14.8% 的文件-主语对携带多个 predicate_class）。

## 十四、结论：射程表

把全部实验汇总，这个检测器真正的能力边界是：

| 形态 | 能抓到吗 | 依据 |
|---|---|---|
| 已有测试文件里，**期望值反转**且方法名不变 | ✅ 抓到 | E4/E6；假阳性 0 |
| 已有测试文件里，期望值反转且**改了方法名** | ❌ 漏 | E5 |
| **删掉整个测试方法** | ⚠️ **55.3%** | leave-one-out |
| **删掉多条断言换成一条弱断言** | ❌ 漏 | E3 |
| **把断言写进全新文件** | ❌ **完全看不见** | 19/19 新增文件 0 命中 |
| **只测最容易通过的形态**（F1 的真实形态，见下） | ❌ 完全无关 | Q6-a/b/c 全 0 |

**F1 的真实形态连"加一条测试"都不是。** 实测语料：

> `tests that iterate over cut points (substring(0, cut/i/len/idx)): 0`

**整个仓库没有任何测试在穷举截断点。** 所以 F1 的缺陷不是「加了一条弱测试」，
而是「**从来没有一条测试去想这件事**」。任何基于 diff 的检测器都对此无话可说——
没有东西可比较，因为那一侧是空的。

## 十五、对方案的具体修正

1. **新增文件必须有判据，否则直接说明它是盲区。** 至少报 `no_baseline_for_new_test_file`（WARN），
   让「本轮 20 个新测试文件没有任何断言对照」这件事在账本上可见，而不是静静地 0 命中。
2. **不要声称能抓「断言被弱化」全形态。** 只能写「同名方法内的期望值反转」。
3. **E5 的漏报要在工具文件头写明**，否则下一个人会以为它在守而实际没守——
   这正是本文诊断说的「闸门验不到的东西，框架不会告诉你它没验」。
