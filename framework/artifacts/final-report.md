# artifacts/final-report.md

> **唯一硬规则**：**只要这一轮启动过，就必须留下报告。**
> 「跑完了但没有报告」不是合法终态——它等同于该轮从未发生，因为没有留下任何可消费的产出。

---

## 第 1 节：何时必须产出

| 情形 | 是否必须出报告 | `report_state` 取值 |
|---|---|---|
| 默认路径（AUDIT_ONLY）正常跑完 | **是** | `COMPLETE` |
| 预算耗尽 | **是** | `PARTIAL_BUDGET` |
| 用户中断 / 对话要结束 | **是** | `PARTIAL_INTERRUPTED` |
| agent 连续失败触发暂停 | **是** | `PARTIAL_BLOCKED` |
| 主 Agent 判断「跑不完」 | **是** | `PARTIAL_ABORTED` |
| 修复路径（FIX）每条发现结束 | **是**（逐条） | `FIX_DONE` / `FIX_FAILED` |

**没有例外。** 上表覆盖了全部终止路径——也就是说，「不出报告」这个分支在设计上不存在。

---

## 第 2 节：报告路径与命名

```
docs/reports/round{N}/round{N}-final-report.md
```

与轮次产物同目录。写成功后**必须**把路径回写 `state.json` 的 `report.final_report_path`，并把 `report.is_complete` 置为对应值。

**写失败处理**（磁盘满、权限、路径被占用）：`status: BLOCKED`，在 stdout 明确报出错误，**不得假装成功**，不得把半截文件当成报告。

---

## 第 3 节：报告骨架（五节固定）

```markdown
# round{N} 审计报告

## 0. 元信息

| 字段 | 值 |
|---|---|
| round_id | round{N} |
| trace_id | string |
| 路径模式 | AUDIT_ONLY / FIX |
| report_state | COMPLETE / PARTIAL_* |
| 开始 / 结束时间 | ISO8601 |
| 是否续跑 | 是（原轮次 round{N}，续跑于 …） / 否 |
| 实际派发 agent 数 | N（来自 budget.spent，不估算） |
| 预算上限 | M |

## 1. 裁决索引表

| finding_id | 严重性 | 维度 | 位置 | 裁决 | 出处 |
|---|---|---|---|---|---|
| ... | HIGH | concurrency | `path:line` | UPHELD | `round{N}-03-critique-arbiter.md` |

**铁律**：主 Agent **只做排序、加索引、加统计**，不得改写任何子 Agent 的措辞、严重性或裁决结论。每一行的「出处」必须是 `artifact_ref`，指向能复核该结论的原始文件。

## 2. 覆盖率

**必须报两组指标，缺一不可。**

### 2.1 派发覆盖率（派了多少）

| 指标 | 数值 |
|---|---|
| `effective_slices` | N |
| 已宽扫 | N（%） |
| 已深挖 | M（%），深挖维度总数 K |
| 未深挖（有线索但预算截断） | X 片 |
| 未深挖（`UNREACHABLE`） | Y 片 |
| `DEFERRED` 切片 | Z 片 |
| 失败的 agent | F 个 |
| 状态不明的 agent | U 个 |

### 2.2 证据覆盖率（真查了多少）—— 2026-11-10 新增，必填

| 指标 | 数值 |
|---|---|
| 产物中**通过门 0** 的 quote 条数 | Q |
| 全部切片声明的文件总数 | F |
| **证据覆盖率 = Q / F** | **xx%** |

**为什么必须报这一组**（红队/蓝队实测）：

派发覆盖率**可以 100% 而证据覆盖率为 0%**。具体形态：每个切片都派了 Agent、都返回 `SUCCESS`，但每份产物都是 `NO_EVIDENCE_FOUND` 且正文什么都不写。此时 2.1 全部是绿灯，而实际一个字都没审。

而 2.2 **伪造不了**：`Q` 统计的是「产物里每条 quote 都能在仓库里按 `file:line` 找到原文」的条数——这个数由 `verify-artifacts.mjs` 的 G0 直接产出，不需要 Agent 配合。**一个空产物 → Q=0 → 证据覆盖率 0%，一眼看穿。**

**计算口径**（机械，零裁量）：

```
Q = verify-artifacts.mjs 输出的 G0「ok」计数
F = Σ(每片 payload.files 或 files_read 的长度，去重后)

若 Q / F < 0.05 → 报告中必须置顶一行：
  「⚠ 本轮证据覆盖率仅 xx%，请先确认 Agent 是否真的读了代码」
```

> **这两组指标的关系**：2.1 回答「流程走完了吗」，2.2 回答「走的时候有没有真的看」。**只报 2.1 是自欺**——它让「跑了 60 个 agent」和「真的看了 60 片代码」看起来一样。

**这一节必须诚实**。覆盖率不足不是羞耻，隐瞒覆盖率才是——`README.md` 的核心原则是「宁可承认覆盖不足，不可产生看起来完整的假象」。

## 3. 未闭合项

按 `handoff-schema.md` 第 3 节的 `open_items` 结构列出，每条含 `kind` / `blocking` / `next_action` / `summary`。

**不允许空数组掩盖实际存在的未闭合项。** round31 的 `open_items: []` 而实际有 38 片 deferred + 83 条待修复，这是反面教材。

## 4. 裁量记录（L1 裁量附录）

| seq | 波次 | 类型 | 做了什么 | 依据 | 机械复核方法 | 可回退 |
|---|---|---|---|---|---|---|
| ... | ... | ... | ... | ... | ... | ... |

**这是 `protocol.md` 第 1.2 节「裁量留痕」的对外呈现。** 没有这一节，等于裁量不可复核，按该节规则该轮结论作废。

## 5. 未深挖线索附录（宽扫产出）

| lead_id | 切片 | 疑似维度 | 位置 | 为什么没深挖 |
|---|---|---|---|---|
| ... | ... | ... | `path:line` | 预算截断 / `UNREACHABLE` / 线索密度不足 |

这一节的价值：**下一轮或人工可以直接从这里接着审**，不必重新侦察。
```

## 第 4 节：不完整报告的额外要求

当 `report_state` 为 `PARTIAL_*` 时，报告**必须**额外包含：

```markdown
## 本轮未完成

**原因**：<预算耗尽 / 用户中断 / agent 连续失败 / 主动放弃>

**已完成**：<波次列表>
**未完成**：<波次列表 + 具体缺口>

**下一步**
- 续跑指令：`继续 round{N}`（状态已存于 `docs/reports/round{N}/state.json`）
- 预计还需：X 个 agent
- 建议优先级：<按 reachability + lead_count 的确定性顺序>
```

**「建议优先级」必须来自确定性规则**（`reachability` → `lead_count` 降序 → FIFO），不得是主 Agent 的主观建议——否则续跑时会引入裁量。

## 第 5 节：与 `run-state.md` 的交接

报告写完后：

```
1. 把 report.final_report_path 写入 state.json
2. 把 report.is_complete 置为 true（仅当 report_state == COMPLETE）
3. 把 phase 置为 "report" → 再置为 "closed"
4. status 置为 CLOSED 或 PARTIALLY_CLOSED（**不得**是 IN_PROGRESS）
5. 落盘
```

**`status` 的闭集**：`RUNNING` / `PARTIALLY_CLOSED` / `CLOSED` / `BLOCKED`。

**`IN_PROGRESS` 已被移除**——round31 正是停在这个值上，既没跑完也没收尾，续跑时无法判断该做什么。新设计用 `RUNNING`（还在跑，需要续跑）+ 报告产物（已有产出）两个独立信号代替它，避免「一个状态同时表示两件事」。

## 第 6 节：自检清单（主 Agent 写报告前逐项确认）

| # | 检查项 | 不通过怎么办 |
|---|---|---|
| 1 | 报告的每一行结论都有 `artifact_ref` | 补出处；找不到出处的条目**删掉**，不得留无出处的结论 |
| 2 | 覆盖率数字来自 `state.json` 的实际计数，不是估算 | 从产物目录重建后重算 |
| 3 | `open_items` 非空时不含 `blocking: false` 的粉饰 | 按 `handoff-schema.md` 第 3 节重新分类 |
| 4 | 裁量记录与 `discipline_log` 完全一致 | 以 `discipline_log` 为准，不一致即作废该轮 |
| 5 | 未深挖线索附录包含了所有 `DEFERRED_DEEP_DIVE` | 补齐 |
| 6 | `report_state` 与实际完成度相符 | 宁可写 `PARTIAL_*`，不得虚报 `COMPLETE` |
| 7 | 报告已真实写盘（可被 `ls` 看到） | 写失败即 `BLOCKED`，不得声称已产出 |
| 8 | **附上「被审仓库零改动」的自检输出** | 见下节；有改动即**严重违规**，必须报告 |

**第 7 条特别说明**：round31 的问题正是「没有报告且没有任何声明」。任何「我以为写了」的情况都按未写处理。

## 第 7 节：零写入自检（强制，附在报告末尾）

`protocol.md` 第 0 节规定：**除非用户明确要求，不得对被审仓库做任何写入**。报告必须附上可复核的证据，而不是一句「我没有改动」。

**主 Agent 必须在报告末尾原样粘贴以下命令的真实输出**：

```bash
echo "=== 被审仓库零改动自检 ==="
git -C <被审仓库> status --short | grep -E '^ ?[MDARC]' \
  && echo "❌ 检测到跟踪文件改动 —— 违反零写入原则" \
  || echo "✅ 跟踪文件零改动"
echo "=== 未跟踪文件（应仅有本轮之外的既有文件）==="
git -C <被审仓库> status --short | grep -c '^??'
```

**判读规则**：

| 输出 | 含义 | 动作 |
|---|---|---|
| `✅ 跟踪文件零改动` | 正常 | 附上即可 |
| `❌ 检测到跟踪文件改动` | **严重违规** | 必须逐项列出改了什么、为什么、如何回退，并在报告顶部醒目声明 |
| 未跟踪文件数**比本轮开始时增加** | 有产物写进了被审仓库 | 列出新增文件；若在 `.gitignore` 内可接受，否则必须清理并改写到仓库外 |

**"本轮开始时"的基准**：主 Agent 应在运行开始时记录一次 `git status --short | wc -l`，写入 `state.json`。结束时对比。**没有基准就无法判断增量**，这一步不能省。

**为什么这条要进报告**：审计的可信度不只来自发现的质量，也来自「审计过程本身没有改变被审对象」。一份改了代码的审计报告，其所有 `file:line` 引用的时间点都不可自证。

### 7.1 已有未提交改动怎么办（实测定本）

`dsh-fcl-android-launcher` 实测时遇到：运行开始时仓库里**已经有 2 个文件的未提交改动**（`DshInstances.kt` + 对应测试，191 行新增），来自更早会话的 `fix-r31-001`。

**处理规则**：

1. **不要回滚它们。** 那不是本轮的产物，回滚等于替用户丢掉别人（或更早的自己）的工作。
2. **不要提交它们。** 未经授权就 commit 是严重违规——哪怕改动看起来是好的。
3. **必须记录基线**：在 `state.json` 写入运行开始时的 `git status --short` 完整快照（不只是计数）。
4. **报告里显式声明**：

```markdown
## 零写入自检

本次运行开始时，被审仓库已有以下未提交改动（**非本轮产生，本轮未触碰**）：

| 文件 | 行数变化 | 推断来源 |
|---|---|---|
| FCL/src/main/java/com/dsh/core/DshInstances.kt | +36/−6 | 更早会话的 fix-r31-001 |
| FCL/src/test/java/com/dsh/DshInstancesPersistenceTest.kt | +155 | 同上 |

本轮对上述文件的改动：**无**（本轮全程只读）。

结束时状态与开始时一致：✅
```

**关键判据**：**"相对基线的增量"才是本轮的责任范围**，绝对状态不是。报告必须同时给出两者，否则读者无法分辨哪些改动是审计产生的。

## 第 8 节：发现必须归并成「缺陷族」，不得逐条打补丁（2026-11-02 新增）

### 8.1 问题

跑完两轮拿到 **99 条发现**（其中 **52 条有产物可查**，见下文口径）后，直觉做法是逐条修。但那会产出一份 128 项的补丁清单——**用户拿到它会直接放弃**，而且看不出哪些是同一个根因。

**实测归并结果**（`D:\Web\style`，本轮 99 条；**注意：仅 52 条有落盘产物，47 条无法回溯**）：

| 缺陷族 | 归并后条数 | 占比 | 根因（一句话） |
|---|---|---|---|
| **状态多处表达、副本漂移** | 25 | 20% | 事实没有单一所有者，N 个副本 = N−1 个漂移点 |
| **文案承诺 vs 实现** | 28 | 22% | 散文里的数字与实现里的数字**中间没有机械连接** |
| **守卫失效 / 假绿** | 12 | 9% | **检查器的正确性从来没被检查过** |
| **`animation ... both` 锁死状态类** | 4（+9 处风险） | 3% | 同一条 `transform` 被「动画填充态」和「状态选择器」两个所有者声明 |
| **其余零散** | ~59 | 46% | 各自独立 |

**约 54% 的发现归结为 4 个根因。** 逐条修 = 修 128 次；按族修 = 修 4 次 + 一行脚本校验。

### 8.2 规则

**报告必须先归并、再给方案。** 具体三件事：

```
1. 归并：把发现按「根因」聚类，而不是按「文件」或「严重性」排列
   - 判断两条发现同族的标准：删掉其中一条的修复，另一条是否仍然需要单独修？
     若「一次修法能同时解决 N 条」→ 同族
2. 归并后必须给出：族名 / 条数 / 占比 / 根因一句话
3. 对每个族给「统一修法 + 自动验证 + 迁移成本 + **不修的取舍**」
```

### 8.3 每个族必须回答「不修的取舍」

这是最容易漏、也最重要的一条。

**实测取舍示例**：

| 族 | 归并后 | 决定修的 | 决定不修的 | 理由 |
|---|---|---|---|---|
| `both` 锁死 | 136 处 `both`（口径：.css 里 animation 声明含 both/forwards）| **5 处**经 DOM 证实 | 131 处 | 其余所在元素没有任何状态类 transform，或有动画但状态本就不改 transform |
| 状态漂移 | 25 条 | **6 个案**（有交互的） | 纯静态案 | 无状态变更即无漂移可能 |
| 文案 vs 实现 | 28 条 | **24 条**（带数字的） | 4 条风格类 | 「不做旧」这类无法机械判定 |
| 假绿 | 12 条 | `_build/` 下 8 个守卫 | `*-scratch/` 上百个 | 那是取证快照，不是守卫 |

**不写的后果**：用户以为「所有条都要修」，实际只需修约 40 处。**明确说"这些不修"和"这些要修"同样重要**——它让方案变得可执行。

> **一个必须诚实披露的前提**：下面的归并表相加只有 85，而原始发现是 99 条——**14 条无归属**。归并本身是启发式的，不保证覆盖全部。

### 8.4 优先级的排序依据

**不要按严重性排，要按「影响面 ÷ 成本」排**，并显式写出分母：

```
影响面 = 用户可见性 × 案数
成本   = 改动行数 × 回归风险
```

**实测反直觉结论**：**先修"量具"（守卫自检），再修"功能"。**

理由：如果守卫是坏的，你**无法证明**后面任何修复真的生效了。族 4 排在族 1–3 之前不是因为它更严重，而是因为**它是其他三族的验收工具**。

> 这条与 `evidence-policy.md` 的「证据必须可核验」是同一条原则的延伸：**测量工具本身也要可核验**。

### 8.5 报告里的族级表达（模板）

```markdown
## 缺陷族 1 · <族名>
- **归并条数**：N 条（占 X%）
- **根因**：<一句话，指出是什么结构导致这类缺陷反复出现，而不是"某处写错了">
- **统一修法**：<能一次解决该族大部分实例的方案 + 代码骨架>
- **自动验证**：<怎么证明修好了——必须能自动跑>
- **迁移成本**：<要改几个文件、有无破坏性>
- **不修的取舍**：<明确列出哪些不修及理由>
```

**最后给一张优先级表**，每行标「影响面 / 成本 / 结论（立刻做 / 本批 / 次批 / 不做）」。

## 第 9 节：报告里的每个数字必须可复跑（2026-11-03 新增）

### 9.1 这条是被自己的错误逼出来的

写这套框架的过程中，同一个统计我报过**三个不同的数**：

| 版本 | 数字 | 问题 |
|---|---|---|
| 第一版 | 7 处 | 只扫了 `_build/` 却说"全仓" |
| "更正版" | 4 处 | 漏了 3 个文件 |
| 某个锐评 Agent 复核 | 11 处 | 正则口径不同 |
| **逐文件重算** | **8 处** | 列出了文件名与条数，可逐条核 |

另一个例子：`136 处 both/forwards` 我先报成 **144**，因为**没写口径**——把 `.html` 的内联 `animation` 也算进去了。

**最严重的一个**：我报「误报率 5/11 ≈ 45%」，后来发现**分子的 11 个页面和分母的 11 个文件只重叠 6 个**——两个不同实验的数字相除，这个百分比在数学上不指向任何东西。

### 9.2 规则

**任何进入最终报告的数字，必须同时给出三样，缺一不可**：

```markdown
<数字>（口径：<分子是什么 / 分母是什么 / 统计范围>）
命令：
  <可直接复制运行的命令>
输出：
  <原始输出的关键行>
```

**三者缺一 → 该数字标 `UNVERIFIED`，不得作为结论依据。**

### 9.3 示例（正例 vs 反例）

**反例**（我实际写过的）：
```
全仓 `animation: ... both|forwards` 144 处（我实测）。
```
——口径不明、无命令、无输出。结果错了 8，且无法被发现。

**正例**：
```
全仓 `animation: ... both|forwards` **136 处**
（口径：`git ls-files "*.css"` 的 83 个文件里，`animation` 声明含 `both` 或 `forwards` 的条数）
命令：node -e "...（见 docs/analysis/2026-11-03-number-recount.md）"
输出：口径1: 136 / 口径2: 136 / 口径3(animation-fill-mode 显式): 0
```
——三个口径里两个收敛到 136，第三个数为 0 说明没有用 `animation-fill-mode` 写的，口径清晰可复跑。

### 9.4 为什么这条比"引用可核验"更容易被违反

`evidence-policy.md` 第 8 节管的是**引用别人的东西**——写的时候会警觉。

而这条管的是**自己算出来的东西**——写的时候会觉得"我刚算的，不会有错"。

**但"我刚算的"恰恰是最容易错的**，因为：
- 命令写完就丢了，下次想复核得重写
- 口径在自己脑子里，没写出来
- 换个角度看同一个数据，会得到不同的数（`7` vs `4` vs `8`）

**所以这条的强度必须和引用纪律一样**：**不是"我算过了"，而是"任何人按这个命令都能算出同一个数"。**

### 9.5 与"缺陷族归并"（第 8 节）的配合

第 8 节要求把发现归并成族并给出**不修的取舍**。而"哪族修多少条"本身就是一个数字。

**所以第 8 节的每张归并表，也必须满足第 9 节的三要素。** 否则会出现这种情况：

> 「`both` 锁死：136 处里修 9 处，130 处不修」
> ——但如果 136 本身口径不明、9 和 130 无法复算，这张表就只是看起来很有条理。

**这就是我实际犯过的错**：归并表写得很整齐（25/28/12/4），但相加只有 85，而标题写的是"128 条的分布"。
