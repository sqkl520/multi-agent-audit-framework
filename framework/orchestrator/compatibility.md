# orchestrator/compatibility.md

> **加载时机**：`environment-probe.md` 探测完之后、`triage.md` 判定 TIER 之前。
> **职责边界**：只回答「这个 harness 能做到哪些、做不到的怎么降级」。不决定审什么。

## 第 1 节：核心问题

**「极限多 Agent」要求 9 个成员 × 3 层递归。但不是每个 harness 都能跑。**

| harness 能力 | 有 | 没有会怎样 |
|---|---|---|
| 能派子 Agent | ✅ 大多数 | **完全没有面板制**，退化为单 Agent |
| 上下文隔离 | ✅ 大多数 | 子 Agent 互相污染，独立性失效 |
| 原生并发 | ⚠️ 部分 | 只能串行，9 个成员跑 9 遍 |
| 能查询任务状态 | ⚠️ 部分 | 无法判断死活（见 `run-state.md` §4.4） |
| 能获取 token 计量 | ❌ 罕见 | 无法做成本控制 |
| 支持 Workflow 脚本 | ❌ 罕见 | 编排需由主 Agent 逐轮驱动 |

**这张表决定了：同一套提示词，在不同 harness 上的**实际面板规模**会差一个数量级。**

所以不能只写「T2 = 9 个成员」，必须写清楚**每个 harness 上这 9 个怎么落地**。

## 第 2 节：能力矩阵（按 harness 分级）

### 2.1 四级分类

| 级别 | 定义 | 典型 harness |
|---|---|---|
| **L-A 全能力** | 有 Workflow 脚本 + 原生并发 + 状态查询 + token 计量 | Claude Code ≥ 2.1.150 |
| **L-B 部分能力** | 有子 Agent + 并发，无 Workflow 脚本 | Claude Code < 2.1.150、多数 agent SDK |
| **L-C 基础** | 有子 Agent，无并发控制（或极低） | 简单 CLI wrapper |
| **L-D 单 Agent** | 无法派子 Agent | 纯 chat 界面 |

### 2.2 各级别下的面板落地

| 能力 | L-A | L-B | L-C | L-D |
|---|---|---|---|---|
| **T0（3 成员）** | 3 并行 | 3 并行 | 3 串行 | **1 个，标注「降级运行」** |
| **T1（5 成员）** | 5 并行 | 5 并行 | 5 串行 | **1 个，标注「降级运行」** |
| **T2（9 成员）** | 9 并行 + 3 层递归 | 9 并行 + 2 层 | **9 串行，无递归** | **1 个，标注「降级运行」** |
| 状态查询 | harness 原生 | harness 原生 | 轮询产物 | 不适用 |
| 失败重派 | 自动（Workflow） | 主 Agent 手派 | 主 Agent 手派 | 不适用 |

### 2.3 降级不等于打折：必须声明

**在 L-C / L-D 上运行时，报告顶部必须加一段**：

```markdown
> ⚠️ 本次运行于降级模式（L-C：无原生并发）
> - 计划面板：T2 = 9 成员 × 3 层
> - 实际执行：9 成员串行，无递归
> - 影响：耗时约 9 倍；无法做交叉验证（后一个能看到前一个的产物）
> - 若要完整能力，请使用支持并发的 harness
```

**为什么必须声明**：用户以为拿到了「极限多 agent」的结论，实际拿到的是单线程串行的结果——**这个差距如果不说明，报告的可信度就是假的**。

## 第 3 节：逐能力降级规则

### 3.1 没有原生并发怎么办

```
检测到无并发能力 → 串行执行
```

**但串行会破坏「独立分析」原则**——而这不是「提示词约定能解决」的问题，红队已指出：

| 泄漏通道 | 为什么挡不住 |
|---|---|
| **文件可见性** | 同机同文件系统，agent 带 `Read`/`Bash` 时，路径约定挡不住主动读取 |
| **主 Agent 的上下文** | 写第 k 个 agent 的 prompt 时，前 k−1 个的结论已经在它上下文里，**它无法「忘记」**，措辞必然被锚定 |
| **`state.json`** | 主 Agent 逐轮写入并被下一轮读取，本身就是一块共享黑板 |
| **执行顺序** | 若「验证」排在「执行」之后，`verifier.md` 要求的「不读执行者自述」在时间上已不可能满足 |

**所以 L-C 的降级必须更彻底**：

```
L-C 上的诚实做法：
  1. 明确宣布「本环境无法保证独立分析」
  2. 报告里【不得】声称「9 个成员独立分析」
  3. 只能声称「9 个成员按顺序执行」——这是事实，不含独立性暗示
  4. 若用户要求真独立，必须换 harness，不是改提示词
```

**禁止的做法**：

| ❌ 错误 | 为什么错 |
|---|---|
| 「每个 Agent 的输入包显式限定可见文件」 | 提示词纪律挡不住主动读取 |
| 「批判 Agent 的可见范围不含执行者产物目录」 | 同上，且主 Agent 的上下文已经泄漏了 |
| 「主 Agent 派发前检查输入包」 | 主 Agent 看不到子 Agent 实际读了什么 |

**验证顺序必须写死**：如果一定要在 L-C 上做验证，**验证 Agent 必须第一个跑**——那时还没有任何执行结果存在。这是唯一能保证独立性的顺序。

### 3.2 无法查询任务状态怎么办

沿用 `run-state.md` §4.4.2 的规则：**不主动杀，等终态**。

```
无法查询 → 记录 state_unknown: true
       → 继续等 harness 的结果
       → 向用户汇报时说「无法确认状态」，不得说「还在跑」
```

**不得用 mtime / 进程表做替代判据**——2026-11-04/05 的误杀就是这样发生的。

### 3.3 没有 token 计量怎么办

```
无 token 计量 → 退化为「agent 计数」

可用护栏：
  - 单次运行总 agent 上限（protocol.md §6）
  - 递归深度上限（triage.md §5）
  - 每层扇出系数上限（5）

不可用的：
  - 基于 token 的成本预警
  - 「Large workflow」类提示（那是 harness 的功能）

报告里必须写明「本环境无 token 计量，成本控制依赖 agent 计数，精度较低」。
```

### 3.4 没有 Workflow 脚本怎么办

这是最常见的情况。**Workflow 的核心价值是「编排移出上下文」，没有它就必须由主 Agent 逐轮驱动。**

```
无 Workflow → 主 Agent 手动循环：
  1. 读 state.json 决定下一个任务
  2. 派 Agent
  3. 收结果
  4. 写 state.json
  5. 回到 1
```

**这已经在 `run-state.md` §7「最小可行实现」里定义过**，本节只说明它的适用边界。

### 3.5 主 Agent 的上下文预算（2026-11-09 新增，红队指出的硬缺陷）

**这是 L-B / L-C 上最先崩的东西——不是被审对象，是主 Agent 自己。**

200 个 agent 的结果全部回流主 Agent 的上下文。即使每个只回 500 token 摘要，也是 **10 万 token 起步**，还没算框架文档本身。

**必须有的四条规则**（原版一条都没有）：

| # | 规则 | 内容 |
|---|---|---|
| **1** | **单 Agent 结果上限** | 每个子 Agent 返回主 Agent 的内容 **≤ 800 token**。超出部分只留在产物文件里，不进上下文。 |
| **2** | **强制结构化摘要** | 主 Agent 只接收结构化字段（`finding_id` / `severity` / `artifact_path` / `verdict`），**不接收叙述正文**。这条在 `wave3-critique.md` 的 Arbiter 上已经做过，现在推广到主 Agent。 |
| **3** | **上下文预算追踪** | 主 Agent 必须估算自己的上下文占用。超过 **70%** 时：把已完成轮次的详细结果**落盘并从上下文移除**，只保留 `artifact_path` + 一行摘要。 |
| **4** | **超限即中止** | 超过 **90%** 时：**停止派发新 Agent**，出报告，`status: PARTIALLY_CLOSED`，明确写「因主 Agent 上下文上限停止展开，已覆盖 N/M」。 |

**禁止的静默行为**：

| ❌ | 为什么危险 |
|---|---|
| 上下文满了就自动截断早期结果 | 最终报告基于残缺证据链，却仍标注完整规模——**这是最坏的一种损失：形式完整、内容残缺、无人知晓** |
| 摘要里混入叙述正文 | 每个 agent 多 200 token，200 个就是 4 万 |

**触发时的报告措辞（强制）**：

```markdown
> ⚠️ 上下文预算触顶，本次运行于 N/M 处停止展开
> - 停止原因：主 Agent 上下文达 90%
> - 已覆盖：N 个 Agent
> - 未覆盖：M−N 个 Agent（清单见 ledger.md）
> - **不得**将本报告视为完整审计
```

> **红队原话**：作者识别了「无处可去时会静默丢失」这个风险，但对策只给了「深度 ≤ 3」——**深度不是上下文预算**。

## 第 4 节：跨 harness 的**文件格式**兼容

**能力之外，还有一层兼容：同一份规则文件在不同 harness 上能不能被读到。**

| 格式问题 | 影响 | 对策 |
|---|---|---|
| frontmatter 自定义字段 | 多数 harness 忽略，不影响 | 保留，读者是人和主 Agent |
| ```json 代码块 | 部分 harness 的渲染会吃掉 | 用严格 JSON，不加注释 |
| 中文路径 / 空格路径 | **会导致工具调用被静默拒绝** | 产物路径必须无空格（`report-naming.md` §5.2） |
| 相对路径引用 | 工作目录不同会全部失效 | 用 `<FRAMEWORK_ROOT>` 绝对路径 |

**2026-11-09 实测补充**：本仓库路径含空格（`AI prompt`），但当天派出的 6 个 Agent **全部成功落盘**。所以「空格路径必然失败」这个结论**不成立**。

**正确表述**：

> 空格路径是**风险因素**，不是必然失败。它在某些工具调用形式下会被拒绝（2026-11-04/05 有 4 例），在另一些形式下正常（2026-11-09 有 6 例成功）。
>
> **对策不变**：能用无空格路径就用。但不能因为它没失败就认为它安全。

## 第 5 节：这台机器上的实际配置

运行以下命令获取你的真实能力：

```bash
node <FRAMEWORK_ROOT>/tools/detect-harness.mjs
```

**探测结果决定了你在 §2.2 表里的哪一列。** 探测不到的项标 `unknown`，按最保守的级别处理（L-C）。

**这台机器的实测**：

```
harness       claude-code (2.1.289)
Workflow 可用  likely        → L-A
并发上限      16（workflow）/ 20（subagent）
stall 重试    5 次（原生）
```

**所以这台机器应该走 L-A 列：T2 = 9 并行 + 3 层递归。**

## 第 6 节：自检

主 Agent 在派发前必须回答：

| 检查 | 通过条件 |
|---|---|
| harness 级别已定 | L-A / L-B / L-C / L-D 四选一 |
| 面板规模已按级别调整 | 对照 §2.2 表 |
| 降级已声明 | 非 L-A 必须在报告顶部加降级说明 |
| 格式兼容已检查 | 产物路径无空格、用绝对路径 |
| 能力缺口已告知 | 无 token 计量 / 无状态查询等，写进报告 |

**五项缺一不可。**
