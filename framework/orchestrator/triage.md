# orchestrator/triage.md

> **加载时机**：主 Agent 收到任务后、派发第一个 Agent 之前。
> **职责边界**：只决定「开多大的面板」。不决定「怎么审」——那是模板的事。

## 第 1 节：为什么需要机械判定

用户要求「任何非平凡任务 ≥5 个专家 Agent，简单任务可降为 主Agent+审查Agent」。

**但如果「非平凡」靠感觉判断，这个规则会退化成两种失效**：

| 失效模式 | 表现 |
|---|---|
| 一律按最贵跑 | 改一行错别字也开 7 个 agent |
| 一律按最便宜跑 | 架构评审只派 2 个，当作「简单任务」 |

**所以判定必须可数。** 下面七项，每项只有 0 或 1，加总即分数。

---

## 第 2 节：TIER 判定卡（七项，不得写形容词）

```
K1 写入面    本任务需要写入 ≥1 个文件，或执行 ≥1 条非只读命令 ......... 1
K2 跨度      需要读取或改动的模块 / 目录 / 服务 ≥ 2 个 ................. 1
K3 交付物    交付物 ≥ 2 个（代码、测试、文档、配置各算一个） ........... 1
K4 证据源    结论需要 ≥2 个独立证据源交叉支持才能成立 ................. 1
K5 候选解    存在 ≥2 个互斥且都能自圆其说的方案 ....................... 1
K6 不可逆    改变对外接口 / 数据格式 / 迁移 / 删除 / 发布 / 权限 ....... 1
K7 未知前提  任务书含 ≥1 个必须自行发现才能继续的未知前提 ............. 1

score = K1+K2+K3+K4+K5+K6+K7

score = 0  → TIER-0（简单）
score = 1  → TIER-1（标准）
score ≥ 2  → TIER-2（复杂）
```

### 2.1 每一项怎么判（可复核的判据）

| 项 | 判 1 的条件 | 判 0 的条件 | 复核方式 |
|---|---|---|---|
| **K1 写入面** | 任务书含「改/写/新建/删除/运行/安装」类动词 | 纯阅读、纯分析、纯查询 | 数动词 |
| **K2 跨度** | 涉及的路径前缀 ≥2 个不同目录 | 全在同一个目录 | `find` / 数路径段 |
| **K3 交付物** | 任务书列出的产物 ≥2 类 | 只有一类（例如「只出报告」） | 数条目 |
| **K4 证据源** | 结论必须交叉验证（如「确认某 API 行为」需查文档 + 查实现） | 单一来源即可定论 | 读任务书 |
| **K5 候选解** | 存在 ≥2 个互斥方案且都能自洽 | 只有一种做法 | 读任务书 |
| **K6 不可逆** | 触及对外接口 / 数据格式 / 迁移 / 删除 / 发布 / 权限 | 全部可回滚 | 读任务书 |
| **K7 未知前提** | 任务书里有「先查清 X 才能决定 Y」 | 前提全部给定 | 读任务书 |

**允许的输入只有三类**：

1. 用户任务书的**字面**内容（数动词、数交付物条目）
2. 侦察 Agent 的结构化返回（`slice_count`、`file_count`、`unverified[]`）
3. 仓库的**元信息**命令输出（`git status`、`find -type f | wc -l`、`wc -l`）

**禁止的输入**：任何需要打开文件才能做的判断（例如「这段代码看起来有并发问题」）。
**那类判断本身就是面板要产出的东西**，不能用来决定要不要开面板。

## 第 3 节：TIER 到面板规模的映射（2026-11-09 修订：取消降级路径）

| TIER | 分数 | **最少**成员 | 成员构成 | 递归上限 | 说明 |
|---|---|---|---|---|---|
| **T0** 简单 | 0 | **3** | 执行 1 + 批判 1 + 验证 1 | 1 层 | **没有"降级到 2 个"这条路** |
| **T1** 标准 | 1 | **5** | 执行、检索、批判、红队、验证 | 2 层 | 五职能齐备 |
| **T2** 复杂 | ≥2 | **9** | T1 五人 + 规划 + 裁决 + 2 个专项 | 3 层 | 专项角色按任务定制 |

### 3.0 为什么取消了 T0 的「降级到 2 个」

**本文件初版写的 T0 = 2 个成员（执行 + 审查），是误读了用户意图。**

用户原话「简单任务可降为『主Agent+审查Agent』」是对**主 Agent**（也就是运行框架的那个会话）说的——意思是「你自己判断，简单的事别硬开大面板」。

**它不是在说「提示词里要留一条降到 2 个 agent 的路径」。** 把这句写进框架，等于给所有任务预设了一条偷懒出口。

**修订后的原则**：

| 场景 | 谁来简化 |
|---|---|
| 用户手动跑的简单任务 | **主 Agent 自己判断跳过面板**（记 `triage_skipped`） |
| 框架自己决定 | **永远开满**，不降级 |

**所以 T0 现在是 3 个而不是 2 个**——即使最简单的任务，也要有「做、骂、验」三方。**下限从 2 提到 3，上限从 7 提到 9。**

### 3.1 为什么不允许「主 Agent 亲自执行」

`protocol.md` §1.2 的 L0 禁止主 Agent 读源码、写代码。**这条不放宽。**

**主 Agent 不得以「任务简单」为理由：**

| ❌ 不许做 | 为什么 |
|---|---|
| 自己读代码、自己写文件 | 违反 L0 |
| **把「要不要开面板」这个决定推回给用户** | 用户的指令是「你指挥手下干活」，不是「每件事都来问我」 |
| 静默降到 3 个以下 | 「极限多 agent」会被悄悄打折 |

**正确做法**：按 TIER 判定给的面板规模开，**该 9 个就 9 个**。
如果用户事前说过「这个任务按简单处理」，那是用户行使简化权，不是主 Agent 自作主张。

**主 Agent 没有简化权，只有执行权。**

### 3.2 极限多 Agent 的含义

用户要求「极限多 agent」。具体到本框架：

| 维度 | 上限 | 依据 |
|---|---|---|
| T2 最小成员 | 9 | 五职能 + 规划 + 裁决 + 2 专项 |
| T2 递归 | 3 层 | Claude Code 官方 subagent 嵌套上限就是 3 |
| 单 Agent 可再派 | 5 个 | 扇出系数，可调 |
| 总 agent 数 | **200**（T2） | `protocol.md` §6 |
| 并发 | 由 harness 决定 | `detect-harness.mjs` |

**理论最大值**：9 × 5 × 5 × 5（3 层）= 1125，受 200 总上限约束。

**这不是"上限"，是"目标"**——用户说「token 不是约束」。如果任务够复杂，就该开到接近这个数。

### 3.3 六个专家角色的边界

| 角色 | 职责 | **不做什么** | 对应 wrapper |
|---|---|---|---|
| **执行** | 产出实际成果（代码、分析、文档） | 不自我验收 | `audit-specialist` / `fix-worker` |
| **检索** | 找全相关材料、文件、先例 | 不做判断，只列清单 | `recon-scout` / `sweep-scout` |
| **批判** | 攻击执行者的**结论是否成立** | 不找覆盖缺口 | `critique-panel`（skeptic） |
| **红队** | 攻击**整个方案的失败路径** | 不评单条结论真伪 | `critique-panel`（devils_advocate） |
| **验证** | 独立重跑，确认结果可复现 | 不读执行者的自述 | `verifier` |
| **规划** | 拆解任务、判定 TIER | 不执行、不评判 | **新增 `planner`** |

**「批判」与「红队」的区别**（这是最容易混淆的一对）：

| | 批判 | 红队 |
|---|---|---|
| 攻击对象 | **这条结论对不对** | **这个方案会不会失败** |
| 典型问题 | 「这个 bug 真能触发吗？」 | 「如果整个方法就是错的呢？」 |
| 成功标准 | 移除了多少条不成立的结论 | 找到多少个未被考虑的失败路径 |
| 看什么 | 证据链 | 前提假设 |

## 第 4 节：信息可见性（防止交叉污染）

**用户要求「子 Agent 必须独立分析」。独立的前提是信息隔离。**

| 角色 | 应该看到 | **不应该看到** |
|---|---|---|
| 批判 | 执行者的结论 + 证据链 | 执行者的推理过程、其他批判者的结论 |
| 红队 | 任务书 + 整体方案 | 所有执行者的具体结论（否则会被锚定） |
| 验证 | 原始任务 + 验收标准 | 执行者的一切自述（已有规则 `verifier.md`） |
| 规划 | 任务书 | 任何执行结果 |

> **反直觉但重要**：红队**不该看执行者的结论**。看了就会被锚定成「找结论里的错」，而不是「找方案本身的问题」。这个分工在 `wave3-critique.md` 里已有先例（Arbiter 只看结构化字段，不看叙述正文）。

## 第 5 节：递归派生的上界（2026-11-09 修订：放宽到 3 层）

用户要求「允许递归派生子 Agent」。原版写 2 层，**用户要「极限」，改为 3 层**。

<!-- RECURSION-DEPTH-TABLE -->
| TIER | 递归上限（层） |
|---|---|
| T0 | 1 |
| T1 | 2 |
| T2 | 3 |

> **上面这张表是「递归上限」的唯一事实来源。** `wrappers/planner.md` 的
> `recursion.max_depth` 约束、`tools/check-plan.mjs` 的运行时门槛、本节下方的说明，
> 全部以它为准。改这里的数字必须同时改 `wrappers/planner.md` 的同名表——
> `tools/check-enum-consistency.mjs` 会逐 TIER 比对，不一致直接红。

**为什么 T0 是 1 层而不是 0**：简单任务也常需要一层助手（执行者派一个查文件的）。
0 层等于「执行者不许再派」，与「极限多 agent」相悖。

**为什么 T2 是 3 层而不是 2**：见下表「官方限制」一行——harness 本身允许 3 层，
把框架的自限压到 2 只会让复杂任务拆不细。**harness 更低时由 `compatibility.md`
§2.2 统一降级（L-B = 2 层、L-C = 无递归），而不是在这里写小。**

每层派生必须继承：零写入、证据标准、失败分类规则

**为什么是 3 层而不是无限**：

| 依据 | 内容 |
|---|---|
| 官方限制 | Claude Code `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` 默认 **3** |
| 上下文寿命 | 每层结果都要回到某处，无处可去时会静默丢失 |
| 可观测性 | 4 层以上的失败，主 Agent 已经无法定位是哪一层 |

**扇出系数**：单个 Agent 最多再派 **5** 个。三层理论最大值 9 × 5 × 5 × 5 = 1125，**受 `protocol.md` §6 的 200 总上限约束**。

**达到上限时的行为**：不静默截断，而是**出报告说明「因总 agent 上限停止展开」**，`status: PARTIALLY_CLOSED`。

> **2026-11-16 修正痕迹**：本节此前只在散文里写「T0 → 1 层 / T1 → 2 层 / T2 → 3 层」，
> 而 `wrappers/planner.md:137` 写的是「T0=0 / T1=1 / T2=2」——**同一框架两套数字**。
> 实战（field-test-1）里 agent 读到 planner 的 2，就按 depth 2 保守执行，并在收尾
> 报告里把这写成「框架文档/闸门矛盾」。现已把层数改成结构化表格（上面的
> `RECURSION-DEPTH-TABLE`），并加校验器逐 TIER 比对两个文件。
> 结论：**triage 的 3 是对的，planner 的 2 是旧副本**。

## 第 6 节：与审计模板的关系

**TIER 只决定「开多大面板」，不决定「怎么做审计」。**

| 场景 | TIER 判定 | 使用的模板 |
|---|---|---|
| 代码审计 | T2（K2/K3/K4 通常为 1） | **五波次**（侦察→宽扫→深挖→锐评→报告）+ 面板 |
| 文档写作 | T1 | 面板五角色 |
| 单文件修改 | T0 | 执行 + 审查 |
| 快速问答 | T0 | 执行 + 审查 |

**五波次不是被替换，而是「代码审计」这个领域的专业模板。** 面板制是通用骨架，五波次是插进骨架的专业流程。

> **这一条是 2026-11-09 三个决策的第二个的答案**：不是替换、不是叠加，而是**模板选择**。
> `scale-mapping.md` 的六字段输入契约（`slice_count` 等）只在「代码审计模板」里有效，通用面板不需要它。**契约不失效，只是适用范围被限定了。**

## 第 7 节：自检

主 Agent 在派发前必须回答：

| 检查 | 通过条件 |
|---|---|
| TIER 已判定 | 七项各有 0/1，总分已算 |
| 成员数达标 | **T0≥3 / T1≥5 / T2≥9** |
| 角色已分配 | 每个成员有明确角色，无遗漏 |
| 递归已定界 | 明确本任务允许几层（T0≤1 / T1≤2 / T2≤3） |
| 信息隔离 | 每个成员知道「不该看到什么」 |
| 不违反 L0 | 主 Agent 自己没有承担任何执行角色 |
| **未擅自降级** | 不得超过规定成员数下调；确实要下调时，只能由**用户**决定，主 Agent 不得自行判断 |

**七项缺一不可。缺任何一项不得派发。**

### 7.1 什么情况才允许问用户

**主 Agent 不是「有事就问」，也不是「一律不问」。**

参照 `dsh-superagent` 的注意力模型（`docs/000-philosophy.md:12`），只有三种情况可以主动开口：

| # | 情形 | 机械判据 |
|---|---|---|
| (a) | 有可交付结果已落盘，用户能用它做决定 | `report.final_report_path` 存在 |
| (b) | 出现了必须由人裁决的事项 | `open_items` 里 `kind == HUMAN_DECISION_REQUIRED` 且 `blocking` |
| (c) | 本轮已终止且无法自动续 | `STALLED` / `MAX_ROUNDS` / `BLOCKED` |

**其余时间保持沉默，继续推进。**

**「要不要开面板」不在上述三条之内**——那是主 Agent 自己的判定职责，不是需要用户裁决的事项。

> **2026-11-09 删除重复小节**：本节初版还有一个「§7.1 唯一的简化入口」，
> 里面写「返回用户：按规则此任务属 T1，需 5 个 agent，你若认为是简单任务，确认后我按 T0 开 3 个」。
> **那与上一节（以及 §3.1「主 Agent 没有简化权，只有执行权」）直接矛盾**，
> 而且它正是用户明确反对的「把决定推回给用户」。已删除。
>
> 正确的做法见 §3.1：**按 TIER 判定开，该 9 个就 9 个。**
