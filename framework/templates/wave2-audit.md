# templates/wave2-audit.md

> **加载时机**：加载前必须已加载 evidence-policy.md 和 output-contract.md。
> **职责边界**：只负责“审计Agent在切片内如何只针对一个维度产出有证据的发现”，不重新定义证据结构或返回格式。
>
> 本文由 DeepSeek 分享对话第 11 轮抽取。**第 1–2 节与第 5–6 节仍为原文**；第 3 节已重写为「不复述 `evidence-policy.md`，只列三条特有加强」，第 4.5–4.7 节为后续实测新增。改写理由见各节的行内说明。

## 第 1 节：审计Agent的职责边界——三做三不做

**做**：

1. **只审计一个维度**。审计Agent在派发时被指定一个 `dimension` 值，取值来自 `logic` / `concurrency` / `security` / `error-handling` / `data-consistency` / `contract`。该维度之外的任何问题，即使看起来再明显，也**不得**写入 `findings`。
2. **只审计一个切片**。审计Agent只接收一个 `slice_id` 及其 `files` 列表，只读取这些文件（以及切片声明的 `shared_dependencies`）。它**不得**读取切片之外的文件来“补充上下文”，除非该文件在 `shared_dependencies` 中显式列出。
3. **只报告有代码证据的问题**。每一条 `finding` 必须满足 `evidence-policy.md` 的门 0。该文件已定义全部细则，本节不重复。

**不做**：

1. **不做跨切片推断**。如果审计Agent认为某个问题需要切片外的文件才能确认，它**不得**自行扩大读取范围，而是将该项写入 `findings`，`status` 为 `EVIDENCE_GAP`，并在 `missing_evidence` 中写明“需要读取 `<具体文件/符号>` 才能确认”。跨切片证据收集是主Agent的调度职责（派证据补采Agent），不是审计Agent的职责。Doubleword 的“bounded local context”原则在这里是硬边界：每个 worker 只看它的切片，不回传研究过程[^ref5]。
2. **不报风格问题或“建议”** 。`dimension` 之外的观察，即使是有价值的改进建议，也**不进入** `findings`。审计Agent可以将其写入 `payload.off_dimension_notes`（一个仅用于透传的字符串数组，不参与下游裁决），但**不得**把它们包装成 `CONFIRMED` 的发现。dsh-review 的教训是“reporting findings with a concrete failure scenario rather than a style opinion”，风格意见会稀释真正有证据的缺陷[^ref6]。
3. **不为凑数而报告低置信度发现**。如果审计Agent在切片中针对指定维度**没有找到任何满足门 0 的问题**，它**必须**返回一个 `NO_EVIDENCE_FOUND` 条目，写明 `searched_scope` 和 `searched_methods`，而不是从推测中“造”一个问题。ai-audit-orchestrator 的原则是“Evidence or silence”；`NO_EVIDENCE_FOUND` 是一个合法的、有价值的结论，不是失败。

## 第 2 节：维度定义与隔离纪律

审计Agent在派发时收到一个 `dimension` 参数。每个维度的审计**问题域**和**禁止越界**的边界如下：

| `dimension` | 审计问题域 | 禁止越界到 |
|---|---|---|
| `logic` | 条件分支错误、off-by-one、状态机非法转移、返回值语义错误 | 并发竞态、安全注入 |
| `concurrency` | 竞态条件、死锁、原子性缺失、共享状态未同步、异步等待泄漏 | 业务逻辑正确性、输入校验 |
| `security` | 注入、越权、敏感信息泄露、不安全的反序列化、路径穿越 | 性能问题、代码风格 |
| `error-handling` | 未捕获异常、错误吞没、静默失败、恢复路径缺失 | 逻辑分支是否“应该”存在 |
| `data-consistency` | 事务边界、部分写入、缓存与源数据不一致、幂等性缺失 | 安全漏洞、并发死锁 |
| `contract` | 函数签名与调用方不匹配、返回值类型违反、接口契约破坏 | 实现细节的逻辑错误 |

**维度隔离的硬规则**（**仅约束本文件即深挖波**；宽扫波 `wave2a-sweep.md` 故意让一个 Agent 看 6 个维度，见该文件第 2 节，两者不冲突）：

- 审计Agent**不得**在 `findings` 中报告 `dimension` 之外的问题。如果它在审计 `logic` 时看到一个明显的 `security` 问题，它**可以**将其写入 `off_dimension_notes`，但该条目**不会**被主Agent当作 `UNRESOLVED_FINDING` 送入锐评波。
- 同一 `slice_id` 的不同维度由**不同的审计Agent实例**负责。主Agent在派发时确保每个 `(slice_id, dimension)` 组合对应一个独立的Agent。这意味着一个切片可能被多个审计Agent并行读取，但每个Agent只报告自己的维度。SendraAI 的“domain isolation”正是这个模式：每个专家审计员运行一个为其领域严格校准的提示，而不是一个提示覆盖所有维度[^ref8]。
- 如果 `scale-mapping.md` 的映射表没有为小规模项目分配全部六个维度，主Agent**不得**让一个Agent同时承担多个维度。它应当按 `scale-mapping` 的规则**减少维度数量**（例如只派 `logic` 和 `security`），而不是让一个Agent“顺便也看一下并发”。一个Agent承担多个维度会重新引入 SendraAI 描述的 cognitive overload——单提示词同时检查多类问题时，模型会滑向容易发现的表面问题，漏掉需要深度追踪的缺陷[^ref9]。

## 第 3 节：门 0 在审计波的三条特有加强

`evidence-policy.md` 已定义门 0 的全部细则——逐字回显、Evidence/Inference 分离、运行时声明不得只引定义、`file:line` 格式。**本节不重复那些定义**，只列审计波特有的三条。其余情况按 `evidence-policy.md` 判定。

| # | 加强规则 | 与 `evidence-policy.md` 的关系 |
|---|---|---|
| **3.1** | **`quote` 必须自包含**：只引一个函数签名或变量名不算。必须引到包含问题表现的那几行（`if` 条件、循环边界、抛异常、锁的获取/释放）。跨不连续区域**不得**在一个 `quote` 里用 `...` 省略，必须拆成多个 `evidence` 条目，各带自己的 `file:line`。 | 收紧 §5「多行引用的边界」 |
| **3.2** | **`inference.alternatives` 不得为空**，除非明确写「无其他合理解释」+ 理由。声称「这里有竞态」时必须考虑：调用方是否已持锁、该函数是否只在单线程上下文被调用、框架是否提供隐式序列化。**列不出来 → Skeptic 直接返 `EVIDENCE_GAP`**，由主 Agent 派证据补采，**不得由主 Agent 替审计 Agent 补全**。 | 比 §2「列出所有合理解释」更硬 |
| **3.3** | **`CRITICAL` 的准入门槛**：审计 Agent **不得**把任何发现标为 `CRITICAL`，除非同时提供调用链证据（从入口到问题点的完整路径）或可复现触发条件。仅有定义位置 + 推断的，最高 `HIGH`。 | 本条**只存在于本文件** |

> **为什么 3.3 要单列**：审计波最容易出的问题不是「漏报」，是**严重性通胀**——把「看起来吓人」的东西标成 CRITICAL，锐评波和修复波就被低质量发现拖住了。把 CRITICAL 锁在「必须有调用链」后面，是一条零裁量的机械门槛。

## 第 4 节：切片内审计的覆盖纪律

审计Agent必须在 `payload` 中证明它**确实检查了整个切片**，而不是只读了其中一两个文件就返回。

**`searched_scope` 的必填性**：每个审计Agent的 `payload` 必须包含一个 `searched_scope` 对象：

```json
{
  "searched_scope": {
    "files_read": ["src/dispatch/pipeline.ts", "src/dispatch/worker-pool.ts", "..."],
    "files_in_slice": 7,
    "shared_dependencies_read": ["src/types/agent.ts"],
    "dimension_checklist": ["条件分支", "循环边界", "返回值语义", "异常路径"]
  }
}
```

`files_read` 必须与 `files_in_slice` 加上 `shared_dependencies_read` 的并集一致。如果某个切片文件**因为工具限制无法读取**，它必须出现在 `unreadable_files` 中并说明原因，**不得**静默跳过。`dimension_checklist` 是该维度的检查清单，审计Agent必须逐项确认“已检查”，而不是只写一个“已全面审计”的模糊声明。

**`NO_EVIDENCE_FOUND` 的完整要求**：如果审计Agent在切片中没有找到任何满足门 0 的问题，`findings` 数组必须至少包含一个条目：

```json
{
  "finding_id": "slice-07-logic-none",
  "dimension": "logic",
  "severity": null,
  "evidence": {
    "file": null,
    "line": null,
    "quote": null
  },
  "inference": {
    "claim": "在本切片中没有发现满足门0的 logic 维度问题。",
    "basis": "已读取全部7个切片文件，检查了条件分支/循环边界/返回值语义/异常路径。",
    "alternatives": []
  },
  "status": "NO_EVIDENCE_FOUND"
}
```

> **⚠ 契约警告（2026-11-01 修复，勿回退）**：此示例**必须**写 `"severity": null`，**不得**写 `"severity": "NONE"`。
>
> 原因：`components/output-contract.md` 第 2.2 节的 `severity` 枚举是闭集 `CRITICAL | HIGH | MEDIUM | LOW`，**不含 `NONE`**；同文件第 1 节明令「不允许自定义状态值」，第 4 节第 7 步「payload 枚举校验」会因此失败，整个实例被判 `CONTRACT_VIOLATION` 并**全部输出作废**。
>
> 这不是理论问题：`dsh-fcl-android-launcher` 的 round31 实跑中，**5 个切片**（`slice-04-eh-09` / `slice-08` / `slice-15` / `slice-16` / `slice-23`）正是因为照本示例写了 `"NONE"` 而被判契约违规；最后 Arbiter 以「证据已可核验，无需重派」把它们捞了回来——**这属于对契约的实质豁免，框架里没有这条合法路径**。
>
> `severity` 对 `NO_EVIDENCE_FOUND` 条目**不承载任何语义**，用 `null` 表达"不适用"是唯一合规写法。若某个 harness 不接受 `null`，正确做法是**从该条目省略 `severity` 键**，而不是发明新枚举值。

`status` 为 `NO_EVIDENCE_FOUND` 的条目**不进入**锐评波的 `target_finding_ids`，但主Agent在 `handoff-schema` 的 `closed_waves` 摘要中必须记录该切片的该维度已被审计。这防止下一轮或下一波因为“没有发现”而误以为“没有审计”。

## 第 4.5 节：可运行时验证的项目，必须真跑（2026-11-02 新增）

**问题**：`evidence-policy.md` 第 3 节要求"运行时行为声明不得只引定义位置"，但**它只规定了「不能只引定义」，没规定「应该去跑」**。在可执行的项目上（Web 站、CLI、脚本、有测试的库），只读代码能发现的问题**远少于**跑一遍能发现的。

**实测依据**（`D:\Web\style` round1，18 条发现中至少 6 条只能靠运行时确认）：

| 发现 | 只有运行时才能确认的部分 |
|---|---|
| 折痕错误态不解除 | 静态读代码看不出"折痕到底到了几 px"；必须读 computed style 才知 `::after` 高度 = 6px |
| 「松手恢复」无效 | 必须点完按钮再读 `--shift`，才知道回执说 20px 而实际仍 56px |
| 进度尺指针倒退 | 必须连续滚动并采样 `--rung`，才看到 3 → 1 的回跳 |
| 七个洞口不可聚焦 | 必须查 `document.querySelectorAll(':focusable')` 才知道数量为 0 |
| 减少动态模式左右失对称 | 必须切 `prefers-reduced-motion` 并滚动才看到 `opacity` 被定格在 1 |
| 主 CTA 点击无反应 | 必须真点一次并比对点击前后的 DOM/hash/scrollY |

**规则**：审计 Agent 在派发时若收到 `runnable: true`（或自行判断项目可运行），**必须**执行至少一次真实运行验证。

### 4.5.0 跑什么才算数：必须调用「公开 API 的主路径」（2026-11-10 实测新增）

**问题**：§4.5 只规定了「必须真跑」，没规定**跑什么**。于是「跑一次 `node --check`」或「import 一下没报错」也算完成了这条规则——而这**什么都测不出来**。

**实测依据**（ground truth 实验）：

被审代码库里有一个函数，`processTasks(tasks, {handler})`，它先 `enqueue` 所有任务、然后清空入参数组、最后拿**已清空的数组**去执行。**传入 3 个任务，返回 `[]`，一个都不跑。**

| 组 | 方法 | 是否发现 |
|---|---|---|
| A | 通读 + 跑脚本 + 自检 | ❌ 未发现 |
| B | 单遍通读 | ❌ 未发现 |
| D | 专门查「承诺 vs 实现」 | ✅ **发现** |

**D 组是怎么发现的**：它写了 3 行代码调用这个函数，打印返回值。

```js
const r = await processTasks([{id:'a'},{id:'b'},{id:'c'}], { handler: async(t)=>'ok' });
console.log(r.length);   // 期望 3，实际 0
```

**建议的做法**（不是硬规则——见下方实测）：

| # | 跑什么 | 为什么 |
|---|---|---|
| 1 | **公开 API 的主路径**：传典型输入，调用主要导出函数，**打印返回值** | 「跑通了不报错」和「跑出了正确结果」是两件事。上例中函数不抛错，只是返回空数组 |
| 2 | **一个已知会失败的输入**：非法参数、超限、空值 | 验证错误路径确实报错 |
| 3 | **对照用例**（**这一条是唯一的硬要求**） | 见下 |

**禁止**：把 `node --check`（语法检查）、`import` 成功、或跑一遍 lint **当作**完成运行时验证。它们证明的是「代码能加载」，不是「代码能工作」。

#### ⚠ 实测修正：上表的第 1、2 条是**建议**，不是硬规则

**我原本把这三条写成了硬规则，然后做了对照实验，结果没看到好处。**

3 组有规则 vs 3 组无规则，同一份代码（20 条缺陷），严格隔离：

| 组 | 规则 | recall 均值 |
|---|---|---|
| 有规则（3 组） | 强制主路径 + 失败输入 | **68.3%**（sd 11.5） |
| 无规则（3 组） | 自由发挥 | **73.3%**（sd 2.9） |

**规则让 recall 下降 5.0 点，Cohen's d = 0.59（中等效应）。**

**但要注意这个结论有多不稳**：有规则组的 sd 是 11.5，其中一组只有 55.0%，是个明显离群点。**去掉那一组，剩下两组均值 75.0%，和无规则组持平。** 也就是说「这条规则有害」这个判断，实际上是由一组数据支撑的。

**能确定的只有**：没有任何数据表明这条规则有益。所以降级为建议是对的，但理由不该写成「已证实有害」。

多漏的三条全是「跑起来看不出、只有读代码才知道」的：

| 缺陷 | 有规则组漏 | 无规则组漏 |
|---|---|---|
| 损坏 JSON 静默返回 `{}` | 1/3 | 0/3 |
| `clear()` 注释与实现不符 | 1/3 | 0/3 |
| `timeoutMs` 从未被用作超时 | 2/3 | 1/3 |

**推测机制**：强制要求「设计运行验证」会挤占读代码的注意力。**这是推测，没有直接证据。**

**所以现在的写法是**：把 1、2 条作为**建议**列出，不作为完成审计的必要条件。执行者可以根据被审项目的特点自行选择跑什么。

#### 唯一保留为硬要求的是「对照用例」

理由不是实验数据，而是逻辑：**没有对照，你无法区分「缺陷是真的」和「我的探针坏了」。**

六组实验里所有正确排除负例文件的，都做了对照：

```
「backoffDelay(10, {base:100, maxDelay:1000}) => 1000，说明上限夹取正确，
  缺陷仅在指数项」
```

这一句同时做了两件事：证明了缺陷在哪，也证明了探针能测出正确答案。

**对照不占额外注意力**——它只是「用同样的方法多测一个已知答案的对象」。

**证据格式**（`control_case` 必填，其余可选）：

```json
{
  "runtime_evidence": {
    "method": "node_cli",
    "control_case": "同一模块的 runWithConcurrency([1,2,3], 2, f) 返回 3 个结果——证明探针本身有效",
    "main_path": {
      "command": "node -e '...'",
      "expected": "返回 3 个结果",
      "observed": "返回 []"
    }
  }
}
```

### 4.5.1 允许的运行方式（与零写入原则兼容）

`protocol.md` 第 0 节禁止写入被审仓库。**运行验证不违反它，前提是遵守以下任一种隔离方式**：

| 方式 | 做法 | 适用 |
|---|---|---|
| **A · 只读观察** | 直接跑只读命令（`node --check`、`--dry-run`、`--list`、`--check`），不产生文件 | 有 dry-run 模式的项目 |
| **B · 隔离副本** | 复制到仓库外的临时目录（或已被 `.gitignore` 覆盖的路径），在副本里跑 | 会写产物的脚本 |
| **C · 服务 + 无头浏览器** | 起本地 HTTP 服务指向源目录（只读），用 headless Chrome 加载页面 | 静态站 / 前端 |
| **D · 沙箱容器** | 容器内挂载只读，产物写容器内 | 需要装依赖的重型项目 |

**硬规则**：
1. **不得在原目录产生新文件**。需要写盘时用方式 B 或 D。
2. **结束后必须清理**，并验证：`git status --short | grep -c '^??'` 与运行前基线一致。
3. **服务只能用 `127.0.0.1`**，不得对外监听。
4. **不得修改被审仓库的配置来"让它跑起来"**（改 `package.json`、装依赖）。跑不起来就如实报 `ENVIRONMENT`，计入 `failure_category`。

### 4.5.2 运行时证据的写法

运行时证据**必须**附可复现的命令与原始输出，不能只写结论：

```json
{
  "runtime_evidence": {
    "method": "headless_chrome | node_cli | test_runner | http_probe",
    "command": "chrome --headless --dump-dom http://127.0.0.1:8123/prototypes/S12/",
    "input": "点击 #reset-wall 一次",
    "observed": "01:已凿开 | 04:已凿开 | count: 已凿开 00 / 07",
    "expected_if_no_defect": "01:未开 | 04:未开 | count: 已凿开 00 / 07",
    "reproducible": true
  }
}
```

**没有 `command` + `observed` 原始输出的"我跑过了"，一律不采纳。** 这与 `evidence-policy.md` 第 8 节「引用必须可核验」是同一条原则在运行时证据上的应用。

### 4.5.3 与静态审计的分工

| | 静态审计（读代码） | 运行时验证（跑） |
|---|---|---|
| 擅长 | 逻辑错误、契约不符、死代码、路径拼写 | 状态漂移、时序问题、真实渲染值、可聚焦性、静默失效 |
| 不擅长 | 需要实测才能确定的数值 | 未执行到的分支、边界条件 |
| 成本 | 低 | 高（起环境、写脚本） |

**两者不是替代关系。** 实测中最好的发现都来自**两者交叉**：静态读代码发现"这里应该有个同步"，再跑一遍证实"确实没同步"。

## 第 4.6 节：标识符对账——静态即可发现的最高性价比检查（2026-11-02 新增）

**问题**：有一类缺陷，**契约的两侧各自都完全自洽**，只是标识符拼写不一致。静态通读两个文件都看不出问题，只有做**集合比对**才能发现。这类缺陷往往影响面极大，因为它是"整套机制级失效"，不是单点错误。

**实测依据**（`D:\Web\style` round2，S04 的阻断级发现）：

```css
/* style.css —— 写得完全正确 */
transform: rotate(var(--rot));           /* 84, 93, 161, 162, 163, 229, 234 共 7 处 */

/* index.html —— 也写得完全正确 */
<figure style="--span:5; --ar:0.862; --r:-1.1deg; --lift:-16px; ...">   /* 9 处 */
```

**CSS 消费 `--rot`，HTML 定义的是 `--r`。差一个字母。** 结果：CSS 自定义属性替换失败 → 整条 `transform` 声明失效 → 九块纸全部零旋转，入场动画、hover 位移、降级档一起失效。

**这个缺陷的可怕之处**：
- 两个文件单独看都是对的，代码审查通不过肉眼；
- 影响面是"页面核心视觉签名"（标题还写着"没有一条对称边"）；
- 只有 `grep var(-- 与 --定义` 求差集才能发现。

### 4.6.1 机械对账步骤（不需要理解代码）

对每个切片执行**四类标识符对账**：

| 标识符类型 | 定义侧 | 消费侧 | 差集含义 |
|---|---|---|---|
| **CSS 自定义属性** | `--name:` 出现在声明里 | `var(--name)` | 定义了零消费 = 死代码；消费了零定义 = **必然失效** |
| **DOM id** | `id="x"` | `getElementById('x')` / `#x` / `href="#x"` | 定义后无引用 = 死控件（假的互动对象） |
| **CSS 类（状态类）** | `.cls { }` 或 `classList.add('cls')` | `classList.toggle/remove` | 有 add 无 remove = 状态无法复位 |
| **动画/关键帧** | `@keyframes name` | `animation: name` | 有定义无引用 = 死代码；有引用无定义 = 静默无效 |

**示例命令（CSS 自定义属性）**：

```bash
# 定义了但零消费
comm -23 \
  <(grep -rhoE '^\s*--[a-z-]+:' --include="*.css" --include="*.html" . | sed 's/[: ]//g' | sort -u) \
  <(grep -rhoE 'var\(--[a-z-]+' --include="*.css" . | sed 's/var(//' | sort -u)

# 消费了但零定义
comm -13 \
  <(grep -rhoE '^\s*--[a-z-]+:' --include="*.css" --include="*.html" . | sed 's/[: ]//g' | sort -u) \
  <(grep -rhoE 'var\(--[a-z-]+' --include="*.css" . | sed 's/var(//' | sort -u)
```

**示例命令（DOM id）**：

```bash
for id in $(grep -rhoE 'id="[a-zA-Z0-9_-]+"' --include="*.html" . | sed 's/id="//;s/"//' | sort -u); do
  n=$(grep -rc "$id" --include="*.html" --include="*.js" --include="*.mjs" . | awk -F: '{s+=$2} END {print s}')
  [ "$n" -le 1 ] && echo "DEAD_ID: $id"
done
```

### 4.6.2 判定规则（差集不等于缺陷）

**差集非空时，每一条都必须判定归属**，不得一律当 bug：

| 差集项 | 可能的判定 | 如何处理 |
|---|---|---|
| 定义零消费 | **死代码**（可删） / **拼写错误**（真 bug） / **动态消费**（脚本里拼字符串，grep 不到） | 必须查第三种：`grep` 变量名片段确认没有动态拼接 |
| 消费零定义 | **必然失效**（除非有 JS 运行时注入） | 查是否有 `setProperty('--name'` 动态注入 |
| id 定义零引用 | **假控件**（真 bug） / **纯锚点**（CSS `:target`、`<label for>`） / **纯语义标记** | 查 CSS 里是否有 `#id` 选择器 |
| 有 add 无 remove | **状态泄漏**（真 bug） | 确认不是靠父元素重建（`innerHTML` 重铺）来复位 |

**这条规则很重要**：`--ri/--rj` 那 9 个变量确实零消费（死的），但 `quirkChar` 那个 id 虽然零脚本引用，却只是语义标记——**二者都不是同等严重的缺陷**。不分青红皂白地报"43 个死标识符"只会淹没真正的 bug。

### 4.6.3 为什么放在审计波而不是锐评波

这个检查**必须在审计时做**，不能留给下游：
- 它是**机械的**，成本极低（几条 `grep` + `comm`）；
- 它发现的是**机制级失效**，如果漏掉，后续所有基于该机制的发现都建立在错误前提上；
- Skeptic 和 Devil's Advocate 看到的只是单条 finding，**无法知道某个 finding 依赖的机制其实是死的**。

**建议把它写进 `wave2-audit.md` 的返回前自检清单**（第 6 节），作为必做项而非可选。

### 4.6.4 层叠级联冲突：`animation ... both` 会锁死后续状态类（2026-11-02 新增）

这是本轮**第三次**遇到同一形态，且它是**系统性**的，不是偶发：

**形态**：某个元素上有一条 `animation: ... both`（或 `fill-mode: forwards`），它结束后**继续占据**被动画的属性（通常是 `transform`）。CSS 动画产生的值在层叠中**高于所有普通声明**（与特异性无关），于是后续任何 `:hover` / `.is-xxx` 里写的 `transform` **全部失效**。

**实测证据**（`D:\Web\style`，同一形态出现 3 次）：

| 页面 | 被锁死的状态 | 用户可见后果 |
|---|---|---|
| S08 | `[data-zoom="on"] img { transform: scale(3.2) }` | 「看 1.2mm 套印错位」按钮点了画面不动 |
| S16 | `.slab.is-kicked .slab-in { animation: kick-back }` | 「点击块号回推 12px」从不发生 |
| S22 | `.sheet.is-folded .face--verso { transform: rotateY(-96deg) }` | 「翻一折露出背面」纸一毫米没动 |

**三次都伴随同一个倒挂**：降级档（`prefers-reduced-motion`）里 `animation: none`，所以**开了"减少动态效果"的用户能看到功能，普通用户看不到**。

**全仓统计**（机械可算）：

```
同时具备「animation … both」与「状态类改 transform」的 CSS 文件：11 个
S04(1/7) S05(2/2) S09(5/2) S11(8/1) S12(3/3) S13(4/1)
S15(2/1) S16(12/1) S17(4/2) S18(2/3) S22(6/3)
                                    （both 数 / 状态类改 transform 数）
```

**建议的检测脚本**：

```bash
# 找出可疑文件：既有 animation…both，又有状态类改 transform
node -e "
const fs=require('fs'),{execSync}=require('child_process');
for(const f of execSync('git ls-files',{encoding:'utf8'}).trim().split('\n').filter(x=>x.endsWith('.css'))){
  let s='';try{s=fs.readFileSync(f,'utf8')}catch(e){continue}
  const both=(s.match(/animation:[^;}]*both/g)||[]).length;
  const stateTx=(s.match(/\.is-[a-z-]+[^{]*\{[^}]*transform:/g)||[]).length;
  if(both&&stateTx) console.log('SUSPECT',f,'both='+both,'stateTx='+stateTx);
}"
```

**判定规则（差集不等于缺陷）**：命中只说明**存在风险**，还必须确认三件事才能定级：

1. **是否同一元素**？`animation` 加在 A 元素、状态类改的是 B 元素的 `transform` → 无冲突。
2. **动画是否已结束并保持**？`both`/`forwards` 才有锁死效应；`none`/`backwards` 不锁。
3. **状态类是否真的需要改该属性**？若状态只改 `opacity`/`background`，不受影响。

#### 4.6.4.1 为什么"是否同一元素"不能靠选择器文本判断（2026-11-02 实测）

**我试过写脚本做选择器文本比对，结果漏掉了最严重的两例。**

脚本逻辑是「动画规则的选择器主体」与「状态规则的选择器主体」做前缀匹配，它只找出 3 处，**漏了 S08 和 S22**：

| 页面 | 动画规则 | 状态规则 | 为什么文本比对不出来 |
|---|---|---|---|
| **S08** | `.specimen img` | `.specimen[data-zoom="on"] img` | 选择器文本**不同**（后者多了属性选择器），但**指向同一批 DOM 元素** |
| **S22** | `[data-rise].in` | `.sheet.is-folded .face--verso` | 选择器文本**毫无共同前缀**，但同一个 `<div>` **同时匹配两者** |

**结论：这个判定必须用 DOM，不能用文本。**

```javascript
// 正确做法：在浏览器里逐个元素判断
for (const el of document.querySelectorAll('*')) {
  // 1. 该元素身上有没有 fill:both/forwards 且已结束、且动画了 transform 的动画？
  const stuck = el.getAnimations().some(a =>
    ['both','forwards'].includes(a.effect.getTiming().fill) &&
    a.playState === 'finished' &&
    a.animationName && transformAnimates(a.animationName)
  );
  if (!stuck) continue;
  // 2. 激活某个状态后，它的 computed transform 变不变？
  const before = getComputedStyle(el).transform;
  activateState(el);              // classList.add / forcePseudoState
  const after = getComputedStyle(el).transform;
  if (before === after) {/* 真实失效 */}
}
```

**代价与收益**：DOM 扫描需要起浏览器、逐个元素跑，比 `grep` 贵一到两个数量级。但**静态比对会漏掉最严重的情况**，而这类缺陷的用户可见后果是"点了完全没反应"——**漏掉它的代价远大于多跑一次浏览器**。

**实践建议**：
- 先用 `grep` 粗筛出「同时有 animation…both 和状态类改 transform」的**文件**（便宜，缩范围）；
- 再对筛出的文件**用 DOM 逐个元素验**（贵，但准确）；
- **不得**用选择器文本比对代替 DOM 验证。

#### 4.6.4.2 DOM 验证的实测收益：11 个候选 → 5 个真案（2026-11-02）

`D:\Web\style` 用 DOM 全量扫描 31 个页面，其中 11 个页面出现了「动画锁死 + 状态类改 transform」的候选，逐个判定结果：

| 判定 | 数 | 页面 |
|---|---|---|
| **CONFIRMED** | **5** | S08 / S16 / S18 / S22 / S25 |
| **FALSE_POSITIVE** | 5 | S01 / S04 / S10 / S12 / S15 |
| **NO_VISIBLE_EFFECT** | 1 | S28（技术上自指但值无差） |

**必须说清一个口径问题（2026-11-03 更正）**：这里的 11 个页面与「静态命中的 11 个文件」**不是同一个集合**。

| | 名单 |
|---|---|
| 静态命中（grep 命中） | S04 S05 S09 S11 S12 S13 S15 S16 S17 S18 S22 |
| DOM 判定（实际验过） | S01 S04 S08 S10 S12 S15 S16 S18 S22 S25 S28 |
| **重叠** | S04 S12 S15 S16 S18 S22（**6 个**） |

被判 `FALSE_POSITIVE` 的 S01 / S10 / S28 **不在静态命中名单里**（它们是 DOM 扫描时才被探针误触发的）；而静态确实命中的 S05 / S09 / S11 / S13 / S17 在 DOM 裁决表里**没有对应结论**。

**因此「5/11 ≈ 45%」是两个不同实验的分子除以另一个实验的分母，这个百分比不成立。** 旧版本曾把它当作「静态比对的误报率」写进规则，是错的。

**能成立的表述只有两条，且必须分开说**：

1. **DOM 全量扫描**（11 个验过的页面）→ **5 个 CONFIRMED**：S08 / S16 / S18 / S22 / S25。
2. **其中静态 grep 能命中的是 3 个**（S16 / S18 / S22）；S08 和 S25 静态认不出——S08 的状态选择器是 `[data-zoom="on"]` 而非 `.is-*`，静态正则匹配不到类名形态。
3. 静态命中的另 3 个（S04 / S12 / S15）经 DOM 验证**全部是误报**；静态命中的 S05 / S09 / S11 / S13 / S17 **从未被 DOM 验证过**，结论未知。

**所以静态扫描的准确率无法从这批数据算出**——分子（DOM 裁决的真实结果）和分母（静态命中集合）不同源。能说的是：**已验过的那部分里，静态命中 6 个、真案 3 个、误报 3 个**。

**为什么误报仍然值得警惕**：全仓有 **583 个被 `both` 锁死 transform 的元素**，但绝大多数动画是 `translateY(14px) → 0` 收尾——**作者值本来就是 `none`，锁死与无锁视觉等价**。只有「状态规则也改 `transform`」时才真失效。**所以「有多少元素被锁」和「有多少真案」是两个数量级的事。**

**误报的四个典型成因，每个都值得写进检查清单**：

| 成因 | 实例 | 防法 |
|---|---|---|
| **选择器过度匹配** | S01：扫描器把纯类名化合物中和成 `*`，`footer` 被误判命中 | 用真实 DOM 匹配，别用文本归一化 |
| **类名被别处使用** | S04：`.reveal` 是 JS 追加给 `.note` 的，从不加到 `.slip` 上 | 查该类**实际被 `classList.add` 到哪些元素** |
| **容器内其他元素被锁** | S12 / S15：该元素 `lockAnims: []`，是兄弟元素被锁 | 必须按**元素身份**判定，不是按容器 |
| **自指但值无差** | S28：`--push` 只在该类自身规则里赋值，加类前后相同 | 对比激活前后 computed 值，不只看有无 |

**结论**：这类缺陷的**静态扫描结果只能当候选，不能当结论**。报告里必须标注「静态推断」还是「DOM 实证」。

**修复方向**（不要求审计 Agent 做，但报告里应给出）：

| 方案 | 做法 |
|---|---|
| 分离元素 | 动画加在外层 wrapper，状态类改内层元素的 `transform` |
| 改用过渡 | `animation` 换成 `transition`，过渡不产生持续占用 |
| 状态后用 `animation: none` | 状态类里显式 `animation: none`，释放锁定（**这正是降级档碰巧生效的原因**） |
| 用 CSS 变量中转 | 动画只改变量，`transform: rotate(var(--rot))` 由普通声明消费 |

> **为什么这条必须写进框架**：三次失效都发生在**"页面看起来完全正常"的地方**——CSS 语法没错、选择器没错、值也没错，只是层级关系被动画态压过。纯文本审查几乎不可能发现，必须靠**运行时读 `getAnimations()` + computed transform** 才能确认。

### 4.6.5 注释里的历史是最好的缺陷线索（2026-11-02 新增）

**本轮两条 HIGH 都是靠"读注释"找到的**，不是靠从零扫描：

| # | 线索 | 顺着它发现 |
|---|---|---|
| 1 | `check-texture.mjs` 注释逐字记录了正则 `(?:^|\})` 的 bug：「`}` 被匹配消耗后下一个模式要求 `^` 或 `}`，于是相邻规则只看到隔一条……**测试盲区保护了缺陷**」 | `verify-prototype.mjs:76` **原封不动还在用第一版正则**，而且**报反了**——真违规时报通过，修复后反而误报 |
| 2 | `check-stale.mjs:48-53` 注释：「`at` 缺失/非法从前是 `continue` 静默跳过 —— 那等于「无法判定」被当成「不陈旧」……改为报出来」 | 同一文件的产品入口分支（`:118-123`）**仍是 `catch { continue }`**，一个字没改 |

**规律**：**修复者已经帮你定位了缺陷形态。** 当有人在某处修了一个模式并留下注释，同类代码路径很可能仍然裸露。

**执行规则**：

```
0. 【最优先】注释是**线索**，不是**结论**。
   读到「已修复 / 曾经的坑 / ⚠️ 2026-xx-xx」这类注释时，
   不得直接采信。必须用 `git log -S '<被修的模式>'` 验证那次修复真的发生过。
   验证不通过（找不到对应提交）→ 按 SUSPICIOUS_COMMENT 立条，不走线索流程。

1. 提取该注释描述的病态模式（正则？异常吞没？路径拼接？编码假设？）
2. 在全仓搜索同模式的其它出现
3. 逐条判断是否已修；未修的，按同样的严重性立条
```

> **⚠ 2026-11-10 为什么加第 0 条**（红队 A9）：本节的定位是「注释是最好的缺陷线索」，这让它天然成了一个**投毒面**——被审仓库的作者只要在代码里写一行 `// ⚠️ 2026-10-31 已修复：这里曾经有竞态`，就能让一条线索看起来已被处理过。
>
> **这条无法机械校验**（「Agent 有没有把注释当指令」在产物上看不出来）。可机械化的只有一半：若 Agent 报告了 `SUSPICIOUS_COMMENT`，它必须带 `file:line` 并走门 0。**这是一个已知的、只能靠提示词弥补的缺口**，`docs/analysis/` 里已登记（`START-HERE.md:180`「产物内容不可信…未修」）。

**为什么这条价值最高**：

- 它把"找 bug"变成"核对修复的完整性"，搜索空间小得多；
- 它命中的都是**作者自己认定过是缺陷**的形态，可信度天然高，不需要再争论"这算不算 bug"；
- 它专抓**"修了一半"**——这类缺陷特别危险，因为它给人"这个问题已经处理过了"的错觉。

**实测统计**：`D:\Web\style` 的项目代码里有大量带日期的修复注释（`⚠️ 2026-10-31`、`第一版…第二版…第三版`），**每一处都值得顺着查一遍**。本轮顺着 2 条注释就找到了 2 条 HIGH。

## 第 4.7 节：被审项目自带的自检，必须先验证它自己（2026-11-02 新增）

**问题**：很多项目带一堆 `check-*.mjs` / `verify*.mjs`。审计 Agent 容易**采信它们的绿灯**——"项目自己都说通过了"。但**这些脚本自身可能是坏的**。

**实测依据**（`D:\Web\style` round2，35 个验证脚本中）：

| 缺陷 | 数量 | 表现 |
|---|---|---|
| 无退出码、无断言 | **6 个** | 只 `JSON.stringify` 到 stdout 然后正常退出 |
| 断言在匹配从不出现的字符串 | 2 个 | 正则字面量 `有别的一个`，生产串是 `另有一个` |
| 运行即崩溃 | 3 个 | `s.text` 不存在 / 正则返回 `null` / 路径拼错 |
| "空集即通过" | 2 条断言 | `vis === rows` 在 `rows === 0` 时为真 |
| 验证"守卫是否摆设"的脚本自己 exit 0 | 1 个 | 打印"✗ 守卫静默失效（摆设）"后仍返回 0 |

**最严重的形态是"防护的防护"失效**：被测代码把异常 `try/catch` 成 `console.warn`（为了不影响主流程），而验证工具只订阅 `Runtime.exceptionThrown`（未捕获异常）。**两个各自合理的决定，组合成完整盲区**——模板层整个掐死，验证脚本仍报"0 错误、exit 0"。

### 4.7.1 四步抽验（对每个自带检查脚本）

审计 Agent 必须抽验**至少 2 个**（若项目 >10 个，抽验 ≥10%）：

| # | 检查 | 方法 | 不通过意味着 |
|---|---|---|---|
| **a** | 有没有失败路径 | `grep -E "process\.exit\|assert\|throw new Error"` 命中数为 0 | 恒 exit 0，结论不可采信 |
| **b** | 断言是否可能空转 | 找 `∀` 形式断言（`allEvery`/`vis === rows`/`x.every`）却无 `> 0` 存在性前提；找字面量 `true` | 数据删光仍 PASS |
| **c** | 断言目标是否真实存在 | 用第 4.6 节的对账方法查断言里的字符串常量/标识符 | 断言永假，是死代码 |
| **d** | **注入故障看它变红**（决定性） | 制造一个已知缺陷，跑脚本，看退出码是否非 0 | **前三条都过了也要做这条** |

**只有 (d) 能证明检查有效。** (a)(b)(c) 是静态推断，(d) 是实测。

**凡 (a)(b)(c) 任一不通过的脚本，其历史 PASS 结论一律不得采信**，必须在报告中标注 `UNRELIABLE_SELF_CHECK`。

### 4.7.2 "降级即失明"原则

当代码里有 `catch` 后**转日志而非抛出**的地方，验证必须显式检查该日志通道：

```
若代码中有 catch → console.warn / console.error / logger.warn：
  验证脚本必须订阅对应的日志通道（CDP 的 Runtime.consoleAPICalled，
  或读日志文件），而不能只订阅异常事件。
否则：降级会被误判为正常。
```

这是 `evidence-policy.md` 第 3 节「异常被抛出不等于会传播」的延伸——**异常被捕获也不等于被记录**。

### 4.7.3 交付证据的时效校验

**引用项目自带的验收报告时，必须比对 mtime**：

```bash
# 证据文件 vs 它声称验证的代码文件
stat -c '%y %n' deliverables/.../verify-result.txt
stat -c '%y %n' prototypes/.../style.css
```

| 情形 | 判定 |
|---|---|
| 证据 mtime **晚于**被测代码 | 可采信 |
| 证据 mtime **早于**被测代码 | **`STALE_EVIDENCE`**，不得采信，必须注明 |

**实测**：`D:\Web\style` 的 `S03-verify.txt` 比 `style.css` 早 4 天、比 `verify.mjs` 早 8 天。该证据说 "19/19 PASS"，实跑是 **18/19 FAIL**，且红的那条断言对象后来被设计**刻意移除**了。

**一张旧的 PASS 报告会被当成当前状态——这是审计里最廉价也最容易犯的错误。**

## 第 4.8 节：主动检查清单——补上「想不到要查」的盲区（2026-11-11 实测修订）

### 4.8.1 问题：某些缺陷，读一遍代码是发现不了的

**实测依据**（6 个独立 agent × 3 轮 = 18 次审查，同一份代码）：

三条缺陷**零命中**：

| ID | 缺陷 | 命中 |
|---|---|---|
| GT-011 | `peek()` 返回队列内部的活引用 | **0/18** |
| GT-012 | `remove(id)` 缺 id 校验，而同族的 `enqueue` 校验了 | **0/18** |
| GT-013 | `capacity` 校验让 `NaN` / `Infinity` / 小数通过 | **0/18** |

```javascript
// GT-013：每一行都"对"，只是少排除几种值
if (typeof capacity !== 'number' || capacity <= 0) {
  throw new TypeError('capacity must be a positive number');
}
// typeof NaN === 'number' 为 true，NaN <= 0 为 false
// → capacity = NaN 时全部 20 次入队成功
```

**为什么难**：代码每行都对；正常输入下一切正常；触发需要特定的值；没有测试会失败。

### 4.8.2 解法：一份「必查清单」，逐项给结论

**对每个被审计文件，逐项回答下面 8 个问题。答案必须是「命中 / 未命中 / 不适用」，不许跳过。**

| # | 模式 | 怎么查 | 证据 | 强度 |
|---|---|---|---|---|
| **1** | 返回值是否暴露内部状态 | 找 `return this.#x[...]` / `.get(...)`。返回的是不是内部容器的同一引用？调用方改了会不会反过来改内部？ | 已证实 | **硬检查项** |
| **2** | 同族函数的守卫是否一致 | 同一类里做同类事的多个方法，逐个对比参数校验 | 已证实 | **硬检查项** |
| **3** | 数值边界是否完整 | 「必须是正整数」的校验，是否排除了 `0` / 负数 / **`NaN`** / `Infinity` / 小数？**`typeof NaN === 'number'` 且 `NaN <= 0` 为 false** | 已证实 | **硬检查项** |
| **4** | 解析结果是否校验形状 | 拆成 4 个子问题分别答，见下方 §4.8.2.1 | 部分证实（8 条目标稳定中 4 条） | **硬检查项（须逐子问题答）** |
| **5** | 能力是否真的实现了 | 注释/配置项/函数名声称的能力（超时/重试/转义），实现里真做了吗？**搜它在全库的使用，看是不是只被定义、从未被调用** | 目标不稳定，但副作用最大 | **追问方向，非检查项** |
| **6** | 转义/编码的顺序对不对 | 多层替换里，先换 A 再换 B 会不会让 B 的产物被 A 二次转义？（先换 `<` 成 `&lt;`，再把 `&` 换成 `&amp;` → `&amp;lt;`，错；`&` 必须最先） | **已证实（三轮 100%）** | **硬检查项** |
| **7** | 边界值的符号处理 | 分页的 page、slice 的起止、数组下标——**负数**会怎样？`arr.slice(-60,-50)` 不报错但语义翻转 | **已证实（三轮 100%，sd 最小）** | **硬检查项** |
| **8** | 引用的绑定是否存在 | 每个调用的名字，在当前作用域里真的存在吗？**`import` 漏了某个名字，函数体里照用不误**——模块加载不报错，一调用就 `ReferenceError`。反过来也一样：定义了却从未使用 | 有真实样本，未做对照实验 | 建议 |

#### 4.8.2.1 模式 4 必须拆成 4 个子问题

实测（fixture2，18 条缺陷，3 轮）：模式 4 射程内有 8 条缺陷，**只有 4 条三轮稳定命中**，3 条时有时无，1 条从未命中。

原因：「解析结果是否校验形状」这个问法太笼统，agent 会挑最容易的那个子问题做，然后交差。**必须逐个回答：**

| 子问题 | 查什么 | 反例（fixture2 实测） |
|---|---|---|
| **4a 原型链键名** | 把外部数据当 map/dict 用时，查表是裸下标 `obj[key]` 吗？`constructor` / `__proto__` / `toString` / `valueOf` / `hasOwnProperty` 会取到继承成员 | `RULES[r.rule]` 裸下标 → `rule:'toString'` 被当成合法断言静默放行 |
| **4b 假值 vs 缺值** | 判「有没有填」用的是 `!== undefined` 还是 `!x`？`0` / `false` / `''` 是合法值还是缺失？ | `required: v => v !== undefined && v !== null && v !== ''` → `false` 被当作已填 |
| **4c 数值边界** | 外部来的数值，`NaN` / `Infinity` / 负数 / 小数 / `-0` 会被当合法值吗？ | `number: v => typeof v === 'number'` → `Infinity` 通过 |
| **4d 嵌套结构** | 对象里嵌套的对象/数组，每一层都校验了吗？`JSON.parse` 结果只验了外层呢？ | —（fixture2 无此形态，但属同一族的常见遗漏） |

**每个子问题对每个文件都必须给「命中 / 未命中 / 不适用」**，不许合并成一条答。

#### 4.8.2.2 模式 5 不要写成检查项

实测：模式 5 只对应 1 条目标缺陷，三轮里只命中 2 次（**不稳定**）。但它的总 recall 是四组里最高的（72.2%，其余为 64.8% / 53.7% / 27.8%）。

**因为它不是「找到一个东西」，而是「启动一条搜索链」。** 追着「这个 `escapeHtml` 怎么从来没人调用」查下去，会自然走到「那插值转义了吗」（XSS）、「转义函数本身顺序对不对」（二次转义）、「校验器的规则表怎么查的」（原型链）。

**写成 checklist 反而有害**——agent 会对着某一处发呆，把「已检查」打上勾就结束。

**正确用法**：把它当**追问方向**。审计时问自己「这个代码库里有没有定义了却没人用的东西？」，有的话顺着追，不要停在「确认它没被用」这一步。

#### 4.8.2.3 模式 8 的真实样本

某次验证用的「无缺陷基准」`store.js` 里，`#persist()` 调用了 `renameSync`，但第 4 行的 `import { ... } from 'node:fs'` 没把它列进去。**该类的 `set()` 一调用就抛 `ReferenceError`，整个写入路径 100% 失效**——而它旁边 15 条缺陷证明脚本没有一条走过这条主路径，所以一直没被发现。

这条值得单列，因为它同时踩中两个盲区：**静态看每行都对**（名字拼写正确、参数正确），**运行时才知道炸**（而且只在真正调用的那条分支上炸）。查法：
- 静态：把每个文件里「像函数调用」的标识符收集出来，对照该文件的 import 列表 + 本地声明（`tools/check-blindspots.mjs` 的 B4 规则）
- 动态：对每个公开方法各调一次（不是只调「主流程」），看有没有炸

#### 4.8.2.4 四组单加实验：哪个模式真的可靠

2026-11-11~12，在 fixture2（18 条缺陷：注入 5 + 原生 13）上做了 4 组 × 3 轮：

| 组 | recall 三轮 | 均值 | sd | **目标缺陷三轮都中** |
|---|---|---|---|---|
| P4 形状 | 50.0 / 61.1 / 83.3 | 64.8% | **16.8** | 4/8 |
| P5 能力 | 83.3 / 66.7 / 66.7 | 72.2% | 9.6 | **0/1** |
| P6 转义 | 11.1 / 33.3 / 38.9 | 27.8% | 14.6 | **2/2** |
| P7 符号 | 50.0 / 55.6 / 55.6 | 53.7% | **3.2** | **3/3** |

**按 recall 排是 P5 > P4 > P7 > P6，按目标命中稳定性排是 P6 = P7 > P4 > P5——完全相反。**

**判据应该用后者。** recall 会被「附带发现」拉高，而目标命中稳定性才说明「这条规则给了之后是否可复现」。

- **P7 最稳**（sd 3.2），**P6 精准**（目标 2/2，但只报 2–7 条）
- **P4 波动最大**（sd 16.8，同代码同提示词三轮差 33 点）→ 所以必须拆成 4a/4b/4c/4d

实测：模式 5 只对应 1 条目标缺陷，三轮里只命中 2 次（**不稳定**）。但它的总 recall 是四组里最高的（72.2%，其余为 64.8% / 53.7% / 27.8%）。

**正确用法**：把它当**追问方向**。审计时问自己「这个代码库里有没有定义了却没人用的东西？」，有的话顺着追，不要停在「确认它没被用」这一步。

| 缺陷类型 | 自由发挥（6 组） | 模式 1/2/3（3 组） | 差 |

| 注入型（明显坏掉的行为） | 70/78 = 89.7% | 32/39 = 82.1% | **−7.7** |

### 4.8.3 实测效果：两份代码库，方向一致

| 代码库 | 有清单 | 无清单 | recall 变化 |
|---|---|---|---|

**精确率的代价是真实的**：fixture2 上有清单组报了 17 条，无清单组报了 9 条，recall 分别是 100% 和 78.6%。

**所以怎么用**：先把开放式审查做完，再拿清单补一轮。不要在开放式审查之前就用清单——那会把注意力过早地锁死在 8 个方向上。

> **数据集不完整时，「两组打平」可能是考卷太简单，不是方法一样好。**

## 第 5 节：为 Skeptic 留下攻击面
## 第 5 节：为 Skeptic 留下攻击面

审计Agent的产出直接进入波次三，由 Skeptic 逐条攻击。因此审计Agent**必须主动暴露自己推断链中最薄弱的一环**，而不是把发现包装成无懈可击的结论。

**`alternatives` 的具体要求**：`HIGH` / `CRITICAL` 发现必须包含**至少两个**替代解释，每个都指向**一个可检查的条件**（「如果 X 成立，则该问题不成立」）：

- 替代 1：「如果调用方在调用前已通过 `withLock` 获取互斥锁，则竞态不存在。需检查 `src/routes/agents.ts:24` 的调用上下文。」
- 替代 2：「如果 `worker-pool` 的 `get` 方法本身是同步且 map 操作原子，则不会读到中间状态。需确认 `get` 的实现是否含异步等待。」

**有 `runtime_evidence` 时的额外要求**：`alternatives` 中至少一条必须解释「为什么运行时的观察可能不代表真实行为」（测试环境与生产不同、触发路径不典型）。

这形成了有用的压力：**审计Agent在发现阶段就必须思考「这个发现最可能错在哪里」**。没做到时 Skeptic 返 `EVIDENCE_GAP`，主 Agent 派证据补采 Agent，而不是让发现直接进入修复。

>   "identifier_reconcile": { "status": "DONE", "note": "CSS 变量差集 3 条，2 条死代码 1 条拼写错误" },
>   "self_check_audit":    { "status": "DONE", "note": "抽验 check-stale / verify-prototype，注入故障后均变红" },
>   "runtime_validation":  { "status": "SKIPPED", "note": "项目无 HTTP 服务，无头浏览器起不来，已在正文说明" }
> }
> ```
>
> `status` 只能取 `DONE` / `SKIPPED` / `NOT_APPLICABLE`。后两者**必须**给至少 10 字的 `note`——静默跳过等于没做。
>
> **自检**：`node <FRAMEWORK_ROOT>/tools/check-payload.mjs <你的产物> --role audit`，退出码非 0 就是不合规。

审计Agent在发出 `output-contract` 返回前，必须逐项确认：

| 检查 | 通过条件 | 失败动作 |
|---|---|---|
| **线索闭合** | 派发时给的每条 `lead_id` 都已处置：升级为 `CONFIRMED`、判 `REFUTED`、或标 `EVIDENCE_GAP` | **补做**。漏处置的线索视为未审计 |
| 维度单一 | `findings` 中每一条的 `dimension` 等于派发时指定的维度 | 移除非本维度条目至 `off_dimension_notes` |
| 切片内证据 | 每一条 `CONFIRMED` 的 `evidence.file` 属于 `files` 或 `shared_dependencies` | 标记为 `EVIDENCE_GAP`，写明需要的外部文件 |
| 门 0 合规 | 每一条 `CONFIRMED` 的 `evidence.quote` 来自本回合读取，`file:line` 存在 | 删除该条，或标记 `GATE_0_FAILED` |
| **自带自检抽验** | 已按第 4.7 节抽验项目的检查脚本（a 退出码 / b 空转 / c 目标存在 / d 注入故障） | 补做；(a)(b)(c) 任一不通过的脚本，其历史 PASS 不得采信 |
| **标识符对账** | 已按第 4.6 节执行四类对账（CSS 变量 / DOM id / 状态类 / 动画），差集逐条判定为「死代码 / 真 bug / 动态消费」 | **补做**。这是必做项，不是可选 |
| 行为声明有控制流证据 | 涉及运行时行为的发现附带调用链/触发条件/日志，而非仅定义位置 | 降级 `confidence: LOW`，`severity ≤ MEDIUM` |
| 运行时验证（可跑的项目） | 已按第 4.5 节执行至少一次真实运行，`runtime_evidence` 含 command + 原始输出 | 补做，或声明 `NO_EVIDENCE_FOUND` 并说明为何无法运行 |
| 替代解释 | `HIGH`/`CRITICAL` 发现至少有 2 个可检查的 `alternatives` | 补充替代解释或降级严重性 |
| 覆盖完整性 | `searched_scope.files_read` 覆盖 `files` + `shared_dependencies`，或缺失文件在 `unreadable_files` 中 | 补全 `searched_scope` |
| 无发现时诚实 | 没有 `CONFIRMED` 时，`findings` 包含至少一个 `NO_EVIDENCE_FOUND` 条目 | 补写 `NO_EVIDENCE_FOUND` |
| 无跨切片推断 | `inference` 中没有依赖切片外文件的结论，除非标记为 `EVIDENCE_GAP` | 将依赖外部证据的结论改为 `EVIDENCE_GAP` |
| 零写入 | 未修改被审仓库任何文件；实验在隔离环境完成并已清理 | **严重违规**，必须报告并恢复 |
| 不越界做风格建议 | 风格/改进建议不在 `CONFIRMED` 的 `findings` 中 | 移入 `off_dimension_notes` |

**「标识符对账 / 自带自检抽验 / 运行时验证 / 承诺兑现」四项是必做项，不是可选。** 它们各自对应一类**纯读代码发现不了**的缺陷，删掉任何一项都会留下一个系统性盲区：

| 必做项 | 只做静态审查会漏掉什么 |
|---|---|
| 第 4.6 节 标识符对账 | 契约两侧各自自洽、只有拼写不一致的**机制级失效**（CSS 消费 `var(--rot)`，HTML 定义 `--r`，差一个字母，九块纸全部零旋转） |
| 第 4.7 节 自带自检抽验 | 「项目自己说通过了」这个前提本身是坏的（实测 35 个脚本里 6 个无退出码、2 个断言空转、3 个运行即崩） |
| 第 4.5 节 运行时验证 | 状态漂移、时序问题、真实渲染值、可聚焦性、静默失效——这些**只有跑一遍才知道** |
| **第 4.8 节 承诺兑现** | **代码没写错、只是少做了一件事**的缺失型缺陷（JSDoc 说返回 boolean 但没 return、说只读但没 freeze）。实测：这是 ground truth 13 条缺陷里**唯一一条两个独立审查员都完全没发现**的。工具 `check-promises.mjs` 在 base 上 0 误报、在 injected 上抓到 2 条 |
