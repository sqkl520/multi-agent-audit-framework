# templates/wave2a-sweep.md

> **加载时机**：波次一闭合、`scale_decision` 写入账本之后。
> **职责边界**：只负责「在切片内快速定位可疑点，产出**线索**」。**不产出发现**，不做完整证据链，不进入锐评波。
>
> **你的返回会被 `tools/check-payload.mjs --role sweep` 机械校验**：
>
> | 规则名 | 触发条件 |
> |---|---|
> | `generated_without_generator_ref` | 把生成物当源码审计，却没引用生成器——改生成器才是修法 |
> | `histogram_mismatch` | `dimension_histogram` 各值之和与 `leads.length` 不等（直方图是覆盖率记账的唯一来源，对不上则覆盖率不可信） |
>
> 本模板此前一次都没点名这两条规则。
>
> **为什么需要这一波**：原设计要求「每个 `(slice_id, dimension)` 组合派一个独立实例」，6 个维度意味着 `N` 片要派 `6N` 个实例——85 片就是 510 个，是预算的 8.5 倍。反过来按「片数」派发，则每片只能审 1 个维度，等于悄悄放弃 5/6 的覆盖。**两遍制把这两件事分开：宽扫负责「不漏」，深挖负责「可信」。**

---

## 第 1 节：核心定义——线索不等于发现

| | **线索（lead）** | **发现（finding）** |
|---|---|---|
| 产出波次 | 本波（二A） | 二B 深挖 |
| 证据要求 | 只要 `file:line` + 一行原文 | 完整门 0：本回合 quote + Evidence/Inference 分离 + alternatives |
| 严重性 | **不判** | 必判（CRITICAL/HIGH/MEDIUM/LOW） |
| 进锐评波？ | **否** | 是 |
| 进最终报告？ | **否**（只进覆盖率统计） | 是 |
| 允许误差 | **高**：允许 70% 的线索在深挖阶段被证伪 | 低：每条都要经得起 Skeptic 攻击 |
| 每片 agent 数 | **1** | 按线索密度决定 |

**这条区分是本波全部设计的支点。** 如果线索被当成发现，就会污染下游、拉低信噪比；如果线索要求完整证据链，那它就退化成原来的审计波，算术重新崩掉。

## 第 2 节：一个 agent 看全部 6 个维度

**硬规则**：宽扫 Agent **不被指定单一 `dimension`**。它拿到的指令是「在这片代码里，按下面 6 个问题域快速扫一遍，把可疑点标出来，标明疑似属于哪个维度」。

这与 `wave2-audit.md` 的「单维度隔离」**不矛盾**——单维度隔离是为了防止**深度审计**时的认知过载（有依据：一个提示词同时检查多类问题会滑向表面问题）。宽扫的定位是**广度**，它本来就不追求深度，因此不受该约束。

6 个问题域（与 `wave2-audit.md` 第 2 节一致）：

| 维度 | 宽扫时要问的一句话 |
|---|---|
| `logic` | 这里的条件分支、循环边界、返回值语义，有没有一眼可疑的？ |
| `concurrency` | 有没有共享状态没同步、异步等待可能泄漏、锁范围可疑？ |
| `security` | 有没有输入直接进敏感操作、路径拼接、反序列化、权限检查缺失？ |
| `error-handling` | 有没有异常被吞、失败静默、恢复路径不存在？ |
| `data-consistency` | 有没有部分写入、事务边界不清、缓存与源数据可能不一致？ |
| `contract` | 有没有签名与调用方不匹配、返回值可能违反约定？ |

**禁止**：宽扫 Agent **不得**为了「看起来全面」而给每个维度都硬凑线索。`leads` 允许为空。

## 第 3 节：输出契约（`role: "sweep"`）

> **⚠️ 你的产物文件必须以一个 ```json 代码块结尾，里面是这个信封。**
>
> **这不是示例，是格式要求。** 你的 Markdown 正文可以随便写（线索讲解、grep 输出、判断依据），
> 但**文件末尾必须有一个完整的 JSON 信封**。
>
> **为什么强调**：2026-11-09 实测 15 个真实产物，**0 个含 JSON 信封**（100% 不合规）。
> 根因就是本节此前只有一个 `json` 示例块，**没有一句「必须写」**。
> 结果是下游校验器要写 73 行 `salvageFromMarkdown()` 去猜——**补偿我们自己的格式失控**。
>
> **自检**：写完产物后，跑
> ```bash
> node <FRAMEWORK_ROOT>/tools/check-payload.mjs <你的产物文件> --role sweep
> ```
> 退出码非 0 就是不合规，按它给的修法补上。

```json
{
  "schema_version": "output-contract-v1",
  "agent_id": "string",
  "role": "sweep",
  "status": "SUCCESS",
  "contract_valid": true,
  "payload": {
    "slice_id": "string",
    "reachability": "PROD | ENTRY | TEST_ONLY | UNREACHABLE | GENERATED",
    "generator_ref": "string|null",
    "files_read": ["path/to/file.ext"],
    "files_unreadable": [{"path": "string", "reason": "string"}],
    "leads": [
      {
        "lead_id": "string",
        "suspected_dimension": "logic | concurrency | security | error-handling | data-consistency | contract",
        "file": "path/to/file.ext",
        "line": 42,
        "quote": "本回合读到的原文，一行即可",
        "why_suspicious": "一句话，不做因果推断",
        "confidence": "HIGH | MEDIUM | LOW"
      }
    ],
    "lead_count": 0,
    "dimension_histogram": {
      "logic": 0, "concurrency": 0, "security": 0,
      "error-handling": 0, "data-consistency": 0, "contract": 0
    }
  },
  "error": null
}
```

**必填字段**：`slice_id`、`reachability`、`files_read`、`leads`（可为空数组）、`lead_count`、`dimension_histogram`。

**`lead_count == len(leads)`**，不一致即 `CONTRACT_VIOLATION`。`dimension_histogram` 的各值之和必须等于 `lead_count`。

**与审计波的关键差别**：`leads` **允许为空数组**。这与 `wave2-audit.md` 的「`findings` 不得为空」**故意不同**——审计波的 `NO_EVIDENCE_FOUND` 是「我按门 0 查过了，没有」，而宽扫的「无线索」只是「快速扫过没看到」，**不构成「已审计」的声明**。覆盖率的记账必须由 `files_read` 承担，不能由 `leads` 为空来推断。

## 第 4 节：门控

宽扫 Agent 返回后，主 Agent 只做机械检查（不需要读代码）：

| # | 检查项 | 通过条件 | 失败处理 |
|---|---|---|---|
| 1 | 信封完整 | 六个顶层字段齐全、类型正确 | `CONTRACT_VIOLATION`，重派 |
| 2 | `role` 正确 | 等于 `"sweep"` | `CONTRACT_VIOLATION` |
| 3 | 计数一致 | `lead_count == len(leads)`，且 histogram 之和 == `lead_count` | `CONTRACT_VIOLATION` |
| 4 | 覆盖声明 | `files_read` 覆盖切片 `files` ∪ `shared_dependencies`，或缺失项在 `files_unreadable` 中 | `CONTRACT_VIOLATION` |
| 5 | 线索可定位 | 每条 `lead` 的 `file` 属于切片文件或 `shared_dependencies` | 该条丢弃，记 `out_of_scope_lead` |

**不检查线索质量。** 质量由二B 深挖和波次三锐评负责。在宽扫阶段筛掉「看起来不靠谱」的线索，等于让主 Agent 做内容判断，违反裁量边界。

## 第 5 节：可达性标记（与预算分配联动）

宽扫 Agent **必须**为切片标记 `reachability`，取值：

| 值 | 判定条件 | 派发含义 |
|---|---|---|
| `PROD` | 该切片的至少一个文件从某个入口点（main / Activity / 注册表 / 路由 / 导出符号）经引用链可达 | 优先深挖 |
| `ENTRY` | **本身就是入口**：CLI 脚本（有 shebang / 直接 `node xxx.mjs` 调用）、被文档或 CI 配置显式调用的工具脚本（2026-11-01 新增） | **优先深挖**（入口比库更值得审） |
| `TEST_ONLY` | 只被测试代码引用 | 深挖优先级最低 |
| `UNREACHABLE` | **既不被任何代码 import，也不是入口，也没有测试引用** | **不深挖**，只在最终报告记「未深挖（不可达）」 |
| `GENERATED` | **文件头自带「勿手改 / 自动生成 / DO NOT EDIT / generated by」标记**（2026-11-01 新增） | **不深挖**，改为审它的**生成器** |

**执行方式**：本波 Agent 在做宽扫的**同时**顺带判断可达性——它可以只做浅层检查（`grep` 该文件是否被非测试代码引用）。**不要求完整 import 闭包**，那是侦察波的职责；二A 的值是对「侦察波没做、或做错」的兜底。

### 5.0 `ENTRY`：为什么「没被 import」不等于「无用」（2026-11-01 新增）

**这是 `UNREACHABLE` 最容易误判的一类。** CLI 工具、构建脚本、探针脚本**天然不会被任何代码 import**——它们由命令行或文档直接调用，因此在纯引用图里看起来是孤岛。

`D:\Web\style` 实测：40 个被判 `UNREACHABLE` 的文件里，绝大多数是这类脚本（`serve.mjs`、`probe-diag.mjs`、`shot-narrow.mjs`、`text-audit.mjs` 等），它们的头部注释写着用途，并在 `deliverables/*.md` 里被人手动调用。**把它们判为不可达会导致最该审的入口代码被跳过。**

**补充判定（必须执行）**：

```
若文件同时满足以下任一，判 ENTRY 而非 UNREACHABLE：
  a) 首行是 shebang（#!/usr/bin/env node 等）
  b) 头部注释或文件名表明它是 CLI / 工具 / 探针 / 构建脚本
  c) 在文档（README/*.md）、CI 配置、Makefile、package.json scripts 中被显式提及
  d) 有可直接执行的形态（`node xxx`、`python xxx`、`bash xxx`）
```

> **判据的保守方向**：**宁可多审一个脚本，也不要漏掉一个入口。** 当无法确定时，标 `PROD` 而不是 `UNREACHABLE`——因为入口代码的缺陷影响面最大。

> **这条修正的代价**：`ENTRY` 判定需要读文件头 + 搜索文档引用，比纯引用图贵。但它是**每片一次**的检查，成本远低于误判导致的漏审。

### 5.1 `GENERATED`：为什么不审生成文件（2026-11-01 新增）

**理由一：审它没有意义。** 生成文件的缺陷必然来源于生成器或输入模板。修生成文件的产物会在下次生成时被覆盖，属于**假修复**。正确的动作是把线索转发给生成器所在的切片。

**理由二：它可能是真实预算的大头。** `D:\Web\style` 实测：198 个纳入文件里 **47 个（23.7%）是生成产物**——包括 48 个自托管字体 CSS（`prototypes/_fonts/css/*.css`，头部写明「由 fetch-fonts.mjs 生成，勿手改」）。若不做区分，近四分之一的审计预算会花在这些文件上。

**判定方法（机械，不看内容）**：读文件**前 10 行**，命中以下任一模式即标 `GENERATED`：

```
勿手改 / 请勿手动修改 / 自动生成 / 由 .* 生成
DO NOT EDIT / AUTO-GENERATED / @generated / This file is generated
Code generated by .* DO NOT EDIT
```

**`GENERATED` 切片的处理**：

1. **不深挖**，`deep_dive_dims` 置空；
2. **必须**在 `payload.generator_ref` 中记录它声称的生成器（从文件头的说明里提取，如 `fetch-fonts.mjs`）；
3. 主 Agent 收到 `GENERATED` 后，**必须**检查该生成器是否已在深挖队列中。若不在，追加一次针对生成器的深挖（这才是缺陷真正的所在）；
4. 最终报告单列「生成产物（未深挖）」并附 `generator_ref`，供人确认生成器确实被审过。

> **不要把它和「资源文件」混淆**：`.css` 生成文件仍是代码（含 `@import`、`url()`、媒体查询），只是**它不是需要人维护的那份代码**。区分依据是「是否由程序生成」，不是「扩展名」。

> **为什么这条重要（实测依据）**：`dsh-fcl-android-launcher` 的 round31 中，478 个首方文件里 273 个是 `fakefx`（JavaFX 移植），实际派发的 40 片里 **29 片是它**（约 72% 审计预算）。而锐评波事后统计，其中 **162 个文件「从任何生产入口都到不了」**，据此撤销了 33 条发现（占全部撤销原因的 80%）。**如果宽扫带了可达性标记，这 29 个 agent 的预算本可以挪给真正可达的代码。**

## 第 6 节：派发规则
```
# 关键：宽扫与深挖共享 discovery_budget，不能先到先得
# 否则宽扫会吃光预算，深挖永远为 0（见下方警告）

if effective_slices < discovery_budget:
    # 小项目：宽扫全量，剩余全给深挖
    planned_sweep_agents = effective_slices
    deep_dive_budget     = discovery_budget - effective_slices
else:
    # 大项目：按比例切分（启发式，非最优值）
    sweep_budget         = ceil(discovery_budget × 0.4)
    planned_sweep_agents = min(effective_slices, sweep_budget)
    deep_dive_budget     = discovery_budget - planned_sweep_agents

concurrency_window = min(8, harness_cap)       # 与 scale-mapping 第 3 节一致
```

> **⚠ 为什么必须切分**：如果直接写 `planned_sweep_agents = min(effective_slices, discovery_budget)`，那么当 `effective_slices ≥ discovery_budget` 时（round31 就是 85 ≥ 40），宽扫会**吃光全部预算**，深挖可用预算为 0——两遍制退化成"只宽扫、零深挖"，比原设计更糟。
>
> 代入 round31：`sweep_budget = 16`、`deep_dive_budget = 24`。宽扫覆盖从 40 片降到 16 片，但**深挖的这 16 片是经可达性筛选后的 PROD 代码**，而原设计那 40 片里 29 片是死代码。

**算术检查（主 Agent 必须算）**：

```
sweep_cost     = planned_sweep_agents
deep_dive_cost = Σ(命中切片的深挖维度数)
total_wave2    = sweep_cost + deep_dive_cost
必须满足：total_wave2 ≤ discovery_budget
若超出 → 按第 6 节优先级截断，其余标 DEFERRED_DEEP_DIVE
```

**深挖触发阈值**（写死，零裁量）：

| 条件 | 动作 |
|---|---|
| 该切片有 ≥1 条 `confidence: HIGH` 的线索 | **必深挖**，且深挖该线索的 `suspected_dimension` |
| 该切片 `lead_count ≥ 3` | 深挖，维度取 `dimension_histogram` 中计数最高的 2 个 |
| 该切片 `reachability == UNREACHABLE` | **不深挖** |
| 其余 | 不深挖，线索原样记入最终报告的「未深挖线索」附录 |

**截断顺序**：先按 `reachability`（`PROD` 优先于 `TEST_ONLY`），同档内按 `lead_count` 降序，再同按切片原始 FIFO。**禁止按文件名、目录名或任何内容特征排序**；`reachability` 是**结构特征**（引用关系），不违反这条禁令。

## 第 7 节：与现有波次的关系

```
波次一 侦察
   ↓ audit_slices + unverified + entry_points
波次二A 宽扫（本文件）         ← 1 片 1 agent，产出 leads + reachability
   ↓ 按第 6 节阈值决定派哪些
波次二B 深挖（wave2-audit.md） ← 按 (slice, dimension) 派，走完整门 0
   ↓ findings
波次三 锐评（wave3-critique.md）← 只处理二B 的 findings
```

**对 `wave2-audit.md` 的影响**：该文件仍是深挖模板，内容基本不变，但有两处需要同步：
1. 它现在**只对二A 标记为「该深挖」的切片**派发，不再是「所有切片」；
2. 它的 `dimension` 取值由二A 的线索决定（`suspected_dimension`），不再是无依据的轮转。

**对锐评波的影响**：`target_finding_ids` 只包含二B 的产出。二A 的线索**不参与锐评**，也不占锐评预算。

## 第 7.5 节：增量落盘（2026-11-04 实测新增，硬规则）

**这一节来自一次实测：3 个宽扫 Agent 里 2 个分析 14–42 分钟后产物仍是 44 字节的空骨架。**

### 7.5.1 规则

```
第 1 步：Write 骨架文件（在开始任何分析之前）
第 2 步：每扫完一个维度，Edit 一次文件，把这批线索追加进去
第 3 步：全部分析完成后，最后一次 Edit 把 status 改成 SUCCESS
```

**禁止「全部分析完再一次性写」。**

### 7.5.2 骨架模板（第一个动作，必须在读代码之前）

```markdown
# {slice_id} 宽扫

- status: IN_PROGRESS
- started_at: {ISO8601}

## Leads

（尚未开始）
```

### 7.5.3 为什么这条必须是硬规则

| 观察到的行为 | 后果 |
|---|---|
| Agent 跑了 19 次 `Bash` 做深入分析，产出全留在上下文里 | 上下文一旦压缩或会话中断，**全部工作消失** |
| 产物文件停留在 44 字节骨架长达 25 分钟 | 主 Agent 从外部**无法区分「正在深挖」和「卡死了」** |
| 会话被压缩（实测出现 5 次 compact 记录） | 早期分析结果被摘要丢弃，最终产物反而更差 |

**最后一条最要命**：这个仓库的 `data.js` 有 2574 行，一个 agent 扫 6 个维度很容易触发上下文压缩。**压缩之后它连自己已经找到过什么都记不清了**——不落盘的代价不是「慢」，是「白干」。

### 7.5.4 与门控的关系（2026-11-09 重写）

`round-detection.md` 与 `state.json` 的 `in_flight` 只能看到「派发了 / 没派发」。

**本节原文声称「产物 mtime 在推进 = 它还活着，mtime 停滞 = 卡住或已死」。这个推断是错的，已删除。**

**为什么错**：实测显示同类任务单 agent 的 Runtime 常态是 **47 分钟**，其中大部分时间在读代码，**根本不写文件**。按「mtime 停滞 = 卡住」判断，一个正常工作的 agent 在前 40 分钟里会被判死 40 次。

| 产物状态 | 现在能推断出的 |
|---|---|
| 骨架 + mtime 持续更新 | **只能说明它在写文件**，不能说明它在工作（也可能在反复改骨架） |
| 骨架 + mtime 停滞 | **什么都不能说明**。可能正在读代码、正在推理、或已死 |
| 空文件 / 文件不存在 | 写盘被拒（`report-naming.md` §5.2）——**这一条仍然有效**，因为它说的是「写失败」，不是「agent 状态」 |
| 完整产物 + status=COMPLETE | 已完成——**这一条有效**，因为它是产物自身的终态标记 |

**唯一有效的活性信号是 harness 报告的状态。** 产物内容只用于**事后**分析（`failure.artifact_bytes` / `last_write_at`），不用于派发决策。

### 7.5.5 校验

**2026-11-09 重大修订：本条原本规定「8 分钟无更新即重派」，已作废。**

**新规则：harness 报告终态之前，不主动终止、不重派。**

| 情形 | 动作 |
|---|---|
| harness 报告 agent 仍在运行 | **等待**。不查产物 mtime、不查进程表 |
| harness 报告完成 | 校验产物 |
| harness 报告失败/超时 | 按 `classify-failures.mjs` 分类处理 |

**为什么废掉 8 分钟阈值**：2026-11-09 观察到的 harness 原生 Runtime 数据显示，**47 分钟是同类任务的常态**（5 个 agent 分别跑 28m36s / 47m48s×3 / 40m31s）。按 8 分钟判据，这 5 个全会被误杀。

而 2026-11-04/05 的实测中，我确实用这个阈值杀掉了 4 个 agent，并把其中 2 个记成 `SCRIPT_TIMEOUT`。**那些归因不可信——它们可能只是还没跑到写产物那一步。**

**保留的唯一判据**：如果 harness **主动报告**某个 agent 失败，才走分类流程。

> **这一条是我在这个项目里犯的最实在的错误之一**：我发明了一个阈值（8 分钟），它比真实工作量小一个数量级，然后据此杀掉了正常工作的 agent，再把结果解释成「agent 有问题」。**衡量工具本身没被验证过，就用它去下结论，是这次的核心失误。**

**产物 mtime 的正确用途**（不是用来杀 agent）：只用于事后分析「这个 agent 写了多少、什么时候写的」，作为 `failure.artifact_bytes` / `last_write_at` 的数据来源。

### 7.5.5.1 失败分类：先定因，再决定重不重派（2026-11-05 新增）

> **重要前提**：本节只在 **harness 主动报告 agent 失败**时使用。
> **不得**用「产物 mtime 很久没变」推断失败——见 §7.5.5 的修订说明。

**2026-11-05 的链式实测**：8 个切片里有 2 个失败（25%），`state.json` 里只有 `state: FAILED`，**没有任何字段记录为什么失败**。而这两个失败的形态不同，处置方式也该不同——但当时无法区分。

**写 `FAILED` 之前必须先分类**，把结果写进 `slices[].failure`：

| `error_type` | 观察到的现象 | 判据 | 重派策略 |
|---|---|---|---|
| `NO_OUTPUT` | agent 输出文件 0 字节，产物从未创建 | 派发后无任何 action | **原文重派一次**（疑似瞬时） |
| `SKELETON_ONLY` | 产物是骨架，`status` 未改为 `COMPLETE` | **只描述产物形态，不推断原因** | **先查 harness 状态**；确认失败后拆维重派 |
| `HARNESS_REPORTED_TIMEOUT` | **harness 明确报告超时**（不是 mtime 推断） | harness 状态字段 | 按 harness 的重试语义；若无，原文重派一次 |
| `TOOL_REJECTED` | transcript 里有 `user-rejected` | 工具调用被权限系统拒绝 | **先修路径**（空格/中文），再重派 |
| `EMPTY_RESULT` | 产物写完但线索数为 0 | 读到了但没找到 | **不重派**，记 `NO_FINDINGS` |
| `CONTRACT_VIOLATION` | 产物有内容但缺必需字段 | 契约校验失败 | 按 `protocol.md` §4.1 计数 |

**必须记录的三个字段**（缺一不可诊断）：

```text
"failure": {
  "error_type": "SKELETON_ONLY",
  "observed": "骨架 status 停在 IN_PROGRESS，mtime 00:20，41 分钟后仍无 Edit",
  "artifact_bytes": 44,
  "last_write_at": "2026-11-05T00:20:00+08:00",
  "inferred_cause": "读完 grep 后未产出任何 Edit 调用，陷入分析循环"
}
```

> **为什么必须记 `artifact_bytes` 和 `last_write_at`**：这两个数字能区分「从没写过」和「写了骨架就停」。实测中前者（`NO_OUTPUT`）和后者（`SKELETON_ONLY`，当时叫 `SCRIPT_TIMEOUT`）的字节数分别是 **0** 和 **44**，而处置策略完全不同——**没有这两个字段，主 Agent 只能盲目重派**。
>
> **`inferred_cause` 允许是推断，但必须标注为推断。** 实测中我通过 transcript 才确认 slice-06 只发起了 1 次真实 Write，「3 次 Edit」只是工具清单里的声明。这个结论来自读 transcript，不是从 `state.json` 能直接看出来的。

### 7.5.5.2 连续失败的处理

同一 `slice_id` 连续 2 轮都是 `FAILED` 时：

| 情形 | 动作 |
|---|---|
| 两次 `error_type` 相同 | **停止重派该切片**，写入 `unverified`，最终报告显式标注「连续失败 2 次，原因：<X>」 |
| 两次 `error_type` 不同 | 允许再试一次（说明不是同一原因） |
| 已重试 3 次 | 无论原因，停止，标 `PERMANENT_FAILURE` |

**实测依据**：slice-02 在 round1 和 round2 **连续失败两次**，`state.json` 里两次都是裸的 `FAILED`，无法判断是同一原因还是不同原因。**没有 `error_type`，这条规则无法执行。**

> **这里的「连续失败」指 harness 主动报告的失败，不是产物 mtime 推断的失败。** §7.5.5 已废除全部基于时间的主动终止，本节只在 harness 报终态后适用。
>
> **单独加「增量落盘」规则没有提高完成率，只是让失败更早可见。** 真正起作用的是**缩小任务范围**，见下方 §7.5.6。

### 7.5.6 窄范围任务才能完成（2026-11-04 对照实验）

同一个 harness、同一天、同一个产物目录，两次对照：

| | 宽任务（slice-16, S05） | 窄任务（S04 变量对账） |
|---|---|---|
| 任务书 | 「扫 6 个维度、两个 970 行文件、12 分钟内返回」 | 「**只跑一条 grep**，记录命中行，不做推断，5 分钟返回」 |
| 允许的推断 | 6 类缺陷判断 | **禁止推断**，只抄 grep 输出 |
| 骨架落盘 | 第 1 分钟 ✅ | 第 1 分钟 ✅ |
| 最终产物 | 9 分钟后仍是 75 字节骨架 | **5 分 25 秒完成，7138 字节**，`status: COMPLETE` |
| 工具调用数 | 大量只读分析 + 自我推翻线索 | **3 次**（Write / Bash / Edit） |
| 校验器结果 | — | `G7 降级抽取 1 条` + `G0 1/1 通过` |

**差异不在模型能力，在任务是否有明确的停机条件。**

宽任务里 Agent 会陷入「再核对一下这条线索是不是我判断错了」的求证循环（最后一次输出原话：「L1 和 L2 是我判断错了，需要撤回」）。**它没有被告知「写到第几条就可以停」**，于是每找到一个候选就继续验证，永远不会到达「写完返回」那一步。

窄任务给了三样东西：固定的命令、固定的输出格式、**固定的产出配额**（只记录 grep 命中，不判断是不是 bug）。这三样合起来构成了一个可判定的终止条件。

**派发规则（硬）**：宽扫任务书必须包含

1. **一条可执行的第一命令**（不是「扫一遍」这类描述）
2. **产出配额上限**（例如「最多 8 条线索，达到即停」）
3. **明确的「不做」清单**（「不验证 DOM、不判断严重性、不读其他文件」）

> **这条比 8 分钟阈值更重要**。阈值只能缩短一次失败的长度，配额能让失败根本不发生。而「每实例 1–2 个维度」的缩小范围，正是配额的一种实现形式。

### 7.5.7 任务书里必须有一个「不可跳过的中间产物」（2026-11-05 实测新增）

**链式实测中 8 个切片失败 2 个（25%），两次都是「骨架写出后再无 Edit」**——agent 读完文件就再没产出任何 Edit，空转 10 分钟到超时。按 §7.5.5.1 的分类，这两个属于 `SKELETON_ONLY`（当时写作 `SCRIPT_TIMEOUT`）。

从 transcript 里挖出的实际行为（slice-06）：

| 观测 | 值 |
|---|---|
| 声明的工具调用 | 4 次 Write + 3 次 Edit |
| **实际生效的写入** | **1 次**（只有骨架） |
| 5 次 `Bash` / 3 次 `Grep` / 3 次 `Read` 之后 | 无任何 Edit 调用 |

**它读完了，然后没有下文。** 不是权限问题（无 `user-rejected`），不是配额问题（配额是「最多 3 条」，它 0 条）。

**修法：在任务书里插入一个强制的中间落盘点。**

```
第 1 步  Write 骨架
第 2 步  跑完第一条 grep  → 立刻 Edit 把 grep 原始输出贴进去
第 3 步  跑完第二条 grep  → 再 Edit 一次
第 4 步  从已贴入的原始输出里挑线索 → Edit 写成 ### L1 ...
第 5 步  改 status: COMPLETE
```

**关键差异**：第 2、3 步要求的是「**把工具输出原样贴进去**」，不是「分析后写结论」。

| 任务形态 | agent 要做的事 | 卡住的原因 |
|---|---|---|
| 「扫这 6 个维度，找出可疑点」 | 先理解、再判断、再产出 | **判断没有终点**，可以无限求证 |
| 「跑这条 grep，把输出贴进去」 | 复制粘贴 | **动作有终点**，贴完就完成 |

实测证据：同一批任务里，要求「贴 grep 输出」的 6 个切片全部完成，要求「扫 6 个维度找可疑点」的宽任务 3 次全部超时。

> **这条规则的代价是任务书变长、步骤变机械**，收益是每个中间步骤都有可验证的落盘动作。**「聪明的任务书」在这套框架里是负债**——它给了 agent 太多判断空间，而 agent 在判断空间里会一直判断下去。

## 第 8 节：常见失败模式

| 失败模式 | 表现 | 判定 |
|---|---|---|
| 宽扫越界做深度推断 | `leads` 里出现完整因果链、`basis` 式论证 | 不违规，但**浪费 token**；宽扫应只写「为什么可疑」一句 |
| 宽扫自称「已审计」 | 返回 `NO_EVIDENCE_FOUND` 式的结论性表述 | `CONTRACT_VIOLATION`——本波不下「无问题」的结论 |
| 为每维硬凑线索 | histogram 每维都恰好 ≥1 且都很模糊 | 不违规但低质；深挖会大量证伪，不惩罚 |
| 全片标 `UNREACHABLE` 以逃避深挖 | 与 `files_read` 矛盾（能读到却不判定可达性） | 由波次三 Devil's Advocate 核查，记 `COVERAGE_GAP` |
| **分析完才一次性落盘** | 产物文件长期停留在骨架，Agent 输出持续增长 | **违规**（§7.5）。**但不得据此杀 agent**——见 §7.5.5，只等 harness 报终态 |
| **产物写入被权限系统拒绝** | 返回 `user-rejected`，Agent 静默继续 | `PERMANENT_FAILURE`。见 `report-naming.md` §5.2（目录含空格） |
| **写了骨架就停、无任何 Edit** | 产物 44 字节，`status: IN_PROGRESS`，无 `### L` 条目 | `SKELETON_ONLY`（§7.5.5.1）。**先查 harness 状态**；确认失败后拆维重派，任务书改为「贴 grep 输出」 |
| **产物从未创建** | 文件不存在，0 字节 | `NO_OUTPUT`。**先查路径可写性**，再原文重派 |

## 第 9 节：派发给深挖任务时，行数与文件清单必须现场核实（2026-11-02 新增）

**这一节来自一次真实的派发事故。**

### 9.1 事故经过

`D:\Web\style` 第 2 轮，主 Agent 派发深挖任务时，任务书里写了这些行数：

| 文件 | 任务书写的 | 实际 | 偏差 |
|---|---|---|---|
| `S25/index.html` | 738 | **389** | +90% |
| `S27/index.html` | 1119 | **498** | +125% |
| `S28/index.html` | 1187 | **531** | +124% |
| `S29/style.css` | 1461 | **381** | +283% |
| `S25/assets/*.mjs`（3 个 / 937 行） | 937 | **文件不存在** | 全错 |

**根因**：这些数字是从本波（宽扫）产出的 `line_count` 字段读的——那是**整个切片的总行数**，被误当成了**单文件行数**。而 `S25/assets/*.mjs` 是凭上一轮切片的目录印象臆造的，`find -name "*.mjs"` 实际返回空。

**这次没有造成漏审**，因为接替的 Agent 自己用 `wc -l` 和 `find` 核了出来，并主动补审了三份未列在范围内的 `style.css`。**但这是运气，不是设计。**

### 9.2 规则

派发深挖任务时：

```
1. 行数必须现场取：
   wc -l <file>        # 单文件
   或对每个 files[] 元素逐个 wc -l 后分别写出
   ❌ 不得把切片的 line_count 当作单文件行数
   ❌ 不得凭记忆/印象写行数

2. 文件清单必须现场核对存在性：
   ls -la <path>       # 或 find
   ❌ 不得凭切片目录印象臆造文件名
   若清单里有不存在的路径，派发前就要发现，而不是让子 Agent 去撞

3. 若确实无法现场核实（如 harness 不支持），必须在任务书里**显式标注**：
   "以下行数为切片估算值，单文件行数请以实际 wc -l 为准；
    若发现清单中的文件不存在，请在报告中说明并跳过。"
```

### 9.3 为什么这很重要

- **行数错了会让 Agent 误判工作量**：它可能因为"这个文件 1461 行太大"而采取抽样阅读，实际只有 381 行、本该逐行读；
- **文件不存在会让 Agent 浪费时间**：它会花时间 `find`、怀疑路径、甚至猜测是不是权限问题；
- **更糟的是"沉默地跳过"**：如果 Agent 没核出来，它可能少审一批文件而报告里看不出来。

**这条规则的代价极低（几条 `wc -l`），收益是消除一整类"任务书本身有错"的失效。**

### 9.4 反过来也成立：子 Agent 有义务核对任务书

**同时应当告诉子 Agent**：任务书里的行数、文件名是**待验证的输入**，不是事实。

> 若发现任务书的行数或文件清单与实际不符，**必须**在报告中显式说明「范围偏差」，并按**实际文件**审计，而不是按任务书硬凑。

这条与 `evidence-policy.md` 第 8 节「引用必须可核验」是同一条原则的延伸——**连派发指令本身也要可核验**。
